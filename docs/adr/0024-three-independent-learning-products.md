### The owner's requirement

The owner's answer of 2026-11-11, verbatim:

> A Learning Path is a separate learning product, not simply a collection of individual courses.
>
> If a learner has already completed a course individually through the Library, that completion must NOT count towards the same course when it is included in a Learning Path. The learner must complete it again within the Learning Path.
>
> Therefore, Individual Course Progress and Learning Path Progress must be tracked independently, even when both use the same course content.
>
> The one-official-attempt rule should also be maintained separately for each learning context.
>
> Most importantly, the Continue button, chapter lock/unlock logic, Learning Path progress, dashboards and reports must all follow the same path-specific completion rule.
>
> Once a learner completes the official attempt launched from the Learning Path, the next chapter should unlock permanently and remain accessible when they return to the Learning Path.

The plan widened this, with the owner's agreement, to three products: the Individual course, each Learning Path, and each day of a learner's Journey.

### Words

- **Product**: the Individual course, a Learning Path, or a day-wise Journey.
- **Context**: where one attempt belongs. One of `individual`, `path:<learning_path_id>`, `journey:<journey_enrollment_id>:<day>`, `preview`. Written when the attempt row is inserted and never changed.
- **Official attempt, revision visit, granted retake**: ADR 0014's terms, read per (learner, course, context).
- **Official rule**: within one (learner, course, context), the rows that count are those that are not abandoned, not revision rows and not previews. One rule, used by SQL and TypeScript alike (step 9).
- **Done**: the context's official result satisfies the resolved `pass_required` (step 10). For a path step, done means `passed_ever` (step 44).
- **Step**: a `learning_path_courses` row. **Day**: one entry of a frozen `journey_versions.days`.
- **Recorded enrolment**: a row in `course_assignments`, `learning_path_assignments` or `journey_enrollments`. Under D15 a self-enrolment is such a row; nothing is implied from an attempt.

### Why one record

The ADR 0023 draft is right about Learning Paths and leaves Journeys, rewards, previews, the webhook and the emails on the shared result. Extending it would keep two rules alive. This record keeps what the draft got right (per-context official attempt, visits and grants; one pure result function with a guard test; the open-attempt index split; paste-first with an either-state check) and replaces the rest. Section "Alternatives considered" lists what changes.

## Decision

Goal: every learner record carries one fixed product context; "official" is decided once per context by one rule; one database function records completion side effects; each product reads only its own records through one progress rule; a read-only Overview shows the three side by side.

Out of scope: any change to the content engines (KIVO, SCORM, third-party cmi5); SCORM 2004; per-product attempt tables; yearly run instances (D5); a per-consumer webhook address; lifting the one-attempt policy clamp; the Guardian track (ADR 0022) and P5; any rewrite, move or deletion of a learner row.

### A. The model

1. **Principles.**
   1. One content library, one attempt table, one context per attempt row, fixed at insert.
   2. "Official" is derived, never stored. It is computed by one SQL view family and one TypeScript function, with one SQL helper, and a parity test keeps them equal.
   3. One database function writes completion side effects (points, journey day credit, path completion, the email claim). It fails closed and a sweep retries it.
   4. Each product has one progress rule, in one SQL object with one TypeScript twin. No reader of one product reads another product's rows. Three deliberate exceptions: rule R-3 of the statements route (a statement naming another attempt of the same learner on the same course is answered and dropped, `statements:132-166`, LIVE); the Overview's unique-learner count; and the paid points key per course, which the owner chose under D8.
   5. History is never rewritten (`docs/ARCHITECTURE.md` section 3, principle 3). No row moves between contexts. Foreign keys refuse a delete that would erase a context. The 0107 backfill writes only new columns: a label derived from each row's own columns and two "already handled" markers. No existing column value on any learner row changes.
   6. Enrolment stays in the three tables that exist today. A self-enrolment is a recorded row in the same table (D15).
   7. A preview is its own context and counts nowhere.

2. **The model.**

   | Product | Recorded enrolment | Context on each attempt | Progress rule (SQL, TypeScript twin) | Rewards |
   |---|---|---|---|---|
   | Individual course | `course_assignments` (user, team, org, group; `release_at`, `due_at`; `source` `admin` or `self`) expanded by `v_course_enrollments_expanded`, direct arms only | `individual` | `v_individual_enrollment_status`; `contextResult({kind:'individual'})` | paid once per course; a 0-point event row for this context (D8) |

| Case | Behaviour | Mechanism |
|---|---|---|
| Same course on days 3 and 7 of one journey | Two official attempts, two scores, two day credits | `journey:E:3`, `journey:E:7` (D1) |
| Same course in paths P and Q | Two official attempts; P moves nothing in Q; points paid once | `path:P`, `path:Q`; the editor warns |

| Finished journey, learner reviews a day | A revision visit tagged to that day | Step 22 |

| Completion side effects fail | No points, credit, webhook or email; the save succeeds; the sweep retries and the webhook then fires; no email | Steps 12, 16, 31, 32 |

### N. Security, scale and performance

66. **RLS and grants.** Every new relation has RLS on, a policy and literal grants in its file; service-only tables carry an explicit no-access policy, because `tests/rls-audit/audit.sql:247-248` fails any table with `organization_id`, RLS on and no policy, and that halts production deploys; a table with RLS off raises the cron audit's critical alert. ## Consequences

- A learner's result on a course is a result in a product. The Library, each Learning Path and each journey day keep their own official attempt, revision visits, grants, bookmark, score and status. Finishing a module in one place completes or unlocks nothing elsewhere.
- Every binding policy keeps its content and is scoped to the context. ADR 0017's guard is untouched: it is per attempt row.
- Course reports show the Individual product. ADR 0020's path arm and hold-back, on staging since 2026-11-11, never reach production as a served state.
- Analysts can learn for real and preview on purpose (D7). Under reading R6 the same holds for `super_owner` and `admin`, and a launch is never a preview by role; that part replaces the owner's rule of 2026-11-06 and waits for the owner's confirmation. A Preview from a path step has no Continue (A21).
- Completion side effects have one writer that fails closed. A passing error no longer pays points or fires a webhook; it delays them until the sweep.
- Each product sends one completion email. cmi5 learners gain the course email; a granted retake no longer re-sends anything. One exception to D16, for the owner to accept or refuse (A20): a journey that an admin's publish completes sends no email.
- Paths and journey programs with learner attempts cannot be deleted; they are archived.
- "Everyone in this org" learners have recorded enrolments, so reports, the Overview and the CRM can see them. Members who never start are not counted.
- The CRM contract has a version per key. Version 1's meaning changes on release; the agreement is a release gate, and Yoddha reading version 2 is a gate on the first production learner.
- The effort is about 69 executor-days plus journey activities, against the plan's 50. Production's first release carries phases 1 to 7 and 9a, about 59 build days, against the plan's 25 for phases 1 to 4; the first learner follows the gate of step 74a.
- Between the phase 2 merge and the production sitting, a production tag of `main` is allowed only while production has no learner (decision A19).
- Binding on later work: a new reader of "done", "official", "in progress" or "revision" calls `contextResult`, `readContextResult` or a product's progress rule, never `computeScoring` or a raw completed-or-passed test; a new write of an attempt, request or visit names its context; a new column that carries a context references its parent `on delete no action`; a new completion side effect is added inside `record_learning_activity`; a new server-render re-read carries its own abort signal.

## Alternatives considered

- **The ADR 0023 draft as written (paths only).** Individual plus each path as contexts, keyed on `learning_path_id`, journeys reading the Individual result. Not chosen: a Library completion would still credit a journey day and rewrite the row; a course on two journey days stays stuck; previews share the Individual slot and stay previews by role; journey membership keeps cancelling points; classification still fails open; the SCORM webhook stays unlatched; 0105's path arm stays in course reports. Kept from it: the diagnosis, the per-context scope of ADR 0014, `contextResult` with the guard test, the index split, `no action` foreign keys, the paste-first order with an either-state check, its reader sweep as the build checklist. Changed from it: journeys become contexts (D1); its decision (h), "the standing result relocks", is replaced by D14; its decision (d), course reports in the context of enrolment, by D2; its decision (c), webhook for the Individual context only, by the per-organisation scope; its decision (g) by D7.
- **Three attempt tables, one per product.** Triples the runtime, the LRS feed and the CRM logic. Rejected.
- **Filtering only in reports.** One product would still complete another. Rejected.
- **A stored `learning_records` table with a cached official pointer.** A writer on the launch hot path, a circular foreign key and a cache that can drift, for nothing a view over enrolment and attempts does not give. Rejected.
- **A generated key without an explicit kind.** A careless insert would silently become an Individual attempt. Rejected in favour of `context_kind` with the CHECK.
- **Nulling the tags on old preview rows.** An update of existing attempt columns. Rejected (step 6).
- **A one-time `side_effects_at` stamp.** Loses a pass that arrives after `completed`. Rejected (step 12).
- **Changing the grain of `v_course_attempt_summary` in 0107.** Six LIVE matviews would count a learner in two statuses until 0109. Rejected for new-name context views (step 9).
- **`notification_log` or `xp_events` as the email latch.** Neither can serve (step 15).
- **Points per product instance (D8 a).** Farmable by repeating a module in open or recreated paths; needs a ledger rule change. Declined by the owner's choice of (c).
- **Freezing the journey deadline per enrolment (D17 a).** Declined by the owner.
- **A feature flag on the core.** Two rules on one table. Rejected (step 72).
- **A webhook scope per API key.** The webhook has no key when it fires. Rejected for a per-organisation setting.
- **Run instances for yearly re-assignment now.** Deferred (D5); `path_run:<id>` stays an additive key later.
