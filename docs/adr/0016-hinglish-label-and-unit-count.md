## Decision

### A. Unit count (U-1A)

1. **A quote-aware, `COURSE_CONFIG`-anchored matcher.** `countLearningUnits` (`lib/courses/units.ts:15–57`) finds the engine's config object by the first occurrence of `COURSE_CONFIG` in the launch HTML and, from there, the first `slides` key written as `"slides"`, `'slides'` or bare `slides`, followed by optional whitespace, `:` and `[`; when `COURSE_CONFIG` is absent it falls back to today's search from the start of the text with the same three spellings. The bracket matcher skips `'`, `"` and backtick strings with their escapes (today it skips `"` only, lines 28–37). The JSON parse of the array and the structural fallback (lines 49–56) are unchanged; the 8 MB scan bound (line 25) is unchanged. `countUnitsInZip` (lines 60–78) is unchanged.
2. **Recount once.** `manifest_data.unitCountAlgo` (jsonb key, no migration) records which matcher produced `unitCount`. `ensureUnitCount` (`progress.ts:39–46`) recounts a version whose `unitCount` is null and whose `unitCountAlgo` is not `2`, from the stored launch file as today (lines 48–60), and writes `unitCount` and `unitCountAlgo: 2` in the one update it already makes (line 66); a version with a number keeps it (the number is right whenever today's matcher found the array); `upload.ts:135–140` and `direct-upload.ts:416–437` write `unitCountAlgo: 2` with the count they store. Effect on learners: `progress_pct` can only rise (`process-statement.ts:172–174`; `progress.ts` keeps the max of its signals), so a recount never lowers anyone's progress; a revision visit changes no progress (ADR 0014).

### B. The declared language (L-a)

3. **The parsers keep the declared language.** `parseTincanManifest` reads `name['@_lang']` of the course activity (`tincan.ts:52`) and the cmi5 parser the first `langstring['@_lang']` of the course title (`cmi5.ts:68`) into `manifest_data.raw.lang` (a BCP 47 tag as written, untouched case; absent when the manifest declares none). Existing rows are not rewritten; only new uploads carry the key.
4. **The validator reports it.** `validatePackage()` adds `declaredLanguage: string | null` to `report.package` (`validate-package.ts:37–50`), from the parsed manifest, on both the upload and the stored scan.
5. **The suggestion is a pure function in `lib/i18n/languages.ts`.** `suggestLanguageSlot(declared: string | null | undefined): LanguageCode | null`: the declared tag when it is a supported code (`isSupportedLanguage`), else its primary subtag (the part before the first `-`, lower-cased: `hi-Latn` → `hi`, `en-US` → `en`, `en-IN` → `en`) when that is supported, else null. `suggestDisplayName(declared): string | null`: `"Hinglish"` when the declared tag is `hi-Latn` (case-insensitive), else null. Nothing else in this record decides a language.
6. **The upload dialog preselects and prefills; the admin confirms.** In `library/upload/page.tsx`, when the validation report of the chosen file arrives with a `declaredLanguage`, the dialog sets `language` to `suggestLanguageSlot(declaredLanguage)` when that is not null and the admin has not changed the select (lines 55, 313–317, 340), and sets `displayName` to `suggestDisplayName(declaredLanguage)` when that is not null and the field is empty (lines 56, 318–325, 341–346); a slot already taken on an existing course (`disabledCodes`, line 316) is not preselected. The admin may change both before uploading; nothing is written until they confirm, so the relabel stays theirs. This is what L-a means by "admin confirms".
7. **The upload routes use the suggestion only where today's default applies.** `upload/route.ts:112` and `init/route.ts:50` replace the bare `"en"` for a new course without a chosen language by `suggestLanguageSlot(declaredLanguage) ?? "en"`, with the declared language read from the uploaded manifest (multipart) or the posted manifest XML (init); an explicit `language` always wins, exactly as today. The default assignment moves after the manifest is read, because today it runs before the manifest is available: in the multipart route the zip is in memory from line 83 and is parsed once, inside `uploadCoursePackage` (`lib/courses/upload.ts` line 60, called at `upload/route.ts` line 215 with `language` from the form), so line 112's `"en"` moves into that helper, between the parse and `resolveTargetPackage` (lines 68–71), applied when `opts.courseId` is absent and `opts.language` is null (the route passes null when the caller sent none; no second parse of the zip); in `init`, the default moves below the manifest check at lines 77–78 and reads the declared language from `body.manifest.xml` through the parsers of step 3. The `display_name` default on those two paths stays null (decision 2 below offers the prefill there as a severable choice).
8. **A validator info row.** `validatePackage()` pushes `declared-language` with status `info` when the chosen slot and the declared tag differ by primary subtag ("The package declares `hi-Latn`; the chosen language slot is `en`."), and `pass` when they agree or the package declares nothing; consistent with the slot comparison of ADR 0005 step 5, informational like the script detection of ADR 0004 step 6, never a block.
9. **What L-a leaves, recorded.** "English name · code" stays in small print on the picker, the change-language menu and the upload dialog's package option, and the Hindi name or code stays the main label on the languages table, the replace dialog and the Library list chip (the six files cited in Context); a Hinglish course therefore reads "Hinglish" wherever `display_name` is the label and "Hindi · hi" beneath it or beside it elsewhere. Only L-b removes that, and L-b is not taken (step 10). Packages exported before the 2026-10-21 editor fix declare `en-US`, so for them nothing changes: no suggestion other than `en`, no prefill. Existing packages and slots are untouched; L&D keeps the relabel of ADR 0004 decision 4 for them. This step goes beyond the wording "an L&D action, not code" of ADR 0002 decision 6 (line 26) and ADR 0004 step 15 (line 78): the relabel is still confirmed by L&D, but the suggestion is code. The two accepted records are not edited; the dated notes of step 15 record it.

No code before such a decision.

### D. Readable question labels (L-c (i))

11. **`readLang` is exported** from `lib/interactions/extract-xapi.ts` (lines 58–69) unchanged, so the reports read a label by the same rule as the learner attempt page.
12. **A pure merge helper, `lib/interactions/labels.ts`** (the existing `lib/interactions/` module, no new folder): `missingLabelIds(rows)` returns the `interaction_id`s whose `interaction_label` is null, in row order; `mergeInteractionLabels(rows, labels: Map<string, string>)` returns the rows with each null label replaced by the map's value when present, the id staying the fallback otherwise.
13. **One bounded lookup per page render.** In `reports/page.tsx` after the matview read (lines 142–148) and in `analytics/page.tsx` after its read (lines 834–839): for each missing id, one service-client query over `xapi_statements` restricted to the course's attempts (through `course_attempts` and `course_versions.course_id`), `verb` = answered (`http://adlnet.gov/expapi/verbs/answered`), `raw->object->>id` equal to the id, `limit 1`, taking `readLang(raw.object.definition.name)`; then `mergeInteractionLabels`. The loop is bounded by the number of missing ids, which the matview already bounds per course (one row per `(course_id, interaction_id)`), and the lens page reads ten rows (line 839); the result is deterministic: the same id yields the same label on every load, which a single capped query over the course's statements would not (many learners could fill the cap with a subset of the ids). The renderers (lines 349 and 1274) are unchanged; the id stays the fallback when no statement carries a name. No migration: the matview itself still holds null for non-English labels, so a direct reader of it (a CSV export, an analyst's SQL) sees ids until the P5 migration of ADR 0005 step 14, which removes this lookup.

### Risks and protections

| Risk | Protection |
|---|---|
| Learners: progress drops after a recount | `progress_pct` is never lowered (`process-statement.ts:172–174`); a recount only adds the units signal; a stored number is kept |
| Grading or official results | nothing in this record reads or writes `score`, `completion_status`, `success_status` or `completed_at`; no scoring code is touched |
| A package lands in the wrong slot | the suggestion is a default the admin sees and may change (step 6); an explicit `language` always wins on the routes (step 7); a slot already taken is never preselected; the `declared-language` info row shows a mismatch |
| An API caller's new course changes slot | only when the package declares a supported tag or subtag and the caller sent no `language`; packages from before the editor fix declare `en-US` and keep `en`; recorded under Consequences |
| Privacy | `raw.lang` is a language tag; the label lookup reads statement rows the admin pages already read in aggregate; no learner identity is added to any report |

| A `responded` statement counted as a wrong answer | the breakdown filters on `answered` (`0031:353–356`); unchanged |

## Consequences

- A Hinglish KIVO package uploaded by an admin arrives in the `hi` slot labelled "Hinglish" unless the admin chooses otherwise; learners see "Hinglish" in the picker and the menu with "Hindi · hi" in small print; admins see "Hinglish" on the course page and in the display-name column and the Hindi name or code on the three admin surfaces of step 9.
- An API caller creating a new course without a `language` gets the declared language's slot instead of `en` when the package declares a supported tag or subtag; a caller that sends `language` sees no change.
- The admin question reports show question text for non-English KIVO courses; CSV exports and analysts' SQL over the matview still see ids until P5.
- Minified KIVO packages gain a unit count and therefore partial progress on the admin views and the CRM feed; versions already counted are unchanged.
- Forwarded feedback statements carry a verb display and the profile version moves with this build (1.1.0, or left as ADR 0014's pull request set it: step 14); the question analytics are unchanged.
- U-2 and LMS-SCORMNOTE stay open and listed; the engine-floor warning follows the redeploy as PR 3.
- Code only; nothing changes on an environment until the build is deployed there; production with the next owner-run tag.

## Alternatives considered

- **A `hi-Latn` slot code (L-b):** reverses ADR 0002 decision 2 and ADR 0004 step 6 / decision 4 of 2026-10-16; the owner answered "L-b no"; recorded in step 10 for the day a later ADR ever takes it.
- **Bring the matview label change forward as migration 0103 (L-c (ii)):** a hand-applied migration ahead of 0100–0102 on staging and before 0100 on production, with the P1 audit's "no 0100-or-later objects" probes restated; the owner chose (i); the P5 migration of ADR 0005 step 14 stays where it is.
- **One capped query for every missing label (FIXPLAN-v3's `limit 500`):** not deterministic: a course with many learners can fill the cap with a subset of the ids, so a label present on one load is absent on the next; rejected for one bounded query per id.
- **Leave the upload routes on `"en"` and suggest in the dialog only:** FIXPLAN-v4 §5.5 names the two routes, and the owner confirmed L-a as put; the route change is limited to the default and an explicit language always wins; the display-name prefill on the routes is offered as a severable decision instead.
- **A script-detection rule deciding the slot:** ADR 0004 step 6 keeps script detection informational, and every non-English slot on staging is Latin script, so a script rule cannot tell Hinglish from English; rejected.
- **Add the D-7 (c) extension keys to the profile with `responded`:** their shape against the BLUEPRINT's `question/*` family is undecided (LMS-EXT); rejected here, decided before the 2.0 export work.
- **Fix U-2 and LMS-SCORMNOTE in PR 2:** both Low; the owner's direction of 2026-10-18 as FIXPLAN-v4 row G records it; recorded and not scheduled.
- **No `PROFILE_VERSION` bump for an added verb:** the file's own rule is to bump rather than change; an analyst joining LRS history needs to know from which build the verb is listed; rejected.
