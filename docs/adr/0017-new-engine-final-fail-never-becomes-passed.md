## Decision

### A. The rule and its scope

1. **The rule.** For an attempt on a course version built with the released KIVO A.1 engine or later (verdict `final`, step 3): once the row's `success_status` is `failed`, no later result changes it within that row. A later `passed` (a cmi5 or plain-xAPI AU-level statement, or a SCORM commit deriving `passed`) is received, stored where today's code stores it, answered as today, and recorded as not applied (step 12); `success_status`, `status` and `score` stay as the final fail left them; nothing keyed on a pass fires: the once-per-course `course_passed` marker and the score bonuses (`0084_course_passed_milestone.sql:222–230, 232–261`), the journey day (`journey_record_completion`), ADR 0015's second `course_completed` (its decision function sees `before` and `after` equal, `branch:0015:89`), the SCORM `justPassed` webhook and the `asset_completion` email (`commit/route.ts:251–255, 306–342`). A later `failed` with a different score does not move the score either (decision 6: the narrow case the owner's rule implies; the general score rule for older and third-party content stays deferred by the owner, ADR 0014 "Decisions requested", `branch:0014:280, 282`). On SCORM the saved course data (`cmi_data`) freezes at the official fail as well (decision 3b, broad; step 9). For a version built with an older engine, a non-KIVO package, or a version whose engine cannot be told, today's behaviour stays (D-2); every such upgrade is logged, and one where a KIVO build's stamp cannot be read, or the stored launch file cannot be read at all, is also recorded on the row (step 6). An administrator-approved extra attempt is a new row and a new registration (ADR 0014 Terminology) and is unaffected by construction. Learner history is never rewritten: the statement is kept write-once, the fail stays, no row is deleted (`docs/ARCHITECTURE.md` §3 principle 3). Activity credit is unchanged: the second session's statements and commits still call `gamification_record_activity` on the official row (`statements/route.ts:158–170`; `commit/route.ts:238–247`), which moves the streak and `last_active_day` on every call (ADR 0014 step 12); only pass-keyed effects are held.

2. **Scope: cmi5, plain xAPI and SCORM 1.2, the same rule and the same record on each** (decision 3). Without SCORM the owner's "never" would differ by export format for one engine: Ambak runs a KIVO SCORM package on the engine's SCORM 1.2 path (`K0009:12`), and nothing enforces the policy that KIVO courses go to Ambak as cmi5 (`K0009:38`; the validator note LMS-SCORMNOTE is recorded and not scheduled, ADR 0016 step 15). Untouched: a `passed` first and a later `failed` (never downgraded, `process-statement.ts:112`; no record); non-AU statements; rows whose `success_status` is `unknown` (step 7); every third-party package (`non_kivo`, step 3); the revision gate of ADR 0014 step 4, which runs first on both routes.

### B. Identifying a new-engine version (confirmation 1)

3. **The stamp, the floor and the verdict.** The KIVO editor writes its `ENGINE_VERSION` into every export's launch file from one build function shared by every export format (`COURSE_CONFIG.settings.engineVersion`, `<html data-engine-version>`, `<meta name="engineVersion">`, the generator meta; editor `D:/My Authoring Tool/kivo-wt-release-a/index.html` as read at its HEAD ee463cb: `engineVersionFromSource` at `:8581–8585`, the `COURSE_CONFIG.settings.engineVersion` copy in `buildHtml` at `:8597`, the `__ENGINE_VERSION__` replacement at `:8617`; `engine.a1.html:21, 24, 25`); an engine without the constant is stamped the literal `unknown` (`index.html:8582, 8584`). The LMS already extracts the value after recognising a KIVO build (`lib/courses/validation/validate-package.ts:123, 147–153`) and today uses it only as report text (`:554–568`). Nothing at run time names the version, and the outcome document's `reg` marker and the bookmark are learner-writable and absent exactly in N18 (`state/route.ts:84–93`; `engine.a1.html:11363, 13533–13537`), so the signal is the package's stamp, per course version (an attempt is bound to one version: `process-statement.ts:54–58, 81–84`; `commit/route.ts:85–92`). New file **`lib/courses/engine-version.ts`** (the existing `lib/courses/` module, no new folder; no `next/*` import, no runtime Supabase import, the `lib/attempts/restart.ts` shape):
   - `extractEngineStamp(html: string | null): string | null`: the five regexes of `validate-package.ts:147–153`, moved here verbatim; `analyzeLaunchHtml` calls it, so the validator's `engineVersion` finding and its report text are unchanged (a behaviour-preserving refactor).
   - `parseEngineVersion(s): [y, m, d, n] | null`: `^\d{4}\.\d{2}\.\d{2}(\.\d+)?$`, a missing `.N` = 0; `unknown`, `sketch-g2`, empty and undefined → null.
   - `compareEngineVersion(a, b)`: numeric, segment by segment (the rule of KIVO's build plan, `docs/release-a-build-plan.md:2145`; `:2144` is blank).
   - **`OUTCOME_FINAL_FLOOR = "2026.10.28"`**: the first **released** engine whose written fail is final (T11, `engine.a1.html:11347`; KE-9). **Pinned for good** (decision 1): a comment says it never moves, the unit test asserts the literal, and if a later engine ever needs a different threshold it is a new constant, never a change to this one. The value is confirmed in the pull request from the live editor after the A.1 redeploy (the way K0010 read the live engine on 2026-10-28; ADR 0014's note of that date records the live editor still at 2026.10.05.2), recorded under this record as a dated note; a reading other than `2026.10.28` stops the merge until the right value is confirmed, and is never a later edit of the constant. "Released" matters: the candidate builds of rounds 1–4 (`build/T/a1/` … `a1r4/`) carry the same stamp without T11; holding a pass on such a kit is the intended result anyway, no candidate kit is recorded on staging, and if one is ever found there it is re-exported or deleted (staging is test data, `docs/ARCHITECTURE.md` §3 principle 5). `ENGINE_FLOOR_WARN`, the movable recommended minimum of the validator's warning (ADR 0006 step 9; LMS PR 3), is **not** defined here: PR 3 defines it beside these helpers, and its test asserts `compareEngineVersion(ENGINE_FLOOR_WARN, OUTCOME_FINAL_FLOOR) >= 0` and that the two are separate exports.
   - `outcomeFinalVerdict({ stamp, readError? }): "final" | "older" | "non_kivo" | "unknown" | "unreadable"`: `final` when the parsed stamp is at or above the floor; `older` below; `non_kivo` when the stamp is `null` (the file was read and is not a KIVO build); `unknown` when the stamp is a string that does not parse (the stored literal `unknown`: a KIVO build whose stamp is missing or unparseable); `unreadable` when the read of step 5 failed (a storage error, a failed fetch, or a null head: no object at the key) or recorded `too_large`. Only `final` guards. `older` and `non_kivo` keep D-2 with a log line; `unknown` and `unreadable` keep D-2 with the log line and the on-row `applied` entry (step 6).

4. **Stamping at upload, both paths** (after ADR 0016's PR 2, which edits the same lines, `branch:0016:42, 47`). `lib/courses/upload.ts`: `manifestData(manifest, unitCount, identity?, unitCountAlgo?, engineVersion?)` (`:207–220`; PR 2's plan, T2 item 2, gives the fourth slot to `unitCountAlgo`, so `engineVersion` is the fifth, after it, as the lead's Round 4 fixes) gains `engineVersion` when the argument is a string or `null`, and omits the key when it is `undefined`; at `:138` the launch text goes straight into `packageIdentity(...)` and is never kept, so a small refactor holds it in a local (`const launchHtml = await launchHtmlFromZip(zip, manifest.launchUrl)`, `:222–241`, 16 MB cap at `:237`) and passes it to both `packageIdentity` and the stamp: `engineVersion = launchHtml === null ? undefined : (!kivo ? null : (parseEngineVersion(stamp) ? stamp : "unknown"))`, with `kivo` and `stamp` from `analyzeLaunchHtml(launchHtml)` (`validate-package.ts:116–123`). The reserve-first insert at `:98` keeps `manifestData(manifest, null)` (no key); the ready write at `:139–142` carries it beside PR 2's `unitCountAlgo: 2`. `lib/courses/direct-upload.ts`: the `launchHtml` of `:415–428` (`pr1a::424–437`; its cap is `DIRECT_UPLOAD_LIMITS.maxLaunchReadBytes`, `:70`, `pr1a::75`, which PR 2 sets from `MAX_LAUNCH_READ_BYTES`) feeds the same expression; the finalize `md` at `:437` (`pr1a::446`, which PR 2 makes `{ ...version.manifest_data, unitCount, unitCountAlgo: 2, identity }`) gains the key under the same rule. **Four states, by design**: a parseable string (a stamped KIVO build); the literal `unknown` (a KIVO build whose stamp is missing or does not parse; the editor's own literal, so the stored value is one the editor already emits); `null` (the file was read and is not a KIVO build: cached as "looked, nothing", like `unitCount: null`, `progress.ts:45–46`); the key absent (the file could not be read: over the cap, launch path unmatched, storage error), which step 5 retries. Nothing stored at upload tells a KIVO build from a third-party one without the launch file (`packageIdentity` keeps a manifest id or the KIVO activity id, `validation/integrity.ts:85–96`, which any cmi5 or xAPI manifest supplies), so the KIVO test is the launch file's and only its. Existing rows are not rewritten; step 5 reads them when first needed. A real A.1 export has not yet been read by the extractor (the stamp reads were on real 2026.10.18 and 2026.10.20 exports and a simulated A.1 head): the pull request adds a trimmed head of a real A.1 export to the fixtures before merge (step 22).

5. **The lazy read: `ensureEngineVersion(svc, version, deps?)`** in `lib/courses/progress.ts`, modelled on `ensureUnitCount` (`:39–72`) as ADR 0016's PR 2 leaves it (its plan, T2 items 1 and 3, and §8.2 L10: the object's size checked with `storage.head(key)` (`lib/storage/types.ts:31`; `StorageHead.size`, `:58–59`) before the signed fetch; the cap `MAX_LAUNCH_READ_BYTES` exported from `lib/courses/units.ts` with the pure `launchBodyAllowed(size, cap)`; the read moved into a module-private `readLaunchHtmlFromStorage`; an injected reader `deps.readLaunchHtml` as the unit-test seam), returning `{ stamp: string | null; cached: boolean; error?: string }`: when `manifest_data.engineVersion` is a string or `null` it returns it with no read; when `manifest_data.engineVersionRead` records `too_large` under the current cap it returns `{ stamp: null, cached: true, error: "too_large" }` with no read; otherwise it reads the stored launch file (`storage_prefix` + `launch_url`, the key of `:52–55`) through PR 2's head check, cap and reader seam, applies step 4's four-state rule, and caches the parseable string, the literal `unknown` or `null` by `update course_versions set manifest_data = {...md, engineVersion}` (`:63–70`; `manifest_data` is not frozen on ready versions: the 0098 trigger covers `storage_prefix`, `launch_url` and `manifest_type` only, `0098_record_protection.sql:131–134`). **The reader's contract (lead's placement; the executor settles the shape in the PR text):** PR 2's reader answers `string | null`, and its `null` means "looked, nothing" for `unitCount`; the stamp has to tell four outcomes apart, so the reader `ensureEngineVersion` injects answers a discriminated result, `{ kind: "ok", html } | { kind: "no_object" } | { kind: "too_large", size } | { kind: "failed", error }`, either by widening `readLaunchHtmlFromStorage` (with `ensureUnitCount` mapping every non-`ok` kind to the null PR 2 gives it, so PR 2's behaviour is unchanged) or by a sibling reader beside it that shares the key, the head check and the cap. A widened reader takes the storage adapter from its caller: `ensureUnitCount` passes `getStorage()`, as under PR 2, and `ensureEngineVersion` passes `getStorageFor(version.storage_driver ?? null)` (see (iii)); the sibling reader needs no such change. **Explicit departures from `ensureUnitCount`**, which caches `null` on a storage error (`:60–67`), which ADR 0016 step 2 had to repair with `unitCountAlgo`, and which under PR 2 keeps a null head as "looked, nothing": (i) here a storage throw, a failed fetch or **a null head (no object at the key)** caches **nothing** and returns `{ stamp: null, cached: false, error }`, which the verdict reads as `unreadable` (the lead's Round 4: "a null head means unreadable and nothing is cached"; copied from `unitCount`, a cached `null` would read `non_kivo` and apply D-2 silently on what may be a new-engine version, the fail-open decision 2 forbids); only a successful read caches `unknown` or `null`. (ii) **The cap**: a head whose `size` fails `launchBodyAllowed(size, MAX_LAUNCH_READ_BYTES)` makes no signed fetch and caches `engineVersionRead: { too_large: true, cap: MAX_LAUNCH_READ_BYTES }` in `manifest_data` (a marker, never `engineVersion: null`), which the verdict reads as `unreadable`; a later cap change (a different `cap` value) retries, as ADR 0016's `unitCountAlgo` lets a later matcher recount; there is no second cap constant and no `content-length` check (the validator's module-private `MAX_LAUNCH_FILE_BYTES`, `validate-package.ts:114`, stays the validator's). (iii) **The driver** (the check's L11, the lead's Round 4): `VersionLite` (`:17–22`) gains `storage_driver?: string | null`, and both the head and the signed URL go through `getStorageFor(version.storage_driver ?? null)` (`lib/storage/index.ts:22`; the version's own driver, as every other stored-file reader does: `content-delivery.ts:171`, `direct-upload.ts:314`), not `getStorage()` (`:39`, the active driver, which `ensureUnitCount` keeps under PR 2; its plan records that asymmetry in §9 as outside PR 2's scope), so a version stored on Supabase before an R2 flip (`docs/CONTENT_STORAGE.md`) still reads instead of failing open on every candidate; `storage_driver` is the 0077 column (`content-delivery.ts:58`), on `main` with every migration through 0099 (`docs/ARCHITECTURE.md` §2), and the executor confirms at the rebase that both environments carry it, as the direct-upload reserve insert already requires (`direct-upload.ts:242`). When it is called: on cmi5/xAPI only on the guard branch (step 8: the row is `failed`, a candidate arrives, the key is absent); on SCORM on every commit on a `failed` row when the key is absent, because the freeze of step 9 needs the verdict for non-candidate commits too (the first such commit is tab A's own trailing exit commit seconds after the fail, so the read happens once and is cached). Both are rare; the read removes any order dependency and any owner-run re-scan: a version uploaded before the stamping ships is read the first time the guard needs it. The cmi5 embed already carries `id, manifest_data, launch_url, storage_prefix` (`process-statement.ts:56`) and gains `storage_driver`; the SCORM route's embed (`commit/route.ts:88`: `course_versions(manifest_data, manifest_type)`) gains `id, launch_url, storage_prefix, storage_driver` (members read versions, `0002_courses.sql:127–136`), and its service client (`:205–209`; `pr1a::229–233`) is hoisted above the guard branch for the `manifest_data` write. A lost update between `ensureUnitCount`, ADR 0016's `unitCountAlgo` write and this write (each writes `{...md, key}` from its own read) is possible and harmless: each key is recomputed from the stored bytes next time.

6. **Logs, and the on-row record of a fail-open, so nothing falls back silently** (decision 2). House pattern `console.warn(JSON.stringify({...}))`, ids only (`statements/route.ts:112–118`; ADR 0015's privacy row): `{ event: "pass_ignored", attempt_id, statement_id | null, runtime, engine_version }` when the guard holds a pass; `{ event: "result_ignored", …, verb: "failed" }` when it holds a later fail's score; `{ event: "pass_upgraded", attempt_id, statement_id | null, runtime, engine_version: <stamp | "unknown" | null>, reason: "older" | "non_kivo" | "unknown" | "unreadable", error? }` whenever a `failed` row becomes `passed` (D-2 applied), on both routes; `{ event: "engine_version_cached", version_id, engine_version }` when the lazy read writes the key or the `too_large` marker; `{ event: "engine_version_unreadable", version_id, error }` when it cannot; `{ event: "ignored_pass_unrecorded", attempt_id, reason }` when the record column is missing or its write failed (step 12); `{ event: "ignored_pass_reports_truncated", organization_id }` when the Reports read fills its ceiling (step 14). Who reads the log: nobody is named today, and whether `console.warn` lines reach the ops review (`.github/workflows/ops-review.yml`, `ops/RUNBOOK.md`) was not checked; this record names the ops review as the reader of these lines, and does not leave a fail-open to the log alone: when `pass_upgraded` fires with reason `unknown` or `unreadable`, the same update writes an `applied: true` entry with the reason into the row's `ignored_pass` record (step 12), which the attempt page shows under its neutral heading (step 15). The entry records that today's one-time upgrade was applied because the engine version could not be read, not that anything failed. `unknown` means strictly a KIVO build whose stamp is missing or does not parse (the owner's "a stamp that should exist"); `unreadable` means the stored launch file could not be read (a storage error, a failed fetch, no object at the key, or a file over the cap), so a stamp may exist and the guard could not decide. A non-KIVO package is `non_kivo`: today's rule working as designed, logged only and never recorded on the row, so third-party rows stay untouched; `older` is by design and logged only. One edge, stated: a read failure cannot tell a KIVO build from a third-party one, so on a third-party version whose launch file is over the cap or unreachable the `unreadable` entry lands too; the entry says why, the next successful read caches the version and settles it, and the attempt page's neutral heading never contradicts the Passed result above it.

### C. The guard

7. **Keyed on the row, never on stored statements** (decision 4). The guard reads `success_status` of the row the request is bound to. A statements-keyed guard would refuse a pass on an attempt with no recorded result, leaving the learner no result, no revision path and no request button (`courses/[courseId]/page.tsx:239–246`). Residuals, recorded: a sustained write outage after the AU `failed` leaves the row `in_progress` with `unknown`, so the next launch resumes the same registration and the guard does not fire; and the sub-second race of two sessions both reading `unknown` (`process-statement.ts:54–58, 194`; `:112` then keeps the pass). "One official attempt per enrolment" is what the guard protects, and on `main` the scoring window does not guarantee it: with `max_scored_attempts > 1` and basis `best` or `latest`, `computeScoring` picks the official attempt over the window (`lib/scoring/policy.ts:236–280`) and `classifyAttempt` treats every row in it as official (`attempt-kind.ts:72–75`), so a learner could fail row 1, launch row 2 without a grant and pass. ADR 0014 closes that with the 0103 clamp and `normalizePolicy`'s clamp, both in PR 1a; the guard therefore ships only after PR 1a and 0103 (step 21) and never reaches an environment without them.

## Consequences

- On a course exported with the released A.1 engine or later, a learner's first final result is their official result on every runtime Ambak serves: once Ambak has recorded Failed, nothing that session, another tab, a reload or a hand-made statement sends later moves the result, the status or the score, and no pass-keyed effect fires. The admin-approved retake stays the one path to another official attempt, exactly as the owner said; for older engines and third-party packages today's one-time upgrade continues, logged.
- The learner sees one result everywhere Ambak shows one: "Not passed" with the recorded score on the course page, the attempt page, the dashboard, the Report Card and the CRM's `learner-summary` and `progress` feeds (the check's L3: `learner-summary` is the CRM pull endpoint, not the tenant LRS), with the course-page notice saying why a session may have shown "Passed". What Ambak cannot change under A.1 is that session's own screen (its "Passed!", celebration, badge or certificate image), because Ambak answers after the engine has drawn it; the next engine release's pre-claim read closes that on cmi5, and the plain-xAPI and SCORM screens follow the KIVO lead's answers.
- Admins see every ignored pass in the Attention Center ("Passed result not applied", one item per attempt, linking to the attempt page) when the center and the type are on, and always in the Reports section "Passed results not applied" with a CSV that carries the attempt id; the attempt page shows the full record and the remedy paths; a D-2 upgrade applied because the engine version could not be read shows under "Result notes" and raises nothing.
- ADR 0015's second `course_completed` arises, after this record, only for packages from engines before A.1 and for third-party content (and never for A.1 plain xAPI or A.1 SCORM, where it could arise before); its rule is unchanged. The tenant-LRS feed carries `content/engine-version` for KIVO packages from this build, and marks every statement the guard did not apply; `raw`-profile consumers are told the rule instead.
- A SCORM revisit of a new-engine course after a fail shows the failing session's result and answers (the freeze), not the second session's; a cmi5 revisit already shows the recorded result under ADR 0014.
- One small migration (0104), owner-applied, staging first; the code works before it and the record fills from the apply on. One new column, no new relation, no RLS or policy change, grants restated.
- Nothing on the record changes by itself; another official attempt comes only through the existing request, ticket and bulk-grant paths (ADR 0014 step 11).

## Alternatives considered

- **Refusing the POST (4xx) instead of storing and holding:** does not change the engine's screen, would refuse the KE-8 pair's array on a retry, and loses the audit copy; rejected.
- **Expiring the attempt's other launch tokens at the fail:** tab B's pass would answer 401 and never be seen, its `terminated` refused; the lost-save case (N18) and the plain-xAPI reload (same URL token) are not covered; rejected.
- **Writing the fail into the engine's outcome document:** the document is AU-private and never re-read by a second session already running; rejected.
- **A statements-keyed guard (refuse any pass once a `failed` statement is stored):** refuses a pass on an attempt with no recorded result (the insert-error case) and leaves the learner no result, no revision path and no request button; rejected for the row-keyed guard (step 7).
- **A `cmi_data` key for the record (the first proposal):** replaced wholesale by every SCORM commit, dropped by a concurrent cmi5 sub-activity write, and the shape ADR 0014's Alternatives rejected for the revision marker; rejected for the column (step 11).
- **A new outcome-events table or `platform_audit_log`:** a new relation (RLS, policy, grants, a reader) for one record per rare event that belongs to the attempt; rejected.
- **One live session per attempt:** would not reach the plain-xAPI reload (same token) and would hold a pending claim from the older tab for a registration that is never relaunched; rejected.
- **Computing "not applied" at page load from the statements:** no record for SCORM (no statements), no durable admin surface, a per-render cost on every attempt page; rejected.
- **Where the stamp lives:** `manifest_data.engineVersion` (chosen: the key the LRS context already reads, no migration); a new `course_versions` column (a migration for one key); 0100's `course_versions.engine_version`, which is written only by `alds_set_version_tier` from the ALDS manifest (`0100_alds_core.sql:191, 229–230`), absent for SCORM and pre-2.0 packages, and the Guardian's, so never the guard's.
- **The narrow SCORM hold (3b narrow):** holds `cmi_data` only on the commit carrying the ignored pass; the row's saved data then becomes the second session's bookmark with `outcomeFinal = passed`, and every SCORM revisit shows "Passed" (step 9); the owner chose broad.
- **Telling the LRS consumer the rule instead of marking (12 (b) alone):** every consumer implements a rule and reads a version string, and a `raw` consumer has no `content/engine-version` at all; the owner chose (a) with (b)'s sentence.
- **A separate production floor, or a floor read from the live editor at run time** (the lead's addition; not in the proposal): the floor is a fact about a released engine, not an environment; a run-time read would make grading depend on an external site; rejected for the pinned constant.
- **Scoping the guard to cmi5 only (the first proposal's decision 3):** rested on K0010's export-format note, not on what Ambak runs; Ambak parses every `imsmanifest.xml` as SCORM 1.2 and nothing enforces "KIVO courses go to Ambak as cmi5"; the owner's "never" would then depend on the export format; rejected (step 2).
