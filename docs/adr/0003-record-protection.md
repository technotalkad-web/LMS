# 0003. Record protection: backups, write-once versions, delete guard, statements never overwritten

Status: Accepted (owner, 2026-10-16)
Acceptance: accepted by the owner on 2026-10-16 after two checks (the migration numbering against the database history, step 7a below; the per-attempt learner impact, ADR 0004 §5), on two conditions that bind ADR 0002–0007: (a) no learner attempt is restarted or abandoned until the owner gives an explicit go after seeing the per-attempt impact list; (b) production migration state is confirmed in the P1 read-only audit (ADR 0007 step 2) before any production apply. All steps are accepted as written except step 7 and decision 2, where the acceptance corrected the committed filename of the 0032 hotfix to its original name `0032_course_versions_unique_per_package.sql` and added the verified numbering facts (step 7a). The owner's answers to the decisions requested below are recorded in that section.
Date: 2026-10-15
Deciders: owner; architect (Fable 5.1)

## Context

- **Backups.** `.github/workflows/backup.yml` dumps the production database nightly to Backblaze B2 and overwrites a `latest/` pointer every night; `pg_dump` does not include Storage objects. `.github/workflows/content-backup.yml` runs `rclone sync` from the R2 bucket, which is unused because `STORAGE_DRIVER = "supabase"` on both environments (`wrangler.toml`), and fails every night on a B2 path collision. Production course packages therefore have no scheduled backup. Staging already lost two original packages by overwrite with no copy. A one-off snapshot script exists on branch `ops/storage-snapshot` (`scripts/backup-storage-snapshot.mjs`: read-only against Supabase, writes `storage-snapshots/<env>/<stamp>/` to B2 and a local copy with a per-object sha256 manifest, never deletes).
- **Statements.** `app/api/xapi/statements/route.ts` assigns `randomUUID()` to id-less statements (line 53), then fills a missing `timestamp` (line 54), then `upsert`s on `(attempt_id, statement_id)` without `ignoreDuplicates`, so a resent id with different content replaces the stored `raw`. The KIVO engine never sets statement ids and re-POSTs the same queued object after a 5xx, which produced 7 duplicate rows on staging that no id-based dedupe can catch. The engine does stamp `timestamp` on every statement before the first send (engine 2026.10.05.2, lines 10989 and 11645) and re-queues the same object, so the content timestamp is present and identical across retries.
- **Versions.** `course_versions.storage_prefix` has no unique index (the step-0 incident: three versions carried another course's folder). Migration 0002 declares `unique (course_id, version_number)`; on staging that constraint is absent because an out-of-repo hotfix (a hand-applied copy of `supabase/migrations/0032_course_versions_unique_per_package.sql` from the unmerged branch `fix/158-versions-unique-per-package`, commit 5ce6264 of 2026-06-04, byte-identical to the branch file; the repository's sequence on `main` skips 0032) dropped it and added `course_versions_package_id_version_number_key unique (package_id, version_number)`. The branch was never merged, so a migration-replay restore would reintroduce the per-course constraint and fail on the 9 duplicate `(course_id, version_number)` pairs that per-package numbering (0030) has produced since. Whether production received the hotfix is unknown until the P1 audit. `lib/storage/supabase.ts` uploads with `upsert: true` (server, signed URL and `x-upsert` header); the browser direct-upload path relies on that to retry a PUT. On the multipart path (`lib/courses/upload.ts`) the files are written before the version row exists (`nextVersionNumber` read, then upload, then `insertVersionRow` with `upload_status = 'ready'`), so two concurrent uploads to one package compute the same prefix and the second overwrites the first's objects before any row constraint can refuse it.
- **Deletes.** `organizations → courses → course_versions → course_attempts → xapi_statements` cascade (0002, 0004). `app/api/courses/[courseId]/route.ts` DELETE is an unguarded RLS delete with no UI caller; the package DELETE route already answers 409 "Deactivate instead" when attempts exist. The CI purge (`tests/e2e/helpers/supabase.ts purgeAllTestData`, run by pr-checks on every non-main push, by nightly-e2e and by the bot suites) deletes `qa-*` organisations by cascade through the service client; `scripts/demo/seed-demo.mjs` and two specs delete by cascade too. Inside a `security definer` function `current_user` is the function owner, and FK cascade actions run as the owner of the referencing table, so a guard keyed on `current_user` would refuse every one of those paths.
- **DR.** `ops/RUNBOOK.md` §8 defines restore as "project → migrations replay → tag deploy". Production is Supabase free tier with no PITR.

## Decision

### 1. Content backups (owner-run; Claude prepares the commands, no secrets in the repository)

1. One-off snapshot of each environment's Supabase Storage `course-content` bucket with `scripts/backup-storage-snapshot.mjs` (branch `ops/storage-snapshot`, to be merged): copy only, never delete, under `storage-snapshots/<env>/<stamp>/`, plus the local copy and `manifest.ndjson` (path, size, sha256). The owner runs it once with production credentials and once with staging credentials, from an env file outside the repository. If a snapshot has already been written to the shared dump bucket it stays there as the first copy.
2. `content-backup.yml` is changed to copy from the Supabase Storage source of production (its S3-compatible endpoint) with `rclone copy --immutable` (never `sync`) to `content/prod/supabase/course-content/` in the dedicated bucket of step 3. New GitHub secrets, named by the executor along the lines of `SUPABASE_S3_ENDPOINT`, `SUPABASE_S3_ACCESS_KEY_ID`, `SUPABASE_S3_SECRET_ACCESS_KEY`, `B2_CONTENT_BUCKET`; owner action: generate an S3 access key in the production project's Storage settings. The R2 source returns only when `STORAGE_DRIVER` flips to `r2` (`docs/CONTENT_STORAGE.md` step 7).
3. D7: a dedicated B2 bucket for content copies, created with Object Lock enabled (B2 allows it only at creation) and a default retention the owner chooses (at least 30 days). Nightly copies and future snapshots go there, never to the dump bucket: `backup.yml` overwrites `latest/` every night, which a locked bucket would refuse.
4. Restore drill (owner, half a day; moved from P0 into the P1 rehearsal of ADR 0007 step 3): restore last night's `pg_dump` into a scratch Supabase project (not a migration replay), then hash-compare one version prefix between the B2 copy and the live bucket using the snapshot manifest (path, size, sha256). `ops/RUNBOOK.md` §8 is amended by the executor to "project → restore pg_dump → tag deploy".

### 2. Statements are write-once

5. `app/api/xapi/statements/route.ts`: the upsert becomes `.upsert(row, { onConflict: "attempt_id,statement_id", ignoreDuplicates: true }).select("statement_id")` (ON CONFLICT DO NOTHING). If a row comes back, processing continues as today. If none comes back (the id already existed): read the stored `raw` and compare it with the incoming statement as received, before the route fills `timestamp` (the stored copy carries the LMS-filled value, so the comparison ignores fields the LMS filled); if they are equal (an exact retry) run `processStatement` again, which must be idempotent for a retry (conditional attempt update; the webhook, XP and journey calls are already batch-level and dedupe-keyed); if it differs, skip `processStatement` and leave that statement out of the `mirrorToExternalLrs` list, and log `statement_conflict` with attempt id and statement id. The response still lists the id with 200. A resent id never changes the stored `raw`.
6. Id-less statements get a deterministic id instead of `randomUUID()`, computed before the route fills a missing `timestamp`: `uuid5(name, ALDS_NS)` through the namespace argument of `lib/lrs/uuid5.ts` (the default `LMS_STATEMENT_NAMESPACE` is not used), with `ALDS_NS = 6b2c1f6e-9c2e-5c3a-8f0b-3c1a6d1e2a10` and `name = [attempt_id, verb.id, object.id, timestamp as sent by content or "", JSON.stringify(result ?? null), JSON.stringify(context?.extensions?.["https://ambak.com/xapi/ext/question/try"] ?? null)].join("|")` (BLUEPRINT §5.3). The extension IRI lives as a constant next to `uuid5.ts` until `lib/alds` exists (P3 moves it). Because the engine stamps `timestamp` before the first send and re-queues the same object, an exact retry collapses to one row and statements from separate launches never collapse. Engine-minted ids arrive with KIVO release A (ADR 0006); the G4 equivalence/409 behaviour of the blueprint is deferred to P6.

### 3. Migrations: commit `0032`, add `0098_record_protection.sql` (SQL intent per ADR 0001 decision 5)

7. The hotfix is committed under its original name, `supabase/migrations/0032_course_versions_unique_per_package.sql` (the file on the unmerged branch `fix/158-versions-unique-per-package`, commit 5ce6264, byte-identical to the hand-applied copy; as written there it is a plain `add constraint` and not idempotent), made idempotent: `drop constraint if exists course_versions_course_id_version_number_key`, then `add constraint course_versions_package_id_version_number_key unique (package_id, version_number)` only when `pg_constraint` has no constraint of that name on `public.course_versions`. It records what staging already has; on production it is applied in the P1 sitting (ADR 0007 step 5) and is a no-op if the hotfix was already applied there.
7a. Numbering verified on 2026-10-16 (acceptance check 1): `origin/main` holds 96 migration files numbered 0001–0097 with the single gap at 0032 and no duplicate numbers; of 178 local and remote branches, none carries a migration numbered 0098 or higher, the only 0032 is the branch above, and no branch reuses a `main` number with a different file; the other hand-applied files kept outside the repository (0030, 0033, 0034, 0035) are byte-identical to the repository migrations of the same number, so there is no other hidden hotfix. Staging holds the objects of 0093, 0096 (`content_scopes`) and 0097 (`organizations.enforce_content_mapping`, `manager_coverage`) and none of the planned 0098/0099 objects (`course_versions.conformance_level`, `course_attempts.is_preview`, `learning_sessions` and `package_certifications` are all absent); it has 9 duplicate `(course_id, version_number)` pairs and 0 duplicate `(package_id, version_number)` pairs, consistent with the hotfix applied. Production cannot be read from the development machine and is believed to be at 0071; its constraint state and migration objects are confirmed in the P1 read-only audit (ADR 0007 step 2) before anything is applied there (acceptance condition b).
8. `0098_record_protection.sql` (the single P0 migration; also carries the DDL of ADR 0004, item 11 below) starts with `create unique index if not exists course_versions_storage_prefix_key on public.course_versions (storage_prefix);`. Precondition: the gate SQL `select storage_prefix, count(*) from public.course_versions group by 1 having count(*) > 1` returns 0 rows (true on staging; production is checked in the P1 audit and repointed by the owner before apply, using the procedure of ADR 0007 step 3). It then repeats the two statements of 0032 under the same guards, so a replay from 0098 alone is correct; no second unique structure under a new name, no partial predicate (`package_id` is NOT NULL since 0030). `lib/courses/upload.ts insertVersionRow` and `lib/courses/direct-upload.ts initDirectUpload` map SQLSTATE 23505 to 409 "another upload to this language is in progress".
8a. Multipart uploads reserve the version first: `lib/courses/upload.ts uploadCoursePackage` inserts the row with `upload_status = 'uploading'` before any byte is written (the unique constraints make a second concurrent upload fail with 23505 before it can overwrite anything), uploads the files, then updates the row to `ready`. On error it deletes the `uploading` row and its prefix; `sweepAbandonedUploads` (`lib/courses/direct-upload.ts`, run by `/api/cron/reaper`) covers crashes. The content route already refuses to serve an `uploading` version.
9. Write-once at version level: a `before update` trigger on `course_versions` raises `course_version_frozen` when `old.upload_status = 'ready'` and any of `storage_prefix`, `launch_url`, `manifest_type` would change. The transition `uploading → ready` may still set them; `storage_driver` is not frozen (the R2 copy script flips it after verification). Object-level upsert in `lib/storage/supabase.ts` stays for in-flight `uploading` prefixes.
10. Delete guard: `before delete` triggers on `public.courses` and `public.course_versions` raise `learner_history_exists` when learner attempts exist on the version (or on any version of the course). Exemption: the PostgREST role claim, `auth.role() = 'service_role'` (the raw form, if written out, is `coalesce(nullif(current_setting('request.jwt.claims', true), '')::jsonb ->> 'role', '') = 'service_role'`; the `nullif` matters because the cast throws on an empty setting). The claim is transaction-local and survives both `security definer` execution and FK cascades, so it covers the CI purge cascade, `seed-demo.mjs`, the two cascading specs and the `uploading`-row sweeper with no call-site changes; `current_user` is never used for this check. Direct SQL-editor deletes carry no claim and are refused, which is intended. "Learner attempt" until migration 0099 exists: any `course_attempts` row on the version except those whose user currently holds `super_owner`, `admin` or `data_analyst` in the attempt's organisation (`not exists` a staff membership); a missing membership counts as a learner, so former members' history still blocks. After 0099 the functions are replaced to use `is_preview = false` (ADR 0005 step 10). The trigger functions are `security definer` (stated explicitly: the guard must read attempts across RLS), `set search_path = pg_catalog, public`, with `revoke execute … from public, anon, authenticated` and `grant execute … to service_role`, per the BLUEPRINT Conventions paragraph; grants per `docs/MIGRATIONS.md`.
11. ADR 0004 DDL in the same file: `alter table public.package_validations drop constraint if exists package_validations_verdict_check;` then `add constraint package_validations_verdict_check check (verdict in ('pass','warning','fail','unplayable','blocked'))`; `add column if not exists override_reason text`, `overridden_by uuid references auth.users(id) on delete set null`, `overridden_at timestamptz`. The file is idempotent, wrapped in one `begin; … commit;`, ends with `notify pgrst, 'reload schema'`, creates no new table (no new table grants), and passes `scripts/check-migration-grants.mjs`.

### 4. Routes

12. `app/api/courses/[courseId]/route.ts` DELETE counts learner attempts first (same definition as step 10) and returns 409 with the package route's wording ("Cannot delete: N learner attempts exist … Deactivate instead"). No Library UI change: no UI calls this route today.

### 5. Tests and CI

13. New lifecycle spec `tests/bot/lifecycle/50-record-guard.spec.ts` (the blueprint's §9 numbers 50–56 are superseded, `docs/ARCHITECTURE.md` §5): course DELETE with learner attempts → 409; delete of a `course_versions` row with learner attempts through an admin session → `learner_history_exists`; an attempt by a user since removed from the organisation still blocks; update of `storage_prefix` on a `ready` version → `course_version_frozen`; a `qa-*` organisation with learner attempts deleted through the service client by cascade succeeds (the purge path); two concurrent multipart uploads to one package → one 409, and the first version's launch file hash is unchanged.
14. New lifecycle spec `51-no-overwrite.spec.ts`: POST a statement id twice with different bodies → 200 both times, stored `raw` unchanged, `statement_conflict` logged; an id-less identical statement POSTed twice → one row, no second webhook or XP event; two id-less statements with different content timestamps → two rows. Unit test `tests/unit/statement-id.test.ts` for the deterministic-id function (fixed vectors).
15. Existing specs 47, 48, 49 and 32 stay green. `package.json` gains a `test:unit` script that runs every `tests/unit/*.test.ts` file as its own `tsx` process and fails on the first failure (a small node runner, `scripts/run-unit-tests.mjs`, so it works in CI and in Git Bash alike; `tsx` takes one entry script, so a glob on one command line would run only the first file) with `tsx` added as a pinned devDependency, and a `unit` job in `.github/workflows/pr-checks.yml` runs `npm run test:unit` on every push and PR, so these and the P3 golden fixtures run in CI.

### Risks and protections

| Risk | Protection |
|---|---|
| Learners: none; no learner-facing behaviour changes | — |
| Grading: an exact retry re-runs `processStatement` | it is idempotent for a retry; spec 51 proves no second webhook, XP or journey credit |
| Privacy: the scratch project used for the restore drill holds production PII | the owner deletes the scratch project after the drill; dumps are never committed |
| Existing records: the unique index fails to apply where duplicates exist | gate SQL in the pre-apply audit; repoint before apply, as done on staging |
| CI purge breaks on the delete guard | exemption on the service_role JWT claim; spec 50 (step 13) proves the purge path |
| Reserve-first leaves `uploading` rows after a crash | `sweepAbandonedUploads` through the reaper cron; such rows are never served |

## Consequences

- Admins can no longer delete a course or version that learners have used; they deactivate the package or make another version current. Versions with only staff attempts remain deletable under the definition in step 10.
- A `ready` version's folder, launch file and type are fixed forever; correction is a new version plus "Make current".
- The browser upload retry keeps working (object upsert stays); the version row, not the object, is the unit of immutability, and the multipart path can no longer overwrite a sibling upload's objects.
- The nightly content backup starts succeeding and protects the bucket that production uses. B2 storage cost rises by the package estate (small: the largest staging version is about 5 MB).
- Once 0032 is committed and 0098 applied, the canonical migrations and the live schema agree on `course_versions` constraints on both environments.

## Alternatives considered

- Object-level no-overwrite (`If-None-Match` or removing `x-upsert`): breaks the browser PUT retry and prefix reuse after an aborted upload; Supabase signed URLs cannot express it.
- A session GUC plus a `purge_organization(p_org_id)` security-definer RPC as the guard bypass: gives an explicit audit trail but changes `purgeAllTestData`, `seed-demo.mjs` and two specs; kept as the fallback if the service-role exemption proves too broad.
- Exemption keyed on `current_user = 'service_role'`: never matches inside a security-definer function or an FK cascade (the function or table owner), so it would refuse the CI purge.
- Enforce the delete refusal only in API routes, no trigger: leaves cascades from `organizations` and direct PostgREST deletes unguarded.
- `rclone sync` for the nightly copy: deletes from the backup whatever disappears from the source, which is exactly the loss being insured against.
- Restore by migration replay: reintroduces the dropped `(course_id, version_number)` constraint and fails on the 9 duplicate pairs.

1. D7: a dedicated B2 content bucket with Object Lock and a retention period of at least 30 days (step 3). Recommended: yes. Decided (owner, 2026-10-16): yes; the exact retention period (at least 30 days) is set by the owner when creating the bucket.
2. Migration numbering: the hotfix is committed as `0032_course_versions_unique_per_package.sql` (its original name on branch `fix/158-versions-unique-per-package`); the P0 migration is `0098_record_protection.sql`; the P4 "alds core" migration becomes `0099_alds_core.sql`; the blueprint's `0099_alds_guardian.sql` is split: `guardian_findings` and `guardian_runs` move into the P5 migrations (`0100`/`0101`, ADR 0005 step 13), `scorm_commit_log` and `scorm_interaction_events` are cut (ADR 0002 decision 4), `guardian_quarantine`, `guardian_events` and `guardian_proposals` are deferred to P6. All ADRs use this numbering. Recommended: yes. Decided (owner, 2026-10-16): yes, after the numbering was verified against the database history (step 7a); the owner's condition that production state is confirmed in the P1 audit before any production apply stands.
3. Definition of a learner attempt for the delete guard before `is_preview` exists: every attempt blocks deletion unless its user currently holds `super_owner`, `admin` or `data_analyst` in that organisation; attempts by former members always block (step 10; matches the blueprint's 0098 step 6d preview rule, inverted so that absence of a membership protects rather than exposes). Recommended: yes. Decided (owner, 2026-10-16): yes.
4. Confirm the service-role exemption through the JWT role claim as the guard bypass (instead of a GUC plus purge RPC). Recommended: yes. Decided (owner, 2026-10-16): yes.
