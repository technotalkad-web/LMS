## Context

### Sources and the owner's words

- The owner's answer of 2026-11-11, with the staging facts, recorded verbatim outside this repository. The requirement, in the owner's words:

  > A Learning Path is a separate learning product, not simply a collection of individual courses.
  >
  > If a learner has already completed a course individually through the Library, that completion must NOT count towards the same course when it is included in a Learning Path. The learner must complete it again within the Learning Path.
  >
  > Therefore, Individual Course Progress and Learning Path Progress must be tracked independently, even when both use the same course content.
  >
  > The one-official-attempt rule should also be maintained separately for each learning context.
  >
  > Most importantly, the Continue button, chapter lock/unlock logic, Learning Path progress, dashboards and reports must all follow the same path-specific completion rule.
  >
  > Once a learner completes the official attempt launched from the Learning Path, the next chapter should unlock permanently and remain accessible when they return to the Learning Path.

### Words

Context = where a learner's attempt belongs: the **individual course context** (`course_attempts.learning_path_id is null`: the Library, a direct assignment, a CRM deep link, a journey launch) or **one Learning Path's context** (`learning_path_id = <that path>`). Official attempt, revision visit, granted retake: ADR 0014's terms, now read per context. Done, stored: ADR 0019's words (`officialDone`, `officialResultStored`), now per context. Reader = any code that answers "done", "official", "in progress" or "revision" for a learner on a course. Step = a `learning_path_courses` row.

### What the code does today: three readers, three rules

Attempt rows already carry their context: the launch page inserts `learning_path_id: pathContextId` (`app/[org]/(learner)/courses/[courseId]/launch/page.tsx:1009`, `:1041`), `consume_grant` inserts it (`0103_revision_visits.sql:889-895`, `p_learning_path_id` at `:727`), and `pathContextId` is trusted only when `?lp=` names a path the learner is assigned to (or `org_public`) that holds this course as a step (`:815-816`). Migration 0034 added the column for reports ("so its reporting can be sliced separately from standalone attempts", `0034:16-28`). But the readers disagree about what the context means:

1. **The path page** (`app/[org]/(learner)/paths/[pathId]/page.tsx`): product decision L2 (`:195-198`). It reads every attempt of the learner on the steps' versions (`:221-232`), keeps the path-context rows (`:234`, `a.learning_path_id === pathId`), and calls a step done when `officialDone(computeScoring(pathRows, policy, grants), passRequired)` (`:263-281`). Its grants (`fetchGrantRetakeIds`, `:251`) and the score shown per step (`:252-258`, "uses ALL the learner's attempts (matches the course page and CRM feeds)") are course-level. A step is "in progress" on an open path-context row that is neither abandoned nor a revision visit's (`:278`).
2. **The launch page's strict lock** (`launch/page.tsx:587-591`, `:669-747`): for every earlier step of a strict path it reads the learner's attempts on those courses (`:719-725`, columns `course_version_id, completion_status, success_status` only) and counts a course done when any row has `completion_status = 'completed' or success_status = 'passed'` (`:734-739`), **in any context**, abandoned rows, staff previews and legacy completed revision rows included, with no `pass_required`; else `redirect(/{org}/dashboard?locked=)` (`:743`). 3. **Continue, `continueReady` and the status route**: the continue address (`app/[org]/(learner)/continue/page.tsx:101-157`) reads the course's versions, the learner's approved grants on the course (`:110-122`, no context), every attempt on those versions (`:138-147`, no context) and concludes on `officialResultStored(scoring, attempts, passRequired)` (`:151`); the launch page's first Continue state does the same over `ev.my`, the course-level evaluation (`:1235-1238`); the status route (`app/api/attempts/[attemptId]/result-stored/route.ts:85-125`) likewise. ADR 0019's "Words" defines "official result stored" over the learner's attempts on the course: course-level.

Two more readers take a fourth and a fifth reading: the dashboard's path tiles count a step done only when the **course-level** official attempt both satisfies `officialDone` and carries the path's id (`dashboard/page.tsx:556-585`), and the SCORM commit route's "path finished" notice uses the raw `completed || passed` rule over path-context rows (`app/api/scorm/[attemptId]/commit/route.ts:562-600`).

**The launch decision is course-level.** `evaluate()` (`launch/page.tsx:305-354`) reads the learner's attempts on every version of the course (`:329-338`), runs `computeScoring` over all of them (`:341`) and derives the candidate kind (`candidateKind`, `lib/attempts/launch-kind.ts:27-38`): `first` while `!limitReached`, else `grant` or `at_row`, and at the row `insert_revision` when no row exists (`:61-80`). `limitReached` is true as soon as one official attempt exists in any context (ADR 0014 rule A: "Every later launch without a consumed grant is a revision visit"). `pathContextId` is computed after that evaluation (`:815`), so the context cannot enter it today. The in-progress row lookup (`:818-`), the flagged-row close before a `first` launch (`:970-986`), the 23505 re-read (`:1059-1066`), slot routing's in-progress set and the language-preference route (`app/api/courses/[courseId]/language-preference/route.ts:131-147`, `:154-173`) are all keyed on (user, version) or (user, course). `consume_grant` (`0103:721-900`) matches the grant by (id, user, course) only, tests `retake_live` on any version of the course (`:780-800`), computes the chain (`stale`, `stands`) over the course (`:802-840`) and abandons every in-progress row of the learner on the course (`:875-888`); `attempt_requests` has no context column (`0083:18-35`) and its one-open index is `(user_id, course_id)` (`0083:45-47`); `revision_visits` has none either (`0103:309-318`). ### The staging case (ids only)

The learner's Chapter 3 attempt `9ea94d90` was started on 2026-11-06 outside the path (`learning_path_id null`, `is_preview true`) and finished on 2026-11-11 11:20 UTC. It is the course-level official attempt of Chapter 3: `is_preview` is never read by scoring (ADR 0005 D1; `lib/alds/launch.ts:20`), so a preview row that derives a completion is official like any other. The later launch of Chapter 3 from the path was therefore a revision visit (row `5da0100a`, `is_revision true`, path context): `limitReached` was true, `candidateKind` answered `at_row`, `rowAction` answered `insert_revision`. Continue (course-level `officialResultStored` true) and the strict lock (a completed row exists) sent the learner into Chapter 4 with `?lp=`, which opened a path-context attempt on Chapter 4. Back on the path page, L2 found no path-context official attempt on Chapter 3: Chapter 3 "not done", so the first incomplete step is Chapter 3 and every later step, Chapter 4 included, reads locked, although a Chapter 4 row exists.

### Why ADR 0014's course-level official attempt makes L2 a dead end

Under ADR 0014 rule A the official attempt is per (learner, course). Once it exists in any context, every launch without a consumed grant is a revision visit, and a revision visit's row never derives completion (rule R-5, `lib/xapi/process-statement.ts`; `0103` `flag_revision_attempt`). L2 asks the path page to find a *path-context official attempt*. For a learner whose official attempt was taken outside the path there can never be one: no path launch can be official, and the only path to a new official attempt, `consume_grant`, is scoped to the course too (`stands` would even expire the grant when the individual result passed). So the step is stuck for good, while Continue and the lock, both course-level, keep letting the learner through. The three readers cannot be reconciled by picking one of today's rules: course-level everywhere is the "any finished attempt" option the owner declined; L2 everywhere is the owner's rule, and it needs the official attempt itself to be per context.

## Decision

Goal: the owner's requirement, built once: the official attempt, revision visits and grants are kept per learning context; one function decides "done", "official", "in progress" and "revision" for a (learner, course, context), and every reader calls it; a step unlocks permanently once the learner's official attempt launched from the path completes it under `pass_required`. Out of scope: KIVO K4, LMS L6 and L2 of the Guardian track (untouched); SCORM 2004; a new learner-facing "contexts" page; the CRM feed's shape beyond decision (b); any backfill or rewrite of a learner row.

### A. The rule

1. **A learning context is the value of `course_attempts.learning_path_id`.** Null is the individual course context (Library, direct assignment, journey, CRM deep link); each Learning Path is its own context. The same course in two paths is two contexts (decision (a)). Journeys are not a context: a journey launch has `learning_path_id null` and reads the individual context (decision (a)); a path-context completion never credits a journey day (step 6).
2. **ADR 0014's rule A holds per context.** In each context a learner has one official attempt (the first completed non-revision, non-abandoned row *of that context*), then review-only revision visits *of that context*, and another official attempt only by a grant *issued for that context*. A completion in one context is not a completion, a revision or a grant trigger in another. Nothing in this record deletes, rewrites or backfills a learner row.
3. **One function for every reader.** `lib/scoring/context.ts` (pure; no `next/*`, `lib/alds/*` or Supabase runtime import; the `lib/attempts/launch-kind.ts` shape):
   - `type LearningContext = { kind: "individual" } | { kind: "path"; pathId: string }`; `INDIVIDUAL`; `contextOf(row)` (from `learning_path_id`); `contextKey(ctx)` (`"individual"` or `path:<id>`); `sameContext(row, ctx)` (`row.learning_path_id` is not distinct from the context); `inContext(rows, ctx)`; `grantsInContext(grantRows, ctx)` (rows whose `learning_path_id` is not distinct from the context; a grant row without the column, read on a database before 0107, is individual).
   - **`contextResult(i)`**, the shared function: input `{ attempts, grantRows, policy, passRequired, context }` where `attempts` are `ScorableAttempt & { learning_path_id: string | null; is_preview?: boolean | null }` rows of one learner on one course (any context; the function filters) and `grantRows` the learner's approved `attempt_requests` rows on the course. Output `{ context, attempts /* in-context rows */, retakeIds, scoring: ScoringResult, status: CourseStatus, stored: boolean, done: boolean, liveRetake: boolean }`, computed as `rows = inContext(attempts, ctx)` (minus preview rows under decision (g)), `retakeIds = grantsInContext(...)` with `used_attempt_id` set, `scoring = computeScoring(rows, policy, retakeIds)`, `status = courseStatus(scoring, rows)`, `stored = officialResultStored(scoring, rows, passRequired)`, `done = officialDone(scoring, passRequired)`, `liveRetake = hasLiveGrantedRetake(rows, retakeIds)`. A row whose `learning_path_id` key is absent (a select that did not name the column) throws: a reader cannot be context-blind by accident.
   - `readContextResult(client, { userId, courseId, context })` in `lib/scoring/context-read.ts` (server only): the continue page's strict reads (`continue/page.tsx:93-147`: `courses.pass_required` `maybeSingle`, `course_versions` ids, approved `attempt_requests` of the learner on the course with `learning_path_id` through the narrower-select fallback, the attempts with `is_revision`, `learning_path_id` and, under (g), `is_preview` through the same fallback), every `{ data, error }` checked, answering `{ ok: false, reason }` on any error, else `contextResult`. Single-pair readers (the launch page, the continue page, the status route, the course page, the attempt-request routes, `force-restart.ts`) call it; batch readers (the dashboard, the path page, the CRM feeds, `insights.ts`, `status.ts`, the admin pages) group their rows by `${user}:${course}:${contextKey}` and call `contextResult`.
   - `computeScoring` is then called by `contextResult` only. `tests/unit/revision-listing.test.ts` (the guard that lists every `computeScoring` caller) is turned around in the form its own `PENDING_1B` list took (`:263-267`): pull request A ships the rule "outside `lib/scoring/context.ts` no file calls `computeScoring` directly" together with a dated allow-list `PENDING_0023` naming every direct caller at `main` (twenty files besides the definition in `lib/scoring/policy.ts`: the launch, continue, course, courses, dashboard and path pages; the status route; the three attempt-request routes and the admin queue; `lib/attempts/grant.ts`, `force-restart.ts`; `lib/scoring/attempt-kind.ts`, `status.ts`; `lib/manager/insights.ts`; `lib/integrations/progress.ts`, the `learner-summary` route; `analytics/page.tsx`; `library/[courseId]/learners/page.tsx`), each with the PR letter that removes it; pull requests B, C and D remove their files; pull request E asserts the list is `[]`. Fold of review finding C2-2: the rule alone would fail PR A's unit job.
   Verified by: `tests/unit/learning-context.test.ts` (step 12).

## Consequences

- One rule, stated once: a learner's result on a course is a result *in a context*; the individual course and each Learning Path are separate products, as the owner asked; the three readers of the Context cannot drift again because they call one function.
- ADR 0014's one-official-attempt rule, revision visits and grants hold per context; its content is unchanged. ADR 0019's Continue follows the path context, its `pass_required` follow-up is closed in the lock, and its `failed=1` banner leads to a request in the path context. ADR 0020's view gains a context column and the course matviews read the context of enrolment (decision (d)). Journeys read the individual context (decision (a)).
- A learner who completed a course in the Library completes it again inside a path; the course page tells them so (decision (f)). A learner who completed it only inside a path sees Not started on the course page.
- Reports, the Report Card and the leaderboard metrics move on the first refresh after the paste, in the directions A7 lists.
- The CRM feeds' course rows keep their shape and report the course taken on its own, so a learner who finished a course only inside a path reads `not_started` there; the path objects count path-context steps (decision (b)); the webhook fires for the individual context only (decision (c)); the five-line addendum tells the consumer all three.
- XP, the pass marker and the score bonuses pay once per course, but each context's first official attempt is scored in its own right (`gamification_record_activity_core`, decision (e)); the leaderboard average takes each context's official score.
- The Learning Paths index, the path Learners page and CSV, the path Reports page, Admin Analytics' completed and overdue counts, the reminders cron and the LRS path statements all read the path's own attempts; none of them any longer counts a Library completion toward a path.
- A Learning Path with learner attempts can no longer be deleted; it is deactivated.
- Binding on later work: a new reader of "done", "official", "in progress" or "revision" calls `contextResult` or `readContextResult`, never `computeScoring` or a raw `completed || passed` test; a new SQL reader joins the two views on `(course_id, user_id, learning_path_id)`; a new column that carries a learner's context references `learning_paths(id) on delete no action`; a new write of an attempt, request or visit names its context.

## Alternatives considered

- **"Any finished attempt" in any context counts toward the path** (the recommendation put to the owner on 2026-11-11: one course-level rule for the path page, the lock and Continue). **Declined by the owner**, in their words: "If a learner has already completed a course individually through the Library, that completion must NOT count towards the same course when it is included in a Learning Path. The learner must complete it again within the Learning Path." Recorded as declined.
- **Keep ADR 0014 course-level and let a path launch after an individual completion be a "counted revision visit"**: contradicts the owner's correction of 2026-10-21 (a revision visit never produces a result) and would need a third kind of row. Rejected.
- **Make only the three readers path-context (L2 everywhere) without touching the official attempt**: the dead end of the Context stays (no path launch can ever be official once an individual attempt exists). Rejected.
- **A new `learning_contexts` table or a generated `context_key` column** in place of `learning_path_id`: more schema for the same semantics; a generated column rewrites the table at the paste. Not chosen now; the two partial indexes and `is not distinct from` give the same guarantees on the existing column.
- **`nulls not distinct` on one unique index**: ties the file to the server's major version; two partial indexes do not.
- **`on delete restrict` on the context FKs**: breaks the organisation cascade that the CI purge and the lifecycle cleanup rely on; `no action` refuses a lone path delete and lets the cascade through.
- **Code first, then 0107** (ADR 0020's order for 0105): the new lookups need the two indexes to allow two open rows; the wrappers make the paste-first window safe instead.
- **A backfill that moves the staging learner's individual attempt into the path context**: a rewrite of learner history (principle 3) and unnecessary: the next launch opens a path-context attempt.
- **Webhook per context now** (decision (c) alternative): a shape change for a consumer that does not use the webhook; recorded as the later option.
- **Course Reports individual only** (decision (d) alternative): undoes ADR 0020's reason for counting path learners. Recorded as the alternative.
- **Reading the role at launch instead of `is_preview` for decision (g)**: the role is not stored on the row; only `is_preview` records it.
- **A per-context `effective_attempt_policy(p_course_id, p_learning_path_id)`** so that a path-scope rule applies inside its path only: under the 0103 clamp every answer is the same constants, so it would change nothing today; recorded as the later option if the clamp is ever lifted.
- **Recreating `mv_leaderboard` with one score per course (the context of enrolment)**: needs the enrolment view inside the `scores` CTE; the per-context average is the same rule `mv_learner_metrics` takes and needs no body change. Recorded as the alternative.
- **Leaving the `computeScoring` guard for the last pull request**: a window of several pull requests with no guard at all; the allow-list keeps the guard live from PR A.
- **"Once done, stays done" for a failed path-context retake**: decision (h)'s alternative; the lock would then disagree with the path's reports and the CRM path object.

## Plain-words summary for the owner

**What this fixes.** You took Chapter 3 on its own (as a staff preview), then opened it from the Learning Path. The LMS treats a course as "done once, done everywhere", so the path could never record a path attempt of its own, Continue let you through, and on return the path showed Chapter 4 locked. Your answer was that a Learning Path is a separate product: a course finished in the Library does not count inside a path. This record builds exactly that, once, so every screen and report gives the same answer.

**What changes for learners.**
- A course has one official attempt **on its own** and one **inside each Learning Path**. Finishing it in the Library does not finish it in a path; finishing it in a path does not finish it in the Library. Revision visits (review only) and admin-granted retakes follow the same split.
- Once a learner completes a step from inside the path, the next step unlocks and stays unlocked after they exit and come back, after revision visits, and after an assignment change. (Open question (h) below: what happens when an admin grants a retake and the learner fails it.)
- The course page shows the learner's own-course result and, underneath, one line per path: "In <path>: Passed 90 %" or "Not started". The path page shows the path result.
- A learner can be in the middle of a course in the Library and in a path at the same time; the two do not disturb each other.
- Points: a learner gets the completion points, the pass marker and each score bonus once per course (not again for the same course in a path; the high-score and perfect bonuses are two separate bonuses, so one can be earned in the Library and the other in a path, as today across a granted retake), and a path attempt is scored on its own merits. Streaks and daily points count every official run.
- Journeys read the own-course result: a course finished only inside a path does not credit a journey day.
- Staff previews (if you accept (g)) never count as anyone's official result, in either context; the preview can open any step but will not show progress. Learner-flow testing then needs a `user`-role account.

**What changes for admins.**
- Path pages and reports (the path Learners tab, its CSV, the path Reports page, the Learning Paths list, the dashboard tiles, the path numbers in Reports) count only attempts taken inside that path.
- The course Reports page gets a "Context" column and filter (All contexts, Individual, each path). Each enrolled learner is counted once, in the context they are enrolled through. Completed, Passed and Failed can **fall** on the first refresh where a path learner's only completion was in the Library; Enrolled does not change. The migration lists which courses move.
- The leaderboard's Highest Scorer average takes each context's official score, so a learner with two official attempts on one course can see their average move at the first refresh.
- Attempt requests and grants carry a context ("Learning Path: <name>" in the queue). A grant for the own-course never opens a path retake, and the other way round.
- The daily reminder and the overdue count stop treating a path completion as finishing a direct assignment.
- A Learning Path that has learner attempts can no longer be deleted; it is deactivated instead.
- The CRM (Yoddha) feeds keep their shape. The path objects count path attempts only. A learner who finished a course only inside a path now reads `not_started` on that course row until they take it on its own. The `course_completed` webhook is sent for own-course completions only. A five-line addendum to the consumer notice says all this; it is agreed before the production release, as the notice was.

**Decisions for you**, each with my recommendation:
- (a) **What is a context?** The course on its own, plus each Learning Path separately. Journeys are not a context; they read the own-course result. *Recommend yes.*
- (b) **CRM feeds.** Course rows report the own-course result (shape unchanged); path objects report the path. One addendum to the notice. *Recommend yes.*
- (c) **Completion webhook.** Sent for own-course completions only; a path completion is read from the path objects. *Recommend yes.*
- (d) **Course Reports.** Each enrolled learner once, in the context they are enrolled through, with a Context filter. *Recommend yes.*
- (e) **Points and leaderboard.** Completion, pass and bonus points once per course; every context's first official attempt is scored; the leaderboard average takes each context's score. *Recommend yes.*
- (f) **Learner's course page.** Own-course result on top, one line per path underneath. *Recommend yes.*
- (g) **Staff previews.** Never a learner's official result, in any context. *Recommend yes*, knowing it means staff accounts never see progress on a path page; test with a `user`-role account.
- (h) **A failed admin-granted retake on a pass-required path step.** Does it lock the later steps again? *Recommend yes*: the result that stands is the result, which is what the reports and the CRM already say about a failed retake; the admin can grant another. The alternative, "once done, stays done", would make the lock disagree with the reports.
- Decided by me, say if you disagree: the attempt policy is one per course and the same in every context (today's one-attempt rule makes this true by construction); the leaderboard view is not rebuilt, its rule is written down; nothing is backfilled or rewritten, the stuck staging case fixes itself at the next path launch.

**Effort.** About 16 executor-days in five pull requests (first estimate 11; the review added one database function, several admin pages, the reminder cron, the analytics feed and a paging fix), plus two sittings of yours: pasting migration 0107 on staging (before the code lands, as 0103 was), and the production sitting where 0105, 0106 and 0107 are pasted before the release tag. Production has no learners, so nothing there needs a backfill or a per-learner list. This is a launch blocker: the first real cohort would hit the stuck case by taking a course and then its path.
