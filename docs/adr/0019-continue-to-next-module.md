### Why a page route, and why no migration

The continue address shows a learner a screen ("Saving your result") and then moves them. That is a learner page, not an API: nothing machine-readable is answered and no client code polls it. It lives at `app/[org]/(learner)/continue/page.tsx`, a new route folder under `(learner)`; the advisor was consulted for this record (Round 80, again on 2026-11-10 for the design, and again at the fold). The route reads only, on the caller's RLS session, and writes nothing: the result is written by the same statements and commits as today, so no new completion path exists. **No migration is needed, and no `continue-migration.sql` is written.** No cron, no environment variable, no new library. The grants rule and the DO-block form of 0103 therefore do not apply to this record.

### Words

Step = one `learning_path_courses` row. Next step = the row of the same path with the smallest `step_number` greater than the `from` course's. Official result stored = the learner's official attempt on the `from` course (as `computeScoring` picks it over the attempts that count, abandoned and revision rows excluded) exists and `courseStatus` does not read `in_progress`. Done = `officialDone(scoring, passRequired)`: with `pass_required` the official attempt must have passed; without it any stored official result is done. Revision visit, granted retake and official attempt are ADR 0014's terms.

## Decision

Goal: a learner who launched a module from a Learning Path can move to the next step with one click; the LMS moves them only after the module's result is stored, and only when that result completes the step under the course's `pass_required` setting (the owner's answer 6). Out of scope: the KIVO result-slide option (KIVO 2.0), journeys (a named later extension), any change to the launch page's gates or the path page's completion rule (the strict lock's own gap on a crafted URL is a named follow-up under Consequences), the CRM/Yoddha feeds, SCORM 2004.

### A. The continue route

1. **New page `app/[org]/(learner)/continue/page.tsx`** (server component; `params: Promise<{ org }>`, `searchParams: Promise<{ lp?: string; from?: string }>`, both awaited). Order, every refusal a `redirect()` outside any `try`:
   - `lp` and `from` must each match the uuid shape; otherwise `redirect(/{org}/dashboard)`.
   - `const { user, org, role } = await requireOrgAccess(orgSlug)` (`lib/auth/require-org-access.ts:15`; it sends a signed-out visitor to `/login`).
   - On the caller client (`createClient()` from `lib/supabase/server.ts`), each read with `{ data, error }` checked: the path, `learning_paths` select `id, is_active` with `id = lp` and `organization_id = org.id`; none, inactive or a read error → `redirect(/{org}/dashboard)`. The steps, `learning_path_courses` select `course_id, step_number` with `path_id = lp`, ordered by `step_number`; a read error → `redirect(/{org}/dashboard)`. If `from` is not among them → `redirect(/{org}/paths/{lp})` with the log line `continue_not_a_step`.
   - `next = nextStepAfter(steps, from)` (step 3).
   - `const isStaff = launchModeFor({ role, revision: false }).isPreview` (`lib/alds/launch.ts:58-61`: `super_owner`, `admin`, `data_analyst`), the launch page's own test at `:1153`: no wait; go to the target of the next bullet at once. Preview launches record no official result, so a wait could never end early for them. Where the next launch then sends a staff member is the launch page's existing rule (the entitlement and release gates let staff through, the strict lock does not), which the route defers to like every other case.
   - Otherwise the wait (step 2), which yields `stored`, `done`, `timedOut`. Then `redirect(continueTarget({ orgSlug, pathId: lp, isStaff, timedOut, stored, done, next }))` (step 3): stored and done → `next` present: `/{org}/courses/{next}/launch?lp={lp}`; `next` absent: `/{org}/paths/{lp}?end=1`. Stored and not done → `/{org}/paths/{lp}?failed=1`, never the next launch, with the log line `continue_not_done`. Timed out → `/{org}/paths/{lp}?saving=1` with the log line `continue_timeout`.
   - Logs are the house pattern, `console.warn(JSON.stringify({ event, path_id, course_id, user_id }))`, ids only.
   The route relies on the launch page for release dates, locks and assignment: a refused next launch lands where the launch page sends it today (`dashboard?upcoming=` or `dashboard?locked=`, `:667`, `:735`; a disallowed course `dashboard?denied=1` or `?upcoming=`, `:236-242`). A learner who is not assigned to the path reaches the path page's own refusal (`paths/[pathId]/page.tsx:119`). Nothing here repeats those rules. The page imports `lib/auth/require-org-access.ts`, `lib/alds/launch.ts` (`launchModeFor` only), `lib/supabase/server.ts`, `lib/scoring/*` and `lib/learner/continue.ts`.
   Proof: spec 63 (b), (c), (d), (e), (e2), (g), (h), (i); `tests/unit/continue.test.ts` (`continueTarget`, `isUuid`, the `data_analyst` preview case); step 11 (a) and (b).

2. **The wait.** Before the loop, once, every read on the caller client with `{ data, error }` checked; **any error, or a course or version set that cannot be read, ends as the timeout target** (`/{org}/paths/{lp}?saving=1`, log line `continue_read_error`), because the fail-soft helpers would read "not required" or "no grants" on an error and move a learner on wrongly:
   - `courses` select `pass_required` with `id = from`, `maybeSingle()`; `passRequired = row?.pass_required === true`; no row or an error → the timeout target. The route does not call `fetchPassRequired` (fail-soft).
   - `course_versions` select `id` with `course_id = from`; an error or no rows → the timeout target.
   - `attempt_requests` select `used_attempt_id` with `user_id = user.id`, `course_id = from`, `status = 'approved'`, `used_attempt_id not null` (the learner's own rows, policy `0083:54-56`); `retakeIds = new Set(rows.map((r) => r.used_attempt_id))`, a `Set<string>`, the shape `computeScoring` takes; an error → the timeout target. The route does not call `fetchGrantRetakeIds` (fail-soft, and keyed by course).
   - `policy = await resolvePolicy(supabase, from)` (`lib/scoring/resolve.ts:44`), fail-soft to `DEFAULT_POLICY`. Accepted here, with the reason: under the owner's revision policy (one official attempt; extra attempts only by admin grant) the default and a read policy choose the same official attempt once the grant ids above are passed; the route writes nothing; and the next launch's own gates read the rows again.
   In the loop, every `CONTINUE_POLL_MS = 1000` for at most `CONTINUE_WAIT_MS = 6000` (reads at 0, 1, … 6 s, so at most seven): the learner's attempts on those versions through `readWithOptionalColumn("is_revision", …, "id, score, started_at, completed_at, completion_status, success_status, status")` on the caller client (the launch page's `MY_COLUMNS` shape, `:308`, with the 0103 fallback); an error ends the wait as the timeout target. Then `scoring = computeScoring(rows, policy, retakeIds)`; `stored = resultStored(scoring, rows) && !verdictPending(scoring, passRequired)` (step 3; the verdict test was added at the build's review fold under the lead's ruling: a `pass_required` course's result is not stored until its verdict is, see Notes, 2026-11-11). When `stored`: `done = officialDone(scoring, passRequired)` and the loop ends. The sleep is `await new Promise((r) => setTimeout(r, CONTINUE_POLL_MS))`; it costs no CPU. Budget on the Workers free plan, for the whole request at the worst poll count: the middleware session read, the learner layout (about twelve reads), the page's `requireOrgAccess` (about five), the path, the steps, the course, the versions, the grants, the policy, and at most seven attempt reads: about 30 of the 50-subrequest cap. CPU is a few milliseconds.
   Proof: spec 63 (b) (the bound and the unchanged row), (c), (e), (e2) and (g) (an early answer once stored); `tests/unit/continue.test.ts` (`resultStored` over every row mix; `verdictPending` directly, and the wait over a sequence of reads, added at the review fold (Notes, 2026-11-11): `completed` then `passed` on the next read moves on, `completed` with no verdict by the bound lands on `?saving=1`, a real failed verdict on a `pass_required` course lands on `?failed=1`, a completed result on a course without `pass_required` moves on; `continueTarget` with `done` true and false); `tests/unit/launch-bar-copy.test.ts` (the page's loop concludes on `resultStored(...) && !verdictPending(...)`).

3. **Pure helpers in `lib/learner/continue.ts`** (the existing `lib/learner/` folder; no `next/*`, `lib/alds/*` or Supabase runtime import, the `lib/attempts/launch-kind.ts` shape):
   - `nextStepAfter(steps: Array<{ course_id: string; step_number: number }>, fromCourseId: string): string | null`: the `course_id` with the smallest `step_number` greater than the `from` row's; `null` when `from` is the last step; throws nothing, returns `null` when `from` is not a step (the page checks that case first and never reaches this branch).
   - `resultStored(scoring: ScoringResult, attempts: ScorableAttempt[]): boolean`: `scoring.officialAttempt !== null && courseStatus(scoring, attempts) !== "in_progress"`. So: a completed, passed or failed official attempt → true (a failed result is stored; whether it is done is `officialDone`'s answer); only an in-progress row → false; only abandoned rows → false; only a revision visit's row → false (a revision visit of a course whose official attempt is complete reads true through that attempt); a live granted retake → false until it completes.
   - `verdictPending(scoring: ScoringResult, passRequired: boolean): boolean`: `passRequired && scoring.officialStatus === "completed"`, the official attempt completed without its pass or fail on a `pass_required` course. While it is true the wait goes on; at the bound the learner lands on `?saving=1`, never `?failed=1`. Added at the build's review fold under the lead's ruling (see Notes, 2026-11-11).
   - `continueTarget(i: { orgSlug: string; pathId: string; isStaff: boolean; timedOut: boolean; stored: boolean; done: boolean; next: string | null }): string`, the branch table in this order, unit-tested row by row:
     1. `isStaff` → `next` ? `/{org}/courses/{next}/launch?lp={lp}` : `/{org}/paths/{lp}?end=1`;
     2. `timedOut` → `/{org}/paths/{lp}?saving=1`;
     3. `stored && !done` → `/{org}/paths/{lp}?failed=1`;
     4. `stored && done` → `next` ? the next launch : `/{org}/paths/{lp}?end=1`;
     5. otherwise (not staff, not timed out, nothing stored: a state the page never produces) → `/{org}/paths/{lp}`, so the function always returns.
     The page calls it with `timedOut = true` only when `stored` is false, and computes `done` only when `stored`.
   - `CONTINUE_WAIT_MS`, `CONTINUE_POLL_MS`, `isUuid(s)` exported from the same file.
   Proof: `tests/unit/continue.test.ts` (step 10), every branch named there.

## Consequences

- A learner on a Learning Path moves module to module without the dashboard or the path page in between, only after the result is stored, and only when the result completes the step under the course's `pass_required` setting. A failed `pass_required` module ends on the path page with a plain sentence and the way to ask for another attempt. Library and journey launches look as today apart from the bar's layout.
- **Follow-up, not an owner question**: the launch page's strict lock (`:711-731`) should read `officialDone` over `excludeAbandoned` rows with the course's `pass_required`, so a crafted URL to a later step after a failed `pass_required` module lands on `dashboard?locked=` like the path page's "Locked" button. A separate small record or a fix under this one, scheduled by the owner; until then the gap exists only for a hand-typed URL, since the Continue route and the path page both refuse.
- The bar is one component for both runtimes; a later change (a journey Continue, a progress indicator) is made once.
- The badge reads "Revision Mode"; ADR 0014's note that it reads "Revision" (`0014:328`) is amended by this record on the wording only, the test id unchanged.
- Specs 43, 57 and 58 wait on `launch-bar` instead of the format label.
- The route is the LMS half of the proposal's layer 3: when KIVO 2.0 adds "Continue in the LMS" on the result slide, the launch page can set the cmi5 `returnURL` to this address for path launches (today it stays `backHref`). That is a KIVO ADR plus a one-line LMS change, not this record.
- Journeys: the launch page already knows `journeyNextCourseId` (`:209-214`); a later record can add `?journey=` to the route and show Continue on journey launches. Hidden until then.
- The L2 difference between the launch lock and the path page is written down (step 15); it is older than this record.
- `docs/ARCHITECTURE.md` §2 gains `continue/` under the learner pages and `lib/learner/continue.ts`; §8 gains the verification row of steps 10-13; §9 gains the strict lock's `pass_required` gap as a known hazard, at acceptance.

## Alternatives considered

- **A route handler** (`app/api/paths/[pathId]/continue`) polled by a client component: a second surface, JSON for a browser-only flow, and the same reads; rejected for a page that shows one sentence and moves on.
- **A fixed Exit URL in the KIVO export**: names one environment and one next module, nests the LMS inside the module frame, and moves before the result lands (PROPOSAL.md, "Why a fixed Exit URL is not the answer"); rejected, and not to be shipped to real learners.
- **A client-side poll inside the launch page** (the bar watches the attempt and enables Continue when stored): a second reader of the result in the browser, a token or an API to read it with, and a learner-visible flicker; rejected; the address does the waiting.
- **Reload-polling** (the page re-requests itself with a counter): a full page and layout render per tick, about eight reads each; rejected for the single bounded server wait.
- **Moving on any stored result and leaving `pass_required` to the launch page's lock** (the first draft of this record): today's lock reads no `pass_required`, so a failed learner on a `pass_required` course would have been sent into the next module, against the owner's answer 6 and the approved revision plan; rejected at the fold.
- **Changing the strict lock inside this record**: a gate change to the launch page in a record about a button and a route; rejected here and named as a follow-up under Consequences.
- **Using `fetchPassRequired` and `fetchGrantRetakeIds` in the route**: both are fail-soft and would read "not required" or "no grants" on a read error, which would move a learner on wrongly; rejected for strict reads whose error ends as the timeout target.
- **Hiding the title through `ensureEngineVersion` at launch**: a storage read and a regex over a multi-megabyte file on the first launch of every unstamped version, on the Workers free plan; rejected in favour of the cached stamp (decision 1).
- **`next/link` for Continue**: the module frame would be unmounted by the router rather than unloaded by a navigation, and the router may prefetch a route that waits and redirects; rejected; Exit keeps its `Link`, as pinned.
