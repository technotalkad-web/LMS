# 0013. Patch the bundled react-dom's lost ping at bundle time until Next ships the fix

Status: Accepted (owner, 2026-10-19): Option A, React's upstream fix applied to the bundled react-dom at bundle time, with the fail-the-build safeguard of decision 2 kept; the owner's words are recorded under "Decisions requested from the owner", as ADR 0008–0011 do, not by rewriting this record. Code only, no migration, no API or schema change. Ships with the next build on every environment.
Date: 2026-10-19
Deciders: owner; executor (diagnosis and fix on branch `fix/course-default-header-refresh`)

## Context

- **The symptom.** Library → course → Languages → "Set as default" on another language: the POST succeeds (the course default moves, the `course.default_slot_set` audit row is written), the table's Default badge moves (client state), but the server-rendered header ("Default language: …") and the Versions list keep the old default until the admin reloads the page. Lifecycle spec 54 test 7 asserts the header and failed 10 of 10 times on the owner's laptop against `next start`, and passed on Cloud Run staging. It also failed once on Linux CI (run 39213802412, 2026-10-19: "5 test(s) skipped in 54-course-default.spec.ts"; the spec is serial with 12 tests, so test 7 failed and 8–12 were skipped). That CI failure is attributed to this mechanism by inference (same test, same assertion), not by trace: the job log and trace need authentication and were not read.
- **The cause is in React, not in our code.** The `router.refresh()` after the POST fetches the new RSC payload (it already says the new language), and the router's pending state holds the new tree, but React never commits it. Next 15.5.18 bundles react-dom `19.2.0-canary-0bdb9206-20250818` (`node_modules/next/dist/compiled/react-dom`), which the App Router uses instead of the app's own `react-dom`. In it, a transition that suspends on a streamed RSC chunk inside a Suspense boundary already showing content (here `[courseId]/loading.tsx`) can lose its retry: when the chunk finishes streaming during React's one-task pause, React attaches its ping listener to an already-resolved chunk, the listener fires synchronously inside the render, and `pingSuspendedRoot` drops an in-render ping (`0 === (executionContext & 2) && prepareFreshStack(root, 0)`). The render ends suspended, `markRootSuspended` clears the pinged lanes, and nothing pings again. Every later `router.refresh()` or soft navigation on that tab hangs too, until a full reload. It depends on timing: the page's RSC response must still be streaming when React reaches the page segment, which is why a laptop talking to staging Supabase reproduces it every time and Cloud Run rarely does.
- **Proof.** Applying only React's upstream one-line change to the served chunk (in the test browser's memory) made spec 54 pass 3 of 3 runs; the same setup without the change failed. React's internal state after a failure showed the transition lane suspended, no pinged lanes and no scheduled callback, with every chunk it had waited on fulfilled.
- **Upstream.** Fixed in react-dom `19.3.0-canary-278794d7-20261002` (bundled by Next 16.4.2): an in-render ping is recorded in `workInProgressRootPingedLanes`, so the render is retried. Not fixed in Next 15.5.28 (the newest 15.x, same React canary) nor in stable react-dom 19.2.4. Bumping `react`/`react-dom` in `package.json` does not help (the App Router uses Next's bundled copy).
- **Exposure.** Every `router.refresh()` and soft navigation in the app can hit it when the RSC response streams slowly: toggle active, Replace content, Assign, Details, Scope, Scoring, version actions, not only Set as default.

## Decision

1. **Apply React's upstream fix to the bundled react-dom client builds when webpack bundles them.** `scripts/react-dom-ping-fix.cjs` is a webpack loader registered in `next.config.ts` for `next/dist/compiled/react-dom/cjs/react-dom-{client,profiling}.{production,development,profiling}.js`. It rewrites `? <not rendering> && prepareFreshStack(root, 0) : (workInProgressRootPingedLanes |= pingedLanes)` into the nested ternary React ships (`? <not rendering> ? prepareFreshStack(root, 0) : (workInProgressRootPingedLanes |= pingedLanes) : (workInProgressRootPingedLanes |= pingedLanes)`). `node_modules` is never modified, so no install hook, no Dockerfile change and no stale build cache: every path that runs `next build` or `next dev` (lifecycle nightly, `cf:build` for staging and production, the Cloud Run Dockerfile, Playwright's `npm run dev`) bundles the fixed copy.
2. **Fail loud on a Next upgrade.** The loader passes a source through unchanged when it already has the fixed form, and otherwise requires the broken form exactly once; zero or several matches throw, which fails the build with the file name and a pointer to this record. `tests/unit/react-dom-ping-fix.test.ts` (the `unit` job) pins the transform for both spellings (production and development builds), the refusals, the path rule on both path separators, and that each of the four installed files is matched by the rule and patched exactly once.
3. **Exit condition.** When Next is upgraded to a version whose bundled react-dom carries the fix (verified for 16.4.2), the unit test's installed-file check reports `already-fixed` instead of `patched` and fails: remove the loader from `next.config.ts`, the script and the test, and mark this record superseded.
4. **Spec 54 is unchanged.** Test 7 keeps asserting the server-rendered header without a reload; it is the regression test for this record.

## Limits

- Only `pingSuspendedRoot` is backported. A function-by-function diff of the bundled `react-dom-client.production.js` (Next 15.5.18 against 16.4.2) shows the ping path otherwise identical (`attachPingListener`, `isThenableResolved`, `resolveLazy`, `ensureRootIsScheduled`; `renderRootConcurrent` differs only in a renamed variable), and 15.5.18's `markRootSuspended` already keeps a recorded ping's lane pending (`suspendedLanes &= ~workInProgressRootPingedLanes`). The other 19.3 changes found there (`getEntangledLanes` in `markRootSuspended`, SuspenseList and Activity handling in `throwException`) belong to other features and are deliberately left out.
- Proven so far on the owner's laptop (Windows, `next start` against staging Supabase). Linux CI and Cloud Run staging confirm it only after the branch runs there.
- webpack only. Under `next build --turbopack` / `next dev --turbopack` the loader does not run; neither is used today. Moving to Turbopack needs the fix ported to `turbopack.rules`, or Next upgraded past the bug, first.
- The react-dom-experimental copy (used only with PPR / cacheComponents, not enabled) and the app's own `node_modules/react-dom` (bundled only into the Pages Router `framework` chunk; this app has no `pages/` directory, so it serves only Next's built-in error fallback) are not patched.

## Alternatives considered

- **Upgrade to Next 16.x.** The clean fix, but a major upgrade (breaking changes per AGENTS.md; the OpenNext/Cloudflare and Cloud Run builds need checking) and a full regression run; not a minimal fix. It remains the way to retire this record.
- **Patch `node_modules` in a `postinstall` script (or patch-package).** Same change, but mutates installed files, needs the Dockerfile to copy the script before `npm ci`, and webpack's persistent cache treats `node_modules` as immutable per package version, so a cache built before the patch would keep serving the broken chunk.
- **Page-level workaround** (a full page load after Set as default, or a watchdog that reloads). Fixes one call site, leaves every other refresh and navigation exposed, and loses client state; rejected.
- **Change the spec** (reload before the assertion, a longer timeout, or asserting the client-only badge). Would hide a real admin-facing bug; rejected.

Decided (owner, 2026-10-19): A, in the owner's words: "I approve Option A: apply the small React fix during the build, as recorded in ADR 0013. Please keep the safeguard that stops the build if a future Next.js upgrade changes the affected code." The safeguard the owner names is decision 2 as written, and it is kept: the loader throws, so `next build` and `next dev` fail naming the file and this record, whenever a matched react-dom file does not contain the broken form exactly once (zero or several matches), which is what a Next upgrade that changes the affected code produces. A file that already carries the upstream fix is passed through unchanged and does not stop the build; that case is caught by `tests/unit/react-dom-ping-fix.test.ts` in the `unit` job, whose installed-file check then fails with `already-fixed` instead of `patched` (decision 3, the exit condition). Neither check is removed or weakened while the loader exists. B remains the way to retire this record (decision 3); C stays rejected as recorded under Alternatives considered.
