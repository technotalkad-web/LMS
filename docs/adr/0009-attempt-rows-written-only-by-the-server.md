# 0009. Learner attempt rows are written only by the server

Status: Proposed
Date: 2026-10-17
Deciders: owner; architect (Fable 5.1)

## Context

Facts below were verified on 2026-10-17 by reading the migrations and the code on branch `feat/adr-0008-restart-default` (line numbers refer to that tree), not by probing a database. No learner's row was read or written.

- **The policies.** `supabase/migrations/0002_courses.sql` lines 161–175 give `public.course_attempts` three policies: `members read own attempts` (select: `user_id = auth.uid() or public.is_org_admin(organization_id)`), `members create own attempts` (insert: `with check (user_id = auth.uid() and public.is_org_member(organization_id))`) and `members update own attempts` (update: `using (user_id = auth.uid()) with check (user_id = auth.uid())`). No later migration (0003–0098) drops or narrows them, revokes a table privilege on `course_attempts`, restricts columns, or adds a `before insert` or `before update` trigger; 0042/0043 only widened the `status` check to `abandoned`, 0062 added the one-in-progress unique index, 0053/0075/0082 added columns. There is no delete policy, so a learner's PostgREST `DELETE` matches zero rows today. The table predates 2026-10-30, so Supabase's default grants give `anon` and `authenticated` insert, update and delete privileges; row-level security is the only control, and the update policy constrains nothing but `user_id`.
- **What a learner can therefore do** with their own session JWT and the anon key, against `/rest/v1/course_attempts`, without any route: (a) `PATCH` any column of their own rows: `status` (an `abandoned` row back to `in_progress`, undoing ADR 0004 steps 10–11, the ADR 0008 A restart and the language-switch reset), `completion_status`, `success_status`, `score`, `completed_at`, `progress_pct`, `cmi_data`, `last_activity_at`, `started_at`, `learning_path_id`, `journey_enrollment_id`, `journey_day`, `course_version_id`, `organization_id`; (b) `POST` a row that was never launched, already `completed`/`passed` with any score, on any version id it knows, because the insert policy binds `organization_id` to the learner's membership but never binds `course_version_id` to that organisation (the FK is the only check), so a forged row may even point at another organisation's version, where the 0098 delete guard then counts it as a learner attempt. Every reader that derives from rows takes such a row as real: `courseStatus()` (`lib/scoring/policy.ts`), `lib/scoring/status.ts` (Library card and Reports tab), the Report Card (`lib/manager/insights.ts`), `/api/integrations/progress` and `learner-summary` (`lib/integrations/progress.ts`), the learner course page, the ADR 0008 restart dry run (its per-attempt list is `status = 'in_progress'` rows), the P1 audit of ADR 0007 step 2, the 0053 monthly `highest_scorer` recognition (reads `score`, `completed_at`, the status columns), `v_course_attempt_scoring` and ADR 0005's certification (completion is never tier-filtered, D1). What does not fire from a direct PATCH: the completion webhook, `gamification_record_activity` and `journey_record_completion`, which run only inside the commit and statements routes (both RPCs are `security definer` with execute revoked from `authenticated`, 0053:552–553, 0058:381–382); the engine reads whatever the row holds at the learner's next legitimate commit.
- **Which code writes `course_attempts`, and with which client.** Caller client (`createClient()` from `lib/supabase/server.ts`, the learner's JWT; these depend on the two write policies): (1) `app/[org]/(learner)/courses/[courseId]/launch/page.tsx` line 745, the attempt insert; (2) the same file line 709, the journey-tag update (`journey_enrollment_id`, `journey_day`) on an existing attempt; (3) `app/api/scorm/[attemptId]/commit/route.ts` line 164, `updateAttemptFailSoft(supabase, …, { userId })` in `lib/courses/progress.ts` line 123, the SCORM commit (its comment at line 29, "RLS on `course_attempts` enforces `user_id = auth.uid()` on updates", describes the policy this record removes). Service client, already: the grant-consumption reset (`launch/page.tsx` 281) and the deactivated-slot close (669); `app/api/courses/[courseId]/language-preference/route.ts` 180; both force-restart paths (`.../packages/[packageId]/versions/route.ts` 173, `lib/courses/direct-upload.ts` 666); the per-version restart (`.../versions/[versionId]/restart/route.ts` 198); the webhook latch (`lib/integrations/webhook.ts` 62); every xAPI write (`app/api/xapi/statements/route.ts` and `activities/state/route.ts` through `lib/xapi/auth.ts serviceClient()`, into `processStatement` and `updateProgressFromState`). SQL: `journey_record_completion` (0058, replaced in 0081/0088/0089) updates `journey_enrollment_id`/`journey_day` as a `security definer` function executable by `service_role` only. Tests and seeds write through the service role (`tests/e2e/helpers/supabase.ts svc()`, `scripts/demo/seed-demo.mjs`, `tests/mobile/audit.mjs`). The sibling tables are already server-only: `xapi_statements` has one select policy (0004:67–76), `xapi_state` and `cmi5_launch_tokens` have RLS and no policy, `attempt_requests` grants learners and admins select only (0083:49–65). Reads of `course_attempts` on the caller client are many (learner pages, launch page, exports) and stay.
- **Two items deferred at the P0 build** (ADR 0004 decision 9, "the next migration window"): `v_course_attempt_summary` (0090 lines 142–186, `security_invoker`, granted to `authenticated` and `service_role`) computes `latest_completion`, `latest_success` and `attempt_count` over every row, abandoned included; `mv_path_enrollment_status` (0090 lines 283–316) counts a learner as `in_progress` when `any_attempt` is true, which a reset-only learner satisfies; `mv_course_enrollment_status` (0073 lines 285–299) has the same leak in `in_progress`/`not_started`. Neither matview has an app reader on this tree (`grep from("mv_` finds `mv_course_performance`, `mv_learner_metrics`, `mv_leaderboard` and the two interaction matviews only); the Library Reports tab computes live through `loadEnrolledCourseStatus` (`lib/scoring/status.ts` 200–266) since the P0 build. `refresh_report_views()` (0031, last replaced in 0056) refreshes both matviews by name with `concurrently`, which needs their unique indexes. `tests/rls-audit/audit.sql` fails any table with an `organization_id` column that has zero policies (0045 records the same constraint), so the select policy on `course_attempts` must remain.
- **Numbering and environments.** ADR 0008 decision 2 (owner, 2026-10-17) fixed 0099 = the `package_validations` write guard (ADR 0008 C, not yet written), 0100 = alds core, 0101/0102 = P5. Two app deployments share the staging database: the Workers staging (auto-deployed on push to `main`) and the Cloud Run trial (owner-deployed, on the 2026-10-07 build at the time of writing). Production runs the 2026-09-17 code, holds the 0002 policies and, owner-confirmed on 2026-10-17, has no courses and therefore no attempt rows to forge; its guard follows v1.3.0 like ADR 0008 C.

## Decision

### A. The rule

1. `public.course_attempts` is written only by the server: every insert, update and delete goes through a route handler or server component that has authenticated the caller and uses the service client with explicit `id`, `user_id` and `organization_id` filters. Learners and admins keep reading their rows through the select policy. No PostgREST role other than `service_role` can insert, update or delete an attempt row. This is ADR 0008 C's rule applied to the table that carries grading, certification and the reset state; it does not widen what any caller can read.

### B. Code first (every environment, before the migration)

2. `launch/page.tsx`: the attempt insert (line 745) moves to the service client. Values stay `course_version_id: v.id` (resolved from the course's own packages or `courses.current_version_id`, both read under RLS on the caller client), `user_id: user.id` from `requireOrgAccess`, `organization_id: org.id`; the 0062 unique-violation fallback (23505 → re-select) is unchanged. The file already creates four service clients (`svcReset`, `svcSlot`, `seedSvc`, `svcGrant`) plus `svc` for the cmi5 token; the executor may create one service client once per request and reuse it; nothing else about the page changes.
3. `launch/page.tsx`: the journey-tag update (line 709) moves to the service client, filtered `.eq("id", existing.id).eq("user_id", user.id).eq("organization_id", org.id)`.
4. `app/api/scorm/[attemptId]/commit/route.ts`: the read (line 59) stays on the caller client; the write (line 164) becomes `updateAttemptFailSoft(svc, attemptId, update, { userId: user.id })` with a service client, so the conditional `status <> 'abandoned'` and the `user_id` filter in `lib/courses/progress.ts` lines 129–137 keep protecting the row. The `userId` extra stays optional in the signature (the token-bound xAPI callers have none) and is mandatory at this call; the stale comment at line 29 is corrected to say the route authorises and the service client writes. Response codes, the non-downgrade rules, the webhook, XP and journey calls are unchanged.
5. New unit test `tests/unit/attempt-write-sites.test.ts`, modelled on `tests/unit/lrs-abandon-sites.test.ts`: it scans every file under `app/` and `lib/` for a `.from("course_attempts")` chain that calls `.insert(`, `.update(`, `.upsert(` or `.delete(` and for every `updateAttemptFailSoft(` call, and compares against an allow-list of file, write count and receiver identifier (`launch/page.tsx` 4 writes; `lib/courses/progress.ts` 1; `language-preference/route.ts` 1; `versions/route.ts` 1; `lib/courses/direct-upload.ts` 1; `restart/route.ts` 1; `lib/integrations/webhook.ts` 1; the commit route's `updateAttemptFailSoft(svc, …)`; every other file 0). A new write site, or a receiver that is not a service-client identifier for that file, fails the `unit` job. Runs in `npm run test:unit`.

### C. The migration (SQL intent; one file, idempotent, `begin; … commit;`, ends with `notify pgrst, 'reload schema'`, passes `scripts/check-migration-grants.mjs`)

6. Recommended placement (decision 2 below): the file is `0099_postgrest_write_guards.sql`, with three sections. Section 1 is ADR 0008 step 19 verbatim (the `package_validations` policy split, revokes and grants); ADR 0008 is not rewritten, this record only adds sections 2 and 3 to the same file. Section 2, `course_attempts`:

   ```sql
   drop policy if exists "members create own attempts" on public.course_attempts;
   drop policy if exists "members update own attempts" on public.course_attempts;
   -- "members read own attempts" (0002 lines 161-164) is kept unchanged: learners read their own rows, admins their organisation's.
   revoke insert, update, delete on public.course_attempts from anon, authenticated;
   grant select on public.course_attempts to authenticated;
   grant select, insert, update, delete on public.course_attempts to service_role;
   ```

   RLS stays enabled; no new policy is created (an insert or update by `authenticated` now fails with 42501 at the privilege, and would match no policy even if the privilege were ever re-granted). The two delete-guard functions of 0098 and `journey_record_completion` are `security definer` and unaffected. No new table, so no new-relation grant; the literal grants above are the explicit statement the guard script and `docs/MIGRATIONS.md` ask for.
7. Section 3a, `v_course_attempt_summary`: `create or replace view` with the existing nineteen columns unchanged in name, order and type, plus three trailing columns computed in the `base` CTE over `ca.status <> 'abandoned'`: `live_attempt_count` (`count(*) filter (where ca.status <> 'abandoned')`), `latest_live_completion` and `latest_live_success` (the same `array_agg(... order by ca.started_at desc)[1]` with that filter). `alter view ... set (security_invoker = on)` and `grant select on public.v_course_attempt_summary to authenticated, service_role` are repeated (idempotent). `docs/ATTEMPT_SCORING.md` gains one sentence naming the three columns and that `attempt_count`/`latest_completion` keep counting reset attempts for history.
8. Section 3b, the two matviews, each `drop materialized view if exists` then `create materialized view` with the same name and columns, its unique index (`mv_course_enrollment_status_idx (course_id)`, `mv_path_enrollment_status_idx (path_id)`; `refresh_report_views()` refreshes `concurrently`), `revoke select ... from anon, authenticated` and the literal `grant select ... to service_role` (0049/0090 shape). `mv_course_enrollment_status`: `completed` = `ever_completed`; `in_progress` = `coalesce(s.live_attempt_count, 0) > 0 and not s.ever_completed`; `not_started` = `coalesce(s.live_attempt_count, 0) = 0 and not coalesce(s.ever_completed, false)`, so the three never overlap. `mv_path_enrollment_status`: 0090's body with `any_attempt` = `bool_or(coalesce(s.live_attempt_count, 0) > 0)`; the `pass_required` branch of 0090 is kept as is. After the apply on an environment the executor runs `select public.refresh_report_views()` through the SQL editor or the `refresh-report-views` cron route and reads the two matviews once.

### D. Deploy order and timing

9. Code before the migration on every environment, never the reverse: with the policies dropped, the old code's launch insert fails with 42501 ("Failed to create attempt" on every launch) and its SCORM commit answers 400. The precondition for applying 0099 on an environment is that every app deployment pointed at that database runs the code of steps 2–4 and of ADR 0008 step 19: on staging, both the Workers staging (push to `main`) and the Cloud Run trial (`bash /d/LMS/deploy-main.sh`, owner-run); the executor confirms the deployed SHAs before asking for the apply. The principle "deploy-safe in both orders" (`docs/ARCHITECTURE.md` §3.6) is deliberately not met here, as for ADR 0008 C, because the change is the policy itself.
10. Staging: 0099 is applied as soon as step 9 holds and spec 55 (step 12) is green on the code; it is not bound to v1.3.0. Production: 0099 is applied only after v1.3.0 is live, never in the ADR 0007 step 5 sitting (ADR 0008 step 20, unchanged), and only if the live tag contains steps 2–4; v1.3.0 should therefore carry this record's code, otherwise 0099 waits for the next tag that does. Production has no attempt rows today, so nothing is exposed there before then.
11. `ops/release-v1.3.0-audit.sql` (ADR 0007 step 2, "absence of every planned 0098/0099 object"): the 0099 object probes are a real select of `v_course_attempt_summary.live_attempt_count` (absent before the sitting, present after the later 0099 apply) and `select policyname from pg_policies where tablename = 'course_attempts'` (the two write policies present before, absent after).

### E. Tests and the staging probe

12. New lifecycle spec `tests/bot/lifecycle/55-attempt-row-guard.spec.ts`, joining the lifecycle-nightly subset (now 50–55; ADR 0007 step 15, ADR 0008 step 17). Seed: a `qa-*` organisation, an admin, a learner (`member`), a second `qa-*` organisation with one course (for the cross-organisation case), a SCORM and a cmi5 course with distinct titles (`uploadNew`, `scormZip`/`cmi5Zip` of `p0-helpers.ts`), assignments, learner launches of both (`inProgressAttempt`). The learner's JWT comes from `signInWithPassword` with `NEXT_PUBLIC_SUPABASE_ANON_KEY` (the spec 50 pattern), the admin's the same way. Every assertion is on a service-role re-read of the row, never on the status code alone (a revoked privilege answers 42501; a dropped policy with the privilege present answers 200 with zero rows; both count as refused). The cases are bound to attempts so that the probe branch of step 13, where the calls succeed, cannot invalidate a later case's precondition: the SCORM attempt serves (a), (b) and (f); the cmi5 version serves the inserts (c) and (d) (a forged `completed` row is not stopped by 0062's in-progress-only unique index); the cmi5 attempt serves (e); (h) launches cmi5 afresh and commits SCORM. (a) learner `PATCH` of own in-progress SCORM attempt to `passed`/`completed`/score 1/`completed_at`/`progress_pct` 100 → row unchanged; (b) learner `PATCH` of `cmi_data` alone on the same row → unchanged; (c) learner `POST` of a never-launched `completed`+`passed` row on the cmi5 version → no new row for that user and version; (d) learner `POST` with the other organisation's version id and own `organization_id` → no row; (e) admin force-restart replace of the cmi5 package (spec 48 pattern) abandons the cmi5 attempt, then learner `PATCH {status: 'in_progress'}` on it → still `abandoned`; (f) learner `DELETE` of the SCORM attempt → row still exists (refused in both branches: no delete policy exists today, and the revoke keeps it so); (g) admin-session `PATCH` on the learner's SCORM row → unchanged; (h) the real paths still work: a fresh cmi5 launch creates an `in_progress` row on the new version and a statement through `/api/xapi/statements` updates it, a SCORM commit through the route on the attempt of (a) answers 200 and the row carries the committed status and score (in the guard branch that attempt is still `in_progress`, because (a) was refused), and the learner still reads their own rows through PostgREST (select policy kept). A `has0099()` probe in `p0-helpers.ts`, keyed on a real select of `v_course_attempt_summary.live_attempt_count` (the `has0098()` shape), selects the branch: with 0099 present the cases assert refusal; without it the same calls run as the **staging probe** of step 13.
13. The staging probe (owner approval requested, decision 4): before the migration, the executor runs spec 55 once against staging on the owner's go. In the no-0099 branch the spec performs exactly the calls of step 12 (a)–(g) on rows of its own `qa-*` organisations, records each outcome (HTTP status, row changed or not) as test annotations and in the report, and asserts the opposite of the guard where the hole is expected ((a)–(e) succeed and change or create the row; (f) and (g) are refused today as well, (f) because no delete policy exists and (g) because the update policy is `user_id = auth.uid()`), so the run is green and legible, and a refused DELETE is not misread as the guard being present. It reads nothing outside its organisations and writes nothing outside them; the `qa-*` rows are removed by the next CI purge. Hazard: never push while it runs (`pr-checks` purges `qa-*` data on every non-main push). The result, with qa ids only, is recorded under this record's acceptance note; it is the only database confirmation of the Context, which was established by reading.
14. Existing proofs stay green on the code before the apply and again after it: lifecycle 00-engine (launch and SCORM commit), 02-journeys (the journey-tag update), 32, 43, 47, 48, 50, 53, 54; `tests/unit/alds-step0.test.ts`, `scoring-status.test.ts` and the new write-sites test in the `unit` job; `rls-audit.yml` on the migration PR (course_attempts keeps one policy that references `auth.uid()` and `organization_id`); `node scripts/check-migration-grants.mjs`; `select public.refresh_report_views()` after the apply. ADR 0008 step 21's spec 52 cases remain the proof of section 1 of the file.

### Risks and protections

| Risk | Protection |
|---|---|
| Learners: launches or SCORM commits fail because the guard lands before the code on some deployment | step 9: code on every deployment that shares the database, SHAs confirmed, spec 55 green, then the apply; production only after v1.3.0 with the code in the tag |
| Grading: the SCORM write changes behaviour when it moves to the service client | the same `updateAttemptFailSoft` with the same payload, the same `status <> 'abandoned'` condition and the same `user_id` filter; spec 55 (h), spec 00, unit `alds-step0` |
| Grading: a forged row exists on staging before the guard | the hole is closed on staging as soon as step 9 holds; production has no rows; the restart dry run and the P1 audit are re-read on the day they are used (ADR 0004 condition a) |
| Privacy: the service client returns more than the learner may see | reads stay on the caller client; the three writes return only the written row's id; the select policy is unchanged |
| Existing records: the migration rewrites or deletes history | no row is touched; the view gains trailing columns; the matviews hold aggregates and are recreated with the same columns |
| CI purge, seed scripts and specs break on the policy drop | they write through the service role (`svc()`); spec 50's purge case stays green |
| `rls-audit.yml` fails `course_attempts` for "no policies" | the select policy is kept (0045 records the same requirement) |
| `refresh_report_views()` fails on a recreated matview | unique indexes recreated (step 8); the refresh is run once after the apply |
| The probe (step 13) touches real data | it creates and uses only `qa-*` organisations; owner go first; result recorded with ids only |

## Consequences

- An attempt row is written only by the launch page, the commit and xAPI routes, the abandon paths, the restart route, the webhook latch and the journey RPC; a learner's session can no longer complete, pass, score, revive or delete an attempt without the content and the route having done it. The 0098 delete guard and ADR 0005's certification stand on rows the server wrote.
- The P4 columns of alds core (`is_preview`, `launch_mode`, `served_language`, ADR 0005 step 10, ADR 0006 step 17) are written by the same service-client insert; no policy widening is ever needed for them.
- If decision 2 is accepted, 0099 carries both PostgREST write guards and the view and matview corrections; 0100, 0101 and 0102 keep their meanings; `docs/ARCHITECTURE.md` §6's wording for 0099 changes at acceptance, not now; the file waits for both code halves on each environment.
- `v_course_attempt_summary` readers can tell live from reset attempts; the two matviews count a reset-only learner as not started, like the live Reports tab; the Library Reports page keeps computing live (not returned to the matview by this record).
- Spec 55 is the standing proof that no PostgREST role but `service_role` writes attempt rows; the write-sites unit test is the standing proof that no code path reintroduces a caller-client write.

## Alternatives considered

- A `before insert or update` trigger refusing writes without the `service_role` claim (the 0098 delete-guard shape) instead of, or in addition to, the policy drop: order-independent, but it would also refuse hand-applied migration backfills such as 0003 and 0062, which run as `postgres` with no claim, and it restates what the policy drop plus revoke already enforces for PostgREST; rejected for the same reason as ADR 0008 C's trigger alternative. Revisit only if a write policy is ever re-added by mistake.
- Column-level restriction of the update policy (let learners update `cmi_data` and `last_activity_at` only): still lets a stale tab revive progress on an abandoned attempt and leaves the insert hole; the routes already carry every legitimate write.
- Keeping the insert policy and dropping only the update policy: the forged-completion case (c) stays open.
- A separate `0100_course_attempts_write_guard.sql`: one topic per file, but it shifts alds core to 0101 and P5 to 0102/0103 one day after ADR 0008 decision 2 fixed them, and the "0102 is not the blueprint's cut item" disambiguation would have to be restated for 0103; the production timing is identical to 0099's, so the separate file buys nothing but a second owner sitting.
- Deferring the view and matview corrections again: they need a migration window and have no learner risk; the next window after 0099 is 0100 (alds core, P4), weeks away.
- Changing existing columns of `v_course_attempt_summary` to exclude abandoned rows: `create or replace view` cannot change existing columns, and `attempt_count`/`latest_completion` are history; trailing columns keep both.
