Status: Accepted (owner, 2026-10-16)

## Context

- "Reliable analytics" needs a definition. The v1 question analytics (`mv_course_interaction_breakdown`, `mv_course_interaction_top_wrong`; migrations 0031/0035) key on `(course_id, raw->object->>id)` with no version dimension, count surveys, timeouts and unanswered items as incorrect, and never covered SCORM. Completion, score, official status, the Report Card, CRM progress and journeys read `course_attempts` only, for every format.
- The blueprint's certification (B5 in the first plan) was reviewed and found under-specified in six places: running it through the real learner path fires CRM webhooks and tenant-LRS forwards; direct-upload validation is not bound to the stored bytes; admins can insert `course_versions` rows and manage `package_validations`, so a naive tier column can be forged; strict gateway rules would reject learner batches on uncertified Level 2 versions; neither the LMS nor KIVO implements `LMS.LaunchData` today; the runner had no hosting (Workers cannot run a browser).
- The KIVO engine digest cannot be computed from stored bytes as the blueprint assumes: COURSE_CONFIG, a per-export license header with a timestamp and an optional domain-lock IIFE all live inside the engine `<script>` block. The editor already runs the real engine in a same-origin preview iframe, so a per-export self-check is possible without Playwright.
- D2 (integrity block, warn, override, uncertified still launches) is carried by ADR 0004, not by this record; this record restates only the launch rule.

## Decision

### 1. Definitions

1. `course_versions.analytics_tier ∈ unverified | pending | uncertified | certified | revoked`. "Legacy" is a UI label for pre-Guardian rows, not a tier. Transitions: no manifest → `unverified`; manifest parsed → `pending` for the duration of the synchronous static check, then `certified` or `uncertified` (with a reason: rule id and one line); timeout → `uncertified (check_error)` with a Re-run action; production findings or digest mismatch → `revoked` (carrying the finding ids and the first violating statement).
2. The tier is written only by a security-definer function `alds_set_version_tier()` executable by `service_role`; that function sets a transaction-local GUC (`set local alds.tier_writer = 'on'`) and a `before insert or update` trigger guards the column: on INSERT it forces `analytics_tier` to its default unless `current_setting('alds.tier_writer', true) = 'on'`; on UPDATE it resets `new.analytics_tier`, `new.certified_at` and `new.certification_id` to the OLD values unless the GUC is on, so an unrelated update (the `storage_driver` flip, `upload_status`, validation linking) never wipes a certified tier (`current_user` is not used: inside a security-definer function it is the owner, and the service client must not be able to set the tier by a plain update either). Admins cannot set it; there is no manual promotion. `super_owner` may re-run or revoke with an audited reason. The tier is never derived from `package_validations`.
3. **D1.** Reliable analytics = KIVO cmi5 question analytics on `certified` versions. Completions, scores, official status, Report Card, CRM, learner-summary and journeys are never tier-filtered, and the admin UI says so once tiers appear. Uncertified packages launch normally (ADR 0004).

### 2. The model (D3): three legs, observation revokes

4. **Certified engine.** A reviewed allowlist in the repository keyed by `(engineDigest, rulesBundleHash, certifiedKinds)`, where `engineDigest` is the sha256 of the minified engine script block of a reference export from the hosted editor (possible once KIVO moves COURSE_CONFIG, the license header and the domain lock out of that block, ADR 0006). Unminified or test-mode builds fail the allowlist by construction.
5. **Static checks on stored bytes** (in the shared validation gate, after finalize, reading the stored prefix as `validate-stored.ts` does): U-rules (U1, U2, U3, U5, U7; U4 informational), engine digest in the allowlist, known `rulesBundleHash`, config kinds and settings against the certified set (slide kinds, bank question types, `attemptScoring`, weight-0 slides, `resumePrompt = never`, domain lock, third-party LRS, `gameLibrary`; any outside → `uncertified` with `kind_not_certified` or `config_not_certified`), the pools under-draw rule, declared language versus the slot, and a package digest (sha256 over sorted path + object sha256) stored with the certification. The in-editor self-check report hash in `alds-manifest.json` (ADR 0006) is verified to be present and consistent.
6. **Every answer validated at ingest** (P5) in four kind classes: keyed-and-scored (choice, true-false, multi-response, sequencing, matching, drag-match, drag-drop, fill-in, confidence, swipe: compare ids not positions, set semantics for multi and matching, ordered for sequencing, the full accepted-variant set for fill-in); scored-unkeyed (dialogue, game, image-id: success kept, no pattern check, excluded from "most common wrong answers"); completion-only (hotspot, interactive-timeline: excluded from hardest questions); unscored (feedback, slider, dial: `success` must be absent). Empty responses are allowed only with an explicit unanswered/timeout marker and are shown in a separate bucket, never as incorrect.
7. **Attribution.** Package-attributable findings (keyed mismatch, grammar, S2/S3/S4/S5, kind not certified, pool mismatch) count toward the version's revoke threshold; LMS-attributable findings (S1/S7 template, missing LaunchData extensions, LMS-caused relaunch ordering) mark the session unreliable and never revoke the version. A rules-bundle bump never revokes: stored bytes are re-checked under the new bundle and the row shows "certified (bundle N), re-check pending" until it passes or fails. Observation revokes; it never grants.

### 3. Rules as code (P3)

8. `lib/alds/types.ts` (blueprint §1.4 without `legacyIds` and the legacy-object-id extension) and `lib/alds/rules/` as a pure TypeScript module (no imports outside the folder, no DOM or Node APIs): S1–S9, U-rules, the session ordering checker, the R10 response grammar, canonical `contentHash`, script and lexical detection. Two entry points: `checkStatement` (shape, grammar, semantic) and `checkSession` (ordering, once-per-registration).
9. `scripts/build-alds-rules.mjs` compiles it with esbuild (added as a pinned devDependency; today it is only an indirect dependency; target es2020, no dynamic import) to an IIFE whose sha256, computed over the exact text normalised to LF/UTF-8 without BOM, is `rulesBundleHash`; `bundles.json` is the registry; golden fixtures (statements and mini-packages with expected pass/fail) run in the pr-checks `unit` job (ADR 0003 step 15). KIVO inlines the IIFE and re-hashes it at load (ADR 0006).

### 4. Migration `0099_alds_core.sql` (P4; numbering per ADR 0003)

10. `course_versions`: `alds_manifest jsonb`, `standard_version text`, `engine_version text`, `conformance_level smallint`, `analytics_tier text` with the check constraint above, `certified_at`, `certification_id`. `package_certifications`: one row per certification run (`course_version_id`, `status`, `rules_version`, `rules_bundle_hash`, `engine_digest`, `package_digest`, `static_report jsonb`, `coverage`, `requested_at`, `finished_at`, `revoked_by`, `revoke_reason`, finding ids); RLS enabled, deny-all policy, `revoke all from anon, authenticated`, literal `grant select, insert, update on public.package_certifications to service_role`. `course_attempts`: `served_language`, `launch_mode`, `is_preview boolean` with the blueprint's 6d backfill (attempts by super_owner, admin and data_analyst), `alds_ingested_at`. `learning_sessions` for cmi5/xAPI only (RLS, deny-all, service_role grant). `xapi_statements`: `session_id`, `standard_version`. `organizations.question_analytics_v2 boolean default false`. No `course_registrations`, no `served_version_id`, no launch RPC. The file also `create or replace`s the two delete-guard functions of 0098 so that a learner attempt is `is_preview = false` (ADR 0003 step 10). Functions follow the BLUEPRINT Conventions paragraph (`security invoker` unless stated, `set search_path`, explicit execute grants) and the grant rules of `docs/MIGRATIONS.md`; the file passes `scripts/check-migration-grants.mjs`.

### 8. P6 trigger

16. A sandbox Playwright certification runner on GitHub Actions (`workflow_dispatch` from finalize), the evaluate/enforce gateway (only security rules reject: S9 voids, binding, abandoned, conflicts) and registrations with `alds_open_attempt` are built only when a package uses a kind or setting outside the certified set, or a third-party Level 2 vendor appears.

### Risks and protections

| Risk | Protection |
|---|---|
| A forged or stale "certified" tier | security-definer writer, trigger, digest-bound bytes, allowlist in the repository |
| Certification runs with side effects on real tenants | no runtime certification in the LMS before P6; the canary uses its own org, no LRS, no webhook |
| Learner completions blocked by strict rules | nothing in this record rejects learner statements; uncertified packages launch and complete |
| Revoke storm on the first real package | per-kind contract, attribution, bundle-bump rule, thresholds on package-attributable findings only |
| v1 and v2 counting the same question twice | v1 excludes 2.0 rows; history note in the lens |

## Consequences

- "Certified" means certified package, not just certified engine: the config kinds and settings are checked against what the fixture proved.
- The first certified package needs: ADR 0006 release A and the 2.0 export, P3's bundle, 0099 on the environment, and the Guardian in the gate. SCORM and legacy stay `unverified` forever.
- Analysts see fewer, trustworthy rows plus an explicit count of what was excluded. Nothing changes for L&D's completion and score views.
- The blueprint's quarantine, resolution API, explainer and strict flip are not built before the first certified package.

## Alternatives considered

- Runtime certification through the real learner path: fires CRM webhooks and tenant-LRS forwards, pollutes the Report Card, and Browse mode suppresses `answered`.
- LMS-hosted browser runner at upload: no browser on Workers or Supabase edge; Cloud Run exists only as a staging trial.
- JSON Schema or CATAPULT as the source of truth: cannot express ordering, once-per-registration, the R10 grammar, canonical hashes or script ratios; CATAPULT stays an occasional external oracle.
- Manual tier promotion by admins: forgeable, and contradicts "observation revokes, never grants".
- Tier-filtering completions or the Report Card: breaks L&D and CRM views for the 17 active SCORM courses that will never be certified.

(a) Options rule (`types.ts`, `AldsCatalogueEntry.options`). Decided: every component id of the xAPI definition is an option of the catalogue entry with an oid `o1..oN`: `choices` (choice, sequencing), `scale` (likert), `source` and `target` (matching; a source and a target are two options with distinct oids), `steps` (performance); the kinds without components (true-false, fill-in, long-fill-in, numeric, other) carry `options: []`. The semantic check requires the definition's component ids to equal that set (SEM `option_set_mismatch`, `statement.ts`), U1 requires the oid form in the manifest (`package.ts`), and S3 `choice_id_not_oid` checks the form on `choices` in the statement. Reason: step 6 compares ids, not positions, so every id that can appear in a response or a pattern must resolve to a catalogue option with its label, for the S5 text comparison, for P5's "most common wrong answers" (which shows option text by oid) and for the key comparison across language variants of one qid; BLUEPRINT §1.1 defines `oid` as `o` + 1..N per qid, assigned by KIVO at option creation, never renumbered on reorder, retired on deletion, and this decision extends "option" to every component without changing that rule. Consequence for ADR 0006 step 10, the KIVO coordination point: the upgrade-on-open assigns oids to matching targets and performance steps as well as to choices and scale points, and freezes them on reorder. P5's `question_catalogue.options` jsonb (`[{oid,label}]`, BLUEPRINT §6.1) is unchanged, so no migration text changes. Routine tightening for bundle 2: `choice_id_not_oid` widened to every component list (today the set equality carries the other lists).

(b) `contentHash` over canonical key entries (`content-hash.ts`). Decided: the hash is taken over the canonical JSON with each `correct` entry rewritten to its canonical pattern text (`grammar.ts` `canonicalPatternText`: set-semantic ids and pairs sorted, one spelling of flags and numbers, items sorted when order does not matter) and the entries sorted; an entry that does not parse for the kind is hashed as written, and R10 reports it. The alternative, hashing `correct` as written and requiring KIVO to write keys in canonical order, is rejected: the hash's purpose (U3 at upload, SEM `content_hash_mismatch` at ingest, revision identity in P5) is "same content, same hash", and two keys the semantic check treats as the same key (a multi-select key saved in another order, accepted fill-in variants in another order, an explicit default flag) must not read as a content change that restarts a question's history. The golden fill-in vector q4 moved to `sha256:7153bf4b9b59903aee02a0ed542c4e192355c0782e989f38c2c8abd8704a7561` (its two accepted variants are each canonical but were not in sorted order); single-entry and already-sorted keys, which every other golden entry has (`alds-core.test.ts` asserts that every golden key entry is already canonical), hash as before. No manifest, statement or certification exists under the earlier definition (no 2.0 export, no 0100), so nothing is re-checked. Proof: `alds-core.test.ts` (ii), the independent reference hash, the "same key hashes the same, and nothing else" vectors and the canonical-text rows, and `alds-bundle.test.ts` running the moved vector against the registered IIFE. KIVO computes the hash with the inlined bundle, so the definition ships with bundle 1 and needs no other coordination.

(c) The engine reopen (`session.ts`, G3 `session_reopened`). ADR 0006 step 4 has release A finalise on `pagehide` and, when the learner interacts after a finalise without a relaunch (a page restored from the back-forward cache), open a new session: a new `initialized`, same registration. The AU cannot mint a session id: cmi5 §10.2.1 has the LMS generate the `sessionid` in the LaunchData `contextTemplate`, one per launch (ADR 0006 step 16), so the reopen necessarily reuses the sessionid, and under cmi5 §9.3 (one `initialized` per session, nothing after `terminated`; BLUEPRINT §5.2 G3) it is a deviation. Decided: the rules' treatment is right and is pinned so: an `initialized` after a `terminated` under the same sessionid is `session_reopened`, severity `warn`, package-attributed (the engine reopened; the LMS issued one sessionid per launch); the reopened segment is checked from scratch (its later `terminated` closes it; there is no `terminated_twice` code); R5 stays per registration, so a reopen never excuses a second AU-level `completed` or `passed` (`completed_twice`/`passed_twice`, error), which is the failure mode ADR 0006 step 5 forbids. Reasons: an error would turn every back-forward-cache restore into a package finding and, in P5, push certified packages toward revoke for behaviour the accepted engine contract prescribes; amending step 4 to forbid the reopen would leave a learner who continues after a restore untracked, the risk step 4 was written against; silence would hide a cmi5 deviation from reconciliation. Grading is untouched: the LMS derives the attempt from AU-level `completed`/`passed`/`failed` statements and from `terminated` only when the attempt is already complete (`lib/xapi/process-statement.ts`); a reopen changes no attempt field. Coordination point for KIVO: the reopen must reuse the LaunchData sessionid; a freshly minted one would fire S7 `session_id_changed`, an LMS-attributed error that marks the session unreliable (step 7). What the P4 certification gate does with it: nothing, by construction. The gate of step 5 is static, `checkPackage` over stored bytes and the self-check stamp; no statement exists at upload, so `session_reopened` can never set or change a tier. It is produced by `checkSession` in three places: the release-A fixture (ADR 0006 step 8), the golden canary (step 12) and P5 ingest and reconciliation (steps 13–15). Rule pinned for P5, which step 7 left implicit: only `error`-severity package-attributable findings count toward a version's revoke threshold; `warn` findings are recorded in `guardian_findings` with their severity and surfaced as counts, never counted toward revoke. Recommended fixture case for ADR 0006 step 8 (a test addition, not an edit): `pagehide` finalise → restore → answer → `completed`, asserting exactly one `session_reopened` warn and no error; "relaunch after Results" must produce no reopen, because the mock LMS issues a new sessionid; "beforeunload without unload → continue" produces no `terminated` and therefore no reopen.

(d) `authoringKind` relabelling (`package.ts` U1; `types.ts` `KEY_CLASS_BY_AUTHORING_KIND`). Decided: kept as built. A label whose class does not agree with the entry is a U1 error: `keyed_kind_without_key` (a keyed label with an empty `correct`), `keyed_kind_untyped` (a keyed label on `interactionType other`), `key_on_unkeyed_kind` (a scored-unkeyed, completion-only or unscored label with a key on a typed kind); an unknown label is `authoring_kind_unknown`, a warning, and the class is then derived from the key. Effect per step 5 and `docs/ARCHITECTURE.md` §5 (the §2 row): U-rule errors make the version `uncertified`; nothing here blocks an upload. Reason: the class decides what the semantic check compares (step 6); if a label could switch the key comparison off, relabelling a choice question `game` would make any `success` pass, which is the forgery the certified tier exists to exclude. The two open decisions in `types.ts`: (2) "may a typed kind with a non-empty key ever be scored-unkeyed or completion-only": no; a typed kind with a key is keyed, and a question that is genuinely unkeyed carries no `correct`; (1) the reviewed table of the xAPI kinds each authoring kind may use: deferred to P4, bundle 2, with the release-A every-kind fixture as its source (it cannot be checked against the engine before that fixture exists); the bundle-bump rule of step 7 applies (re-check, never revoke).

Additions to notes (b), (c), (e) and (k) (2026-10-19, later the same day, after the review of the integrated branch; same standing direction; 0100 is still applied nowhere):

- (b) `xapi_statements` gets its two columns in 0100 as plain columns (`session_id uuid`, `standard_version text`; step 10 names only the columns). The foreign key `session_id` → `learning_sessions(id) on delete set null` and the partial index on `session_id` move to 0101, the first writer (P5): there the index is built `create index concurrently` outside a transaction, then the constraint is added `not valid` and validated, in that order. Two reasons: a non-concurrent index build inside 0100 scans all of `xapi_statements` while the transaction holds `course_versions` and `course_attempts`; and the foreign key without the index would make every `learning_sessions` delete (an attempt, course or organisation delete, the staging CI purge) scan `xapi_statements` for the set-null action. `assert-0100.sql` asserts that neither exists after 0100.
- (c) The guard `alds_guard_version_tier()` protects eight columns, not four: with the setting off, an INSERT also forces `alds_manifest`, `standard_version` and `engine_version` to null and `conformance_level` to 1, and an UPDATE also keeps their OLD values. Reason: 0002's "admins insert versions" policy lets an org admin insert a `course_versions` row through PostgREST, and without this a planted `conformance_level = 2` with a hand-made `alds_manifest` would later read as Level 2 for P5 ingest (step 13). `assert-0100.sql` (2), (3) and (5b) cover the insert, a plain update and a service-role update. The writer's `coalesce(p_…, current)` on the four manifest columns is unchanged; whether a re-run that parses no manifest should clear a stored `alds_manifest` and `standard_version` is decided before P5 (step 13 trusts them).
- (e) Three records. The root: the gate checks the `alds-manifest.json` in the directory of the version's launch manifest (`cmi5.xml`, `tincan.xml` or `imsmanifest.xml` by the shortest-key rule; uploads keep a zip's top folder, so that directory may be one level down), or at the storage prefix when no launch manifest is listed (`rootAldsManifestKey()`); a copy elsewhere means `skipped: 'no_manifest'` with nothing written. The direct path keeps a zero-cost pre-filter (no `alds-manifest.json` at any depth) before the version read. The decision order: after the first `error` finding and before the allowlist leg, a package whose type is not `cmi5` is `uncertified` with `manifest_type_not_certifiable` (only KIVO cmi5 packages can be certified, D1, step 1); the reason codes the gate writes therefore also include `check_running` (the `pending` write) and `manifest_type_not_certifiable`, both in `lib/alds/tier.ts`. The position: in `finalizeDirectUpload` the gate runs last, after the forced restart of ADR 0008 step 7 / ADR 0011 and the update notification, so a slow gate or a worker killed inside it can never cost the restart or its report. The multipart path is unchanged tonight: the gate runs inside `uploadCoursePackage`, after `publishVersion()`, so the replace route's forced restart (`app/api/courses/[courseId]/packages/[packageId]/versions/route.ts`) and the upload route's notification run after it; moving it out of the library into the three routes is an open item for the architect before the flag is switched on anywhere.
