# 0010. The SCORM commit route writes only SCORM attempts

## Context

Verified on 2026-10-18 by reading the pushed branch `feat/adr-0008-part2-and-0009` at head 8d0f103 (the ADR 0008 C + D + ADR 0009 build, rebased onto `origin/main`; the 0099 file at 00b2a36; line numbers refer to that tree). No database was probed.

- **The route.** `app/api/scorm/[attemptId]/commit/route.ts` authenticates the session (lines 44–50), loads the caller's own attempt on the caller client with `.eq("id", attemptId).eq("user_id", user.id)` and the embed `course_versions(manifest_data)` (62–69), answers 404 for an unknown attempt and 410 for an abandoned one (84–89), derives `completion_status`, `success_status`, `status`, `score`, `progress_pct` and `completed_at` from the posted `cmi` object through `deriveCompletionStatus`, `deriveSuccessStatus`, `deriveAttemptStatus` and `deriveScore` (`lib/scorm/types.ts`; route lines 100–163), and writes through the service client (`updateAttemptFailSoft(svc, attemptId, update, { userId: user.id })`, line 174, ADR 0009 step 4). Nothing reads `course_versions.manifest_type`. A learner who holds an `in_progress` cmi5 or xAPI attempt can therefore POST `{ cmi: { "cmi.core.lesson_status": "passed", "cmi.core.score.raw": "100" }, finished: true }` to `/api/scorm/<that attempt>/commit` and the row becomes `passed`/`completed`, score 1, `completed_at` and `progress_pct = 100` set; because the route is the server, the completion then flows exactly as a real one: `classifyAttempt`, `gamification_record_activity`, `journey_record_completion`, the CRM completion webhook and the `asset_completion` email (lines 182 onward). Migration 0099 (ADR 0009) closes PostgREST writes and does not touch this: the route still writes as the server. The xAPI side has the controls this bypasses: statements are bound to the attempt by its launch token (`lib/xapi/auth.ts`) and only AU-level statements complete an attempt (`lib/xapi/process-statement.ts`, `isAboutAu`).
- **Who legitimately calls the route.** Only `app/[org]/(learner)/courses/[courseId]/launch/scorm-runtime.tsx`: the `LMSCommit`/`LMSFinish` flush (line 61) and the `beforeunload` beacon (line 132). The launch page renders `ScormRuntime` only when `v.manifest_type === "scorm12"` (`launch/page.tsx` line 902) and `Cmi5Runtime` otherwise; `cmi5-runtime.tsx` exposes no `window.API` shim (its line 9), so a cmi5 or xAPI package has no SCORM API to call. KIVO's SCORM export uploads as `scorm12`; KIVO's "LMS-provided xAPI" mode and Storyline/Captivate/iSpring tincan packages are `xapi` (0076) and use the xAPI routes. `course_versions.manifest_type ∈ scorm12 | cmi5 | xapi` (0002, widened by 0076); SCORM 2004 is not supported (`docs/ARCHITECTURE.md` §1), so "a SCORM attempt" is exactly `manifest_type = 'scorm12'`. Every test caller commits against a SCORM attempt: `tests/bot/lifecycle/helpers.ts scormCommit`, specs 00, 32, 34, 48, 53 and 55 (h), and `tests/load/learner-journey.js`, which parses its attempt id from the `ScormRuntime` prop in the launch payload. A non-2xx commit makes the runtime show its "error" state and return false; the next `LMSCommit` flushes the full CMI dictionary again (lines 57–79).
- **Why cmi5/xAPI attempts matter more.** SCORM trusts the browser-held CMI by design and stays unverified (ADR 0002 decision 1, ADR 0005); cmi5 is the ALDS certification path, where completion and question facts come from statements (ADR 0005, 0006). A cmi5 attempt completed through this route is a completion with zero AU-level statements; the only detector today is the ADR 0007 step 2 audit query for exactly that, run once before the v1.3.0 tag, not an ongoing check. Completions, Report Card, CRM and journeys are never tier-filtered (ADR 0005 D1), so the completion counts everywhere.
- **Left open by the build (ADR 0009 step 8).** 0099 section 3b's comment (lines 214–222 of the file) records that `mv_path_enrollment_status` keeps 0090's body with `any_attempt` over live attempts, and that its `completed` and `not_started` counts can both include one learner only if a completed or passed attempt were ever `abandoned`. No server path does that: every abandon is conditional on `status = 'in_progress'` (`language-preference/route.ts` 180–186, `versions/route.ts` 173–178, `lib/courses/direct-upload.ts` 666–671, `restart/route.ts` 198–204, `launch/page.tsx` 281–287 and 669–675), 0062's backfill abandoned `in_progress` duplicates only, and a completed or passed attempt leaves `in_progress`. Only a hand-run fix or a row forged through PostgREST before 0099 could produce the overlap. No app code reads the matview.

## Decision

### A. The rule

1. The SCORM commit route writes only attempts whose version is a SCORM runtime (`course_versions.manifest_type = 'scorm12'`). Any other attempt is refused before any derivation with 409 `{ error: "wrong_runtime", manifest_type }` and nothing is written. cmi5 and xAPI attempts are written at runtime only by the xAPI statements and State routes, bound by their launch token. No migration; `manifest_type` has existed since 0002.

### B. Steps

2. Caller inventory, read-only, recorded in the pull request before the change: every occurrence of `/api/scorm/` under `app/`, `lib/`, `components/`, `public/` and `tests/`; the launch page's runtime choice (`ScormRuntime` only for `scorm12`); the absence of a SCORM API shim in `cmi5-runtime.tsx`; the k6 script's attempt source. If any path that posts to the route for a non-`scorm12` attempt is found (a hybrid package, an engine mode not listed in Context), the executor stops and reports; the rule is not widened on the executor's own judgement.
3. `lib/scorm/types.ts` gains two pure exports next to the derive functions (the `lib/attempts/restart.ts` shape: the route does the I/O, the decision is unit-tested): `isScormRuntime(manifestType: string | null | undefined): boolean`, true only for the exact string `"scorm12"`; and `commitRuntimeRefusal(manifestType)` with three outcomes: `null` for `"scorm12"`; `{ status: 409, error: "wrong_runtime", manifest_type, message }` for any other non-empty string (a known, non-SCORM runtime); `{ status: 503, error: "attempt_unreadable", message }` for `null`, `undefined` or `""` (the type could not be established, so nothing may be written).
4. Route change in `app/api/scorm/[attemptId]/commit/route.ts`: the attempt read selects `course_versions(manifest_data, manifest_type)`. The read has three outcomes, each spelled out so none is inferred: (i) `readErr` → 503 `{ error: "attempt_unreadable" }`, nothing written, replacing today's blind write (lines 70–73); (ii) no attempt row and no error → 404 `attempt_not_found` (unchanged); (iii) an attempt row → 410 if `abandoned` (unchanged), then `commitRuntimeRefusal(a.course_versions?.manifest_type)`: 409 for a known non-SCORM type, 503 when the embed is null or the type empty (today that case writes), `null` for `scorm12` → derive and write as today. Order of answers: 401, 400 (invalid JSON), 503 (i), 404, 410, 503 or 409 (iii), then derive and write. On a 503 the runtime shows "error" and its next `LMSCommit` flushes the full CMI dictionary again, so no in-memory state is lost. Response shape, non-downgrade rules, the webhook, XP and journey calls are unchanged for `scorm12` attempts. The route's doc comment states the rule.
5. Unit test `tests/unit/scorm-commit-runtime.test.ts` (picked up by `npm run test:unit`, the pr-checks `unit` job): `isScormRuntime` is true for `"scorm12"` and false for `"cmi5"`, `"xapi"`, `null`, `undefined`, `""` and `"SCORM12"`; `commitRuntimeRefusal` returns `null` for `"scorm12"`, the 409 shape (with the type echoed) for `"cmi5"`, `"xapi"` and `"SCORM12"`, and the 503 shape for `null`, `undefined` and `""`. `tests/unit/attempt-write-sites.test.ts` keeps passing (the write site and its receiver are unchanged).
6. Lifecycle, on qa data only: spec `55-attempt-row-guard` gains case (k), after (h) and before (e, part 2) (the revive stays last, as the spec's binding rules require), in every branch. Seed addition: `tests/bot/fixtures/xapi.zip` is uploaded as a fourth course of the learner's organisation and, unlike the forge target of (c), the learner launches it, so an xAPI attempt exists. Case (k): the learner POSTs a passing SCORM commit (`cmi.core.lesson_status = passed`, `cmi.core.score.raw = 100`, `finished: true`) against the fresh cmi5 attempt of (h), targeted by the attempt id (h) recorded (after (e, part 1)'s force restart that is the attempt on the new version, not the abandoned one) → 409 `wrong_runtime`, and the service-role re-read shows the row unchanged (`in_progress`, `completion_status in_progress`, `success_status unknown`, `score null`, `completed_at null`, `completion_webhook_at null`); the same commit against the xAPI attempt → 409, unchanged; the SCORM commit of (h) still answers 200. Specs 00, 32, 34, 48 and 53 stay green (SCORM attempts only). Spec 48's existing cases keep proving 404 for an unknown attempt and 410 for an abandoned one.

### C. The open point of ADR 0009 step 8 (decision 2 below)

7. `mv_path_enrollment_status` stays as 0099 section 3b writes it, with its comment as the record of the overlap condition. The executor adds one read-only query to the 0099 header's after-apply list: `select count(*) from public.course_attempts where status = 'abandoned' and (completion_status = 'completed' or success_status = 'passed')`. It runs at exactly two moments, after the staging apply of 0099 and after the production apply of 0099 (which follows v1.3.0, ADR 0009 step 10), and both results are recorded under this record's acceptance note. The expected result is 0 at both (production has no attempt rows). A non-zero count goes to `ops/INCIDENT_LEDGER.md` with ids only and changes nothing (ADR 0002 decision 4); only then is the body tightened, in the next migration window (0100). With two zero results the point is closed.

### Risks and protections

| Risk | Protection |
|---|---|
| Learners: a legitimate SCORM commit is refused | `ScormRuntime` is rendered only for `scorm12` versions, so every legitimate commit targets a `scorm12` attempt; step 2's inventory; specs 00, 32, 34, 48, 53, 55 (h) and the k6 script prove 200 |
| Learners: the fail-closed read loses a commit | the runtime keeps the full CMI dictionary in memory and flushes it on the next `LMSCommit`; the unload beacon was already fire-and-forget; a 503 replaces a write made without knowing the attempt's type or status |
| Grading: a cmi5/xAPI attempt completed without statements | closed by the 409; existing such rows (if any) are history and are listed by the ADR 0007 step 2 audit, never rewritten |
| Grading: a SCORM derivation changes | none of the derive functions or the non-downgrade rules change; spec 55 (h), spec 00 |
| Privacy | the 409 body carries the `manifest_type` string only; reads are unchanged |
| Existing records | no row is touched; no migration; the matview keeps its pinned body |

## Consequences

- A runtime write reaches an attempt only through the route built for that attempt's runtime: SCORM through the commit route, cmi5 and xAPI through the token-bound xAPI routes. ADR 0009's "written only by the server" gains "and only by the right server path".
- Code only; it can ship in the ADR 0008/0009 build or the next one, on any environment in either order with 0099.
- The fail-closed read removes the one remaining blind write of the commit route.
- The matview overlap stays a documented condition no server path produces, checked once per environment after the apply.

## Alternatives considered

- A SCORM session token binding the commit route to the launch, like the xAPI token: cut with SCORM journaling by ADR 0002 decision 4 and ADR 0006 (§4, §5); the type check closes the cross-runtime hole without it, and SCORM's own CMI stays browser-trusted either way.
- Refusing cmi5 only and allowing xAPI: xAPI attempts are statement-driven too and have the same token binding; both are refused.
- A database trigger comparing the writer to the version type: the database cannot tell which route wrote; ADR 0009 decision 6 declined a trigger on this table.
- Folding the rule into ADR 0009: that record is accepted and scoped to PostgREST writes; a separate short record keeps its acceptance intact.
- Tightening `mv_path_enrollment_status` in 0099 now (for example `not_started` only when `completed_courses = 0`): the file is written, pinned by ADR 0009 step 8 and about to be applied; reopening it for a condition no server path produces costs a second review for no observed row.

## Decisions requested from the owner

1. Adopt the rule and steps 1–6, including the fail-closed 503 when the attempt or its version type cannot be read (step 4). Recommended: yes; it closes the only route-level path by which a cmi5 or xAPI attempt can be completed without statements, and it changes nothing for SCORM learners. Decided (owner, 2026-10-18): yes, in the owner's words: "1. YES — The SCORM save route must reject non-SCORM attempts and must not save anything if the attempt type cannot be verified." Both halves of step 4 are accepted as written: the 409 for a known non-SCORM type and the 503 that writes nothing when the type cannot be established.
2. The `mv_path_enrollment_status` overlap of ADR 0009 step 8: accept it as documented in 0099 section 3b's comment, with the read-only count of step 7 at its two moments (after the staging apply, after the production apply), and tighten the body in the next migration window only if either count is non-zero. Recommended: accept as documented; no server path abandons a completed attempt, no app code reads the matview, 0099 is not reopened, and two zero counts close the point. Decided (owner, 2026-10-18): yes, in the owner's words: "2. YES — Accept the documented database-summary limitation for now. After SQL 0099 is applied, run the read-only check and report any issue found before making further changes." Step 7 as written: the count runs after each 0099 apply, staging first and then production; each result is recorded under this note; a non-zero result is reported to the owner, with ids only in `ops/INCIDENT_LEDGER.md`, before any change is made anywhere, and the body is tightened only on the owner's go in the next migration window.
