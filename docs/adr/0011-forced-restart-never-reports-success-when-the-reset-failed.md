## Decision

### A. The rule

1. A forced restart (replace-package with `mode = force_restart`, on either upload path) reports success only when every in-progress attempt it selected on the package's older versions is, by the database's own answers, no longer in progress. It reports a genuine zero ("No learners were in progress") only when the selection read succeeded and found none. A failed read, a failed update, a read that answers neither rows nor an error, and any selected attempt still in progress after the run are failures: the answer is a non-2xx status whose body says the new version is published and the reset is not, with the counts, and points the admin at "Restart learners on this version" (ADR 0008 A, `versions/[versionId]/restart`, which checks its errors and has a dry run) as the retry. The publish is never rolled back or hidden; nothing beyond today's selection is ever touched.

### B. Steps

2. **One implementation for both paths.** New file `lib/attempts/force-restart.ts` in the existing `lib/attempts/` module, next to `restart.ts` and `abandon.ts` (no new folder, no module-boundary change). Two parts in one file, the `restart.ts`/`abandon.ts` shape: a pure part with no `next/*` import and no runtime Supabase import (`import type { SupabaseClient }` only, as `abandon.ts` does, so `tsx` unit tests load it): `type ForceRestartOutcome = { status: "ok" | "failed"; expected: number | null; restarted: number; resolved: number; unresolved: number; unresolved_version_ids: string[] | null; message: string }`, `classifyForceRestart(input)` (step 4) and `forceRestartMessage(outcome)` (step 9's wording, so both routes and the unit test share one text); and an I/O part `forceRestartOlderVersions(svc: SupabaseClient, args: { packageId: string; newVersionId: string }): Promise<ForceRestartOutcome & { restartedIds: string[]; tokensExpired: boolean }>` (step 3). The multipart route's block (lines 163–193) and `abandonOldAttempts` (707–725) are replaced by one call each; `abandonOldAttempts` is deleted.
3. **Reads and the update, inside `forceRestartOlderVersions`, every answer checked.** (R1) `course_versions.select("id").eq("package_id", packageId)`: an `error`, a `data == null` answer with no error, or an answer that does not contain `newVersionId` (the version just published belongs to this package, so a list without it is a wrong or truncated read, never "no older versions") is a selection failure; otherwise the ids minus `newVersionId` are the older versions; an empty remainder is a genuine zero and nothing else is queried. (R2) the pre-selection: `course_attempts.select("id, course_version_id").in("course_version_id", <chunk of 150 older ids>).eq("status", "in_progress")`, paged at 1000 rows ordered by `id` (the `lib/db/chunked.ts` house rules, written locally until decision 2 is taken, because `fetchAll` cannot yet report an empty answer); an `error` or a `data == null` page is a selection failure; `expected` is the number of distinct ids found (grant retakes included, because the selection includes them). (U) for each chunk of 150 selected ids: `.update({ status: "abandoned" }).in("id", chunk).in("course_version_id", <the distinct version ids of that chunk's rows>).eq("status", "in_progress").select("id")`; stop at the first error, keeping the ids returned so far as `restartedIds` (an update that returns `data == null` without an error is an update failure). The condition is the same one every abandon path uses (ADR 0010 Context, fourth bullet): a completion, a language-switch reset or another admin's restart that lands first wins, and no attempt outside the selection can be touched. (R3) when `restartedIds.length < expected` or the update failed: re-read the shortfall ids in chunks of 150, `select("id, status, course_version_id")`; an `error` or `data == null` is a re-read failure. Then, exactly as today and only for `restartedIds`: `expireLaunchTokens(svc, restartedIds)` (`lib/attempts/abandon.ts`; a failure is logged and surfaces as `tokensExpired: false`, informational, never a failure of the restart, mirroring the per-version route's `tokens_expired: false`), and `enqueueAbandonedStatements(svc, restartedIds)` (`lib/lrs/abandoned.ts`, fail-soft, unchanged). No audit row is added (unchanged; see Alternatives).
4. **Classification (`classifyForceRestart`), pinned, not inferred.** Input: the R1/R2 outcome (`selectionError` or the selected `{ id, course_version_id }` rows), `updateError`, `restartedIds`, and the R3 outcome (`rereadError` or the re-read rows). Rules, in order: (a) selection failed (an R1 or R2 error, a `data == null` answer, or an R1 answer without `newVersionId`) → `failed`, `expected: null`, `restarted: 0`, `unresolved_version_ids: null`; (b) selection succeeded with no rows → `ok`, `expected: 0`, `restarted: 0` (the genuine zero); (c) every selected id is in `restartedIds` and the update did not fail → `ok`, `restarted = expected`; (d) otherwise, for each selected id not in `restartedIds`: a re-read row whose `status` is `completed`, `passed`, `failed` or `abandoned` (the only values the 0043 constraint allows besides `in_progress`) is `resolved` (a legitimate transition landed first); a row still `in_progress`, a row missing from the re-read, or a failed re-read is `unresolved` (fail-closed: a missing row's only producer today is the §9 qa purge, never the app, and "could not confirm" is reported as a failure, not as success); (e) `unresolved = 0` and the update did not fail → `ok` with `restarted`, `resolved` and `expected` as counted; (f) `unresolved > 0`, or the update failed → `failed` with the counts and `unresolved_version_ids` = the distinct `course_version_id` of the unresolved ids, taken from the selection rows (the re-read may be missing), sorted. An id returned by the update that was not in the selection cannot happen with an id-bound update; if it does, it is counted in `restarted` and logged, never an error. `expected`, `restarted`, `resolved` and `unresolved` are counts; attempt and user ids never appear in a force-restart response or message (the per-version dry run is the per-attempt list, ADR 0008 step 4).

### Risks and protections

| Risk | Protection |
|---|---|
| Learners: an attempt is reset that was not reset before | none can be: the selection (older versions of the package, `status = 'in_progress'`) and the conditional update are unchanged; the re-read of step 3 (R3) is a `select`; step 11 (iii) proves the update's conditions and that a failed read issues no update |
| Learners: a legitimate completion that lands during the run is undone or reported as a failure | the update is conditional on `status = 'in_progress'`, so the completion wins (ADR 0008 step 3, ADR 0010 Context); the re-read classifies it as `resolved`, and the run is `ok` (step 4 d–e) |
| Grading: an abandoned attempt counts, or a completion is lost | nothing about `abandoned` changes; ADR 0004 steps 10–11 and the 0099 view/matview corrections stand; no derivation, score or official-attempt rule is touched |
| Grading or records: the publish is rolled back because the reset failed | never: the response says `published: true` with `version_id`; the browser does not abort on that body (step 7), and `abortDirectUpload` refuses a `ready` row in any case |
| Privacy: the failure message or body leaks identities | counts and version ids only; no attempt ids, user ids, names or emails in any force-restart response, message or banner (step 4) |
| Existing records: history rewritten or deleted | no row other than the selected in-progress attempts is written, exactly as today; no migration |
| An un-updated client (API caller, old browser tab) reads the new failure | it sees a 500 with a readable `error`, never a success; the success shape keeps every existing field |
| Spec 34 hides a failure as a skip | step 10 removes the skip |
| A genuine zero is misreported as a failure (false alarm) | only when a read answers neither rows nor an error, which is a failed read by definition; a false alarm costs the admin one dry run of the per-version restart, which then says "No in-progress attempts" |
| Token expiry fails after a successful reset | informational `tokens_expired: false`, as the per-version route; runtime writes to an abandoned attempt answer 410 regardless of tokens (`lib/attempts/abandon.ts`) |
| Decision 2 changes a shared helper | Proposed, separate; every caller listed before the change; thrown errors already handled by the callers' `try/catch` |

## Consequences

- A forced restart has three honest outcomes, told apart by the database's own answers: reset (with counts), nobody in progress, and failed-with-the-new-version-published. The admin reads which one happened in the Library and an API caller reads it from the status code.
- Both upload paths run one implementation, so they cannot drift again; the write-sites unit test pins the one write site and its callers.
- ADR 0008 step 7 is amended on error handling and reporting only; the per-version restart stays the one-version tool and becomes the documented retry for a failed forced restart.
- The spec-level skip that could hide a real failure is gone; a failed forced restart now fails spec 34, 48 or 55.
- Code only; nothing changes on an environment until the build is deployed there; production has no attempt rows as of 2026-10-17, so nothing is exposed there before v1.3.0.
- If decision 2 is taken, every reader built on `fetchAll`/`fetchByIds` stops reading an empty answer as zero rows.

## Alternatives considered

- Rolling back the publish when the reset fails (repoint `course_packages.current_version_id` to the previous version): rejected. The upload succeeded and learners may already be launching the new version; a rollback would hide a good upload behind a reporting problem, and the course default rule of ADR 0008 B would then have to be unwound too. The honest answer is "published, reset failed, retry per version".
- Retrying the reset silently inside the route (loop until the read succeeds): rejected. A retry that eventually gives up still has to report; a retry that succeeds hides a flaky database from the admin; the per-version route with its dry run is the deliberate retry.
- 207 Multi-Status, or 200 with a `restart_failed` flag: rejected. Both are 2xx, which every existing caller treats as success (`ok()`, `finRes.ok`), so any client not updated in the same build would report success on a failed reset, the exact outcome the owner forbids. 500 with `published: true` is the one shape no existing client takes for success, and it is the sibling route's precedent.
- Fixing each path in place with duplicated logic: rejected; the two blocks already drifted (one checks its update error, the other nothing), and the classification has eight cases that must stay identical.
- Excluding grant retakes from the force-restart selection, as the per-version route does: not part of this decision; ADR 0008 step 7 kept the two paths' selection as it was, and changing what is reset is a different decision from reporting it honestly. Recorded here so the question is not lost.
- An audit row (`platform_audit_log`) or an Attention Center item for a failed forced restart: deferred. The admin sees the failure immediately and the per-version dry run lists what is left; an Attention provider for "in-progress attempts on non-current versions of an active package" would catch this and other causes and can be its own short record.
- Treating a missing row on the re-read as resolved (it cannot be in progress): rejected in favour of fail-closed reporting; the only known deleter is the qa purge, and "could not confirm" must never read as success.
