# 0018. Patch the bundled react-dom's hydration replay (React #418 at the learner layout's `<main>`) at bundle time, through the ADR 0013 loader

Status: Accepted (owner, 2026-11-05): Option A, React's upstream fix for the replay (the cursor restore in the replay's `case 5`, and `Forked` kept by `resetWorkInProgress`) applied to the bundled react-dom at bundle time through the webpack loader ADR 0013 already registers, with ADR 0013's fail-the-build safeguard kept as written; the owner's words are recorded under "Decisions requested from the owner", as ADR 0013 does, not by rewriting this record. The order against the next production tag stays open there. Code only, no migration, no API or schema change. Branch `fix/launch-hydration-418` off `origin/main`; nothing is pushed, deployed or tagged without the owner.

## Context

- **The symptom.** On a hard load of a learner launch page the browser reports `Minified React error #418` (`args[]=HTML`) as a page error about 1.7 s in. Lifecycle spec 57 asserts `expect(pageErrors, "no page errors").toEqual([])` (`tests/bot/lifecycle/57-kivo-release-a-xapi.spec.ts:384`) and fails on it; spec 56 (cmi5) records page errors into its event log (`:1064`) and has shown the same error once. On the staging deployment of `main` at e43d1ef (Next 15.5.29) it fired naturally on 4 of 154 launches with page-error capture: 3 xAPI and 1 cmi5, every one the first launch in a fresh browser context (a revisit has the chunk cached), three of them within nine minutes and that cluster unexplained. All 4 were among the first 30 of those launches; the other 124, a dedicated night of natural runs (fresh courses, an instrumented error chunk, 4x page CPU, 70 new learners, the test machine at full CPU), gave 0. The deployments before it gave 0 of 79. Locally: `next dev` 0 of 12, a production build 0 of 10, the same build with random delays on metadata, layout, page and SSR 1 of 33.
- **The node and the cause.** The node is `<main>` in `app/[org]/(learner)/layout.tsx:293-295`. Server and client agree, so this is not a markup mismatch; React re-claims an element it has already hydrated. Next renders a layout's `{children}` as its `LayoutRouter` with the segment's `error.tsx` as the `error` prop (`node_modules/next/dist/server/app-render/create-component-tree.js`, `error: ErrorComponent`), and `app/[org]/(learner)/error.tsx` is a client component, so `<main>`'s Flight row carries a client reference to the error boundary's chunk; on a hard load before that chunk arrives the Flight client gives `<main>` a lazy child blocked on it (the diagnosis's reading of the bundled Flight client). Hydrating `<main>`, `beginWork` claims the DOM element, sets `hydrationParentFiber` to `<main>` and moves `nextHydratableInstance` to its first child (`react-dom-client.production.js:7606-7622`); reconciling the lazy child then throws (`handleThrow` `:10930`, reason 3, then 7 at `:11102`). If the chunk resolves inside the same scheduler task, `isThenableResolved` sends the fiber to `replaySuspendedUnitOfWork` (`:11108-11112`), whose `case 5` only resets hooks and falls into the default (`:11211-11217`): `beginWork` runs on `<main>` a second time with the cursor still on `<main>`'s first child (the `<!--$-->` comment), `canHydrateInstance` (`:13947`) returns null and `throwOnHydrationMismatch` (`:2739`) raises #418. If the chunk is still pending at that moment React unwinds and retries later with no error; if it was already loaded nothing throws. The window is one scheduler task against the chunk's arrival, only on a hard load with the chunk not in the browser cache; soft navigation does not hydrate. Lines are the bundled `node_modules/next/dist/compiled/react-dom/cjs/react-dom-client.production.js` (`19.2.0-canary-0bdb9206-20250818`, byte-identical in Next 15.5.18 and 15.5.29); in the production and profiling builds `case 5` is in `replaySuspendedUnitOfWork`, in the two development builds it is in `replayBeginWork`, which `replaySuspendedUnitOfWork` calls. The broken form occurs exactly once in each of the four client builds and the fixed form in none (measured by the unit test).
- **Upstream.** Two React commits make the fix. facebook/react#35494 (c18662405c, 2026-01-13, fixing #35210): the replay's `case 5` restores the hydration cursor when the replayed fiber is `hydrationParentFiber` (`popToNextHostParent(fiber)`, then `nextHydratableInstance = fiber.stateNode` while hydrating, or re-entering hydration otherwise). facebook/react#35518 (f0fbb0d199, 2026-01-16): `Forked` joins `StaticMask`, because a replay stripped it and the replayed fiber lost its useId slot. Both, and ADR 0013's ping fix, are in the canary Next 16.4.5 bundles (`19.3.0-canary-278794d7-20261002`). They arrived separately, read as data from the packages: Next 16.0.11 and 16.1.7 have neither replay commit; 16.2.0 and 16.2.12 have both and not the ping fix; 16.3.0, 16.3.8 and 16.4.5 have all three. No Next read carries the restore without the flag. Not fixed in any 15.5.x; 15.5.29 is the newest. The fixed text in decision 1 was read from Next 16.4.5's package for this record: from `case 5:` to `default:`, the output of this transform on each of the four 15.5.29 builds is byte-identical to the same build of 16.4.5.
- **Why the restore needs the second commit.** `placeChild` sets `Forked` (bit 20) on a fiber it mounts (`:3339`), and `beginWork` reads it only on a fiber with no alternate, pushing that fiber's useId slot (`:7369-7371`). A replay's `unwindInterruptedWork` pops the slot, `resetWorkInProgress` strips the flag with its mask 65011714 (`:2494`), and `beginWork` then pushes nothing. Before the restore a replayed hydrating `<main>` failed at once with #418 and client-rendered, so this never showed there. Fibers that replay through the same path with no cursor to restore (a keyed Fragment, a context provider, a class, `<body>`) already lose the slot on e43d1ef with no error, and this hunk closes those too (measured in Chromium on react-dom alone). With the restore that path succeeds, and under a host with siblings useId then returns values that differ from the ids in the DOM, with no error (proof below). Reach today: the repository's only `useId` is `RestartDialog` (`app/[org]/(admin)/library/[courseId]/version-actions.tsx:455`), rendered after a click, and no other built client chunk calls it, so no page hydrates one; a future one under a layout host would diverge silently on this path.

## Decision

1. **Add two hunks to the ADR 0013 loader.** `scripts/react-dom-ping-fix.cjs` (name kept: `next.config.ts` registers it and `docs/ARCHITECTURE.md` cites it) gains `patchReplay(src)` and `patchForked(src)`, exported beside `patchSource`. `patchReplay`, broken form: `case 5:` whitespace `resetHooksOnUnwind(<v>);` whitespace `default:`, where `<v>` is `next` in the production and profiling builds and `unitOfWork` in the development builds (both read in the installed files). Fixed form: `fiber === hydrationParentFiber && (isHydrating ? (popToNextHostParent(`. The replacement inserts upstream's text between `resetHooksOnUnwind(<v>);` and `default:`, keeping the variable name and the file's indentation:
   ```js
   var fiber = <v>;
   fiber === hydrationParentFiber &&
     (isHydrating
       ? (popToNextHostParent(fiber),
         5 === fiber.tag &&
           null != fiber.stateNode &&
           (nextHydratableInstance = fiber.stateNode))
       : (popToNextHostParent(fiber), (isHydrating = !0)));
   ```
   `patchForked` reads `resetWorkInProgress`'s first statement, `workInProgress.flags &= <n>;`, which must occur exactly once. A mask holding bit 20 is fixed; 65011714 becomes 66060290, which is 15.5's mask with bit 20 added and nothing else; any other mask refuses. Next 16.4.5's own mask (1206910978) is not copied: it also holds `PortalStatic` (bit 26) and `ViewTransitionStaticParent` (bit 30), which 15.5 lacks, and bit 26 is `PlacementDEV` in 15.5's numbering. The loader runs `patchSource`, `patchReplay` and `patchForked` on the same source; each answers `patched`, `already-fixed` or `refused` on its own.
2. **Fail loud, per hunk.** As ADR 0013 decision 2: a source with the fixed replay form exactly once and the broken form never passes through unchanged; otherwise the broken form must occur exactly once; zero, several or mixed matches throw, and the message names the file, the hunk and the record that owns it (ADR 0013 for the ping hunk, this record for the other two). Measured: each of the four Next 15.5.29 builds patched once by each hunk and parses; a second pass answers `already-fixed`; all four of Next 16.4.5's builds answer `already-fixed` on all three hunks and pass through unchanged. With the replay pattern broken on purpose, and again with the mask hunk refusing the build's mask, `next build` exits 1 naming the file, the hunk and ADR 0018.
3. **The unit test.** `tests/unit/react-dom-ping-fix.test.ts` adds: replay and mask fixtures in both spellings patched once to the exact text, a second pass `already-fixed`, refusals on zero, two and mixed forms, the loader throwing on a refused replay or mask source naming the file and ADR 0018, `next.config.ts` registering the loader on the path rule, and the installed-file check now requiring `patched` from all three hunks on all four files, the names the restore uses declared in each file, bit 20 being the flag `placeChild` writes and `beginWork` reads, the mask becoming 66060290 once with the file's other static-mask sites left alone, and the loader's output parsing. Measured with 71 mutations of the loader and of the rule in `next.config.ts`: 67 killed, and 4 equivalent ones, which survive as they should. The `next.config.ts` comment names both records. `docs/ARCHITECTURE.md` §1, §2 and §9 carry the pointer.
4. **Exit condition.** Both fixes are in the canary Next 16.4.5 bundles; the replay fix arrived by Next 16.2.0 and the ping fix by 16.3.0. So a Next upgrade to 16.3.0 or later flips all three hunks to `already-fixed` and fails the installed-file check: remove the loader from `next.config.ts`, the script and the test, and mark ADR 0013 and this record superseded. A Next whose bundled react-dom carries one record's fix and not the other's (16.2.x) fails the check on that record's hunks only: remove those hunks and supersede that record only. On 16.0.11 and 16.1.7 the mask is another value without bit 20 (132120578), so `patchForked` refuses and the build stops for a person to read. 16.0.0 to 16.0.2 still carry 65011714, so all three hunks patch as on 15.5 and nothing stops; 16.0.3 is the first read with 132120578. Measured on copies: Next 16.3.0's and 16.4.5's four builds fail 16 lines, the three hunks and the mask's value on each; 16.2.0's fail 12, this record's two hunks and the mask's value on each; 16.1.7's stop the test at the refused mask; 15.5.29's with the mask fixed fail 4 lines, that hunk on each.
5. **The layouts are unchanged.** `(learner)/layout.tsx`'s `<main>` and `(admin)/layout.tsx` are not edited under A; the keyed Fragment stays recorded as the fallback (Alternatives considered).
6. **Proof, in order.** `npm run test:unit`; a local production build under forced timing, expecting fires without the hunk and 0 with it (both done, Context); a useId comparison on the learner and admin shapes (done, Context); then, after an owner-run staging deploy, spec 57 with its `:384` assertion unchanged (it stays the detector), spec 56's in-force group with its captured page errors read, and the forced and late-cmi5 checks regenerated for the new chunk, all expecting 0 and `/api/xapi/fetch` 200 only. Until the branch merges, a spec 57 failure whose only page error is #418 is this item.
7. **Branch and gates.** `fix/launch-hydration-418` off `origin/main`, not on the PR 1b work branch; its diff is the three files above, this record, a dated pointer under ADR 0013 and the pointers in `docs/ARCHITECTURE.md`. No push without the owner; no production action; its order against the next production tag is decision 2 below.

## Limits

- webpack only, as ADR 0013: under `--turbopack` (unused today) no hunk runs.
- The repository form has been built and run on a local production build only. Every forced run and spec run in this record used e43d1ef's code; after the branch moved onto later `main` the builds and their chunk reads were repeated and those runs were not, so the reruns of decision 6 are their proof on this code. On the staging deployment the restore alone was verified, by patching the served chunk inside the test browser; the `Forked` hunk has run on no deployment, and no deployment carries the fix yet. Cloudflare has run neither: the only proof there is a local read of `cf:build`'s output.
- A local `.next/cache` keeps the old module if the loader's bytes change with its mtime unchanged; the deploy builds start with no cache.
- The four natural staging fires were not probed; they are tied to `<main>` by the same message, the same timing signature in the request logs (launch chunk to iframe request 50–115 ms against a median of 9) and the forced runs on the same build. That signature also appears on five launches with no recorded error, so it is not a detector; spec 57 is.
- Forcing widens a one-task window to "always": it shows the path and the fix and says nothing about natural frequency. The specs' passes on the local build say nothing about it either, at a natural rate this low.
- `next dev` never fired naturally, so there is no development-mode diff text. The development build's spelling of the two hunks is covered by the fixture, the installed-file check and one `next dev` compile read back from its client chunk; it was not run in a browser.
- The admin layout was forced on two pages, and the admin page's re-render was read from the page's text and one `<main>`, not driven further. SCORM's late form was read from the boot count and the requests in a 9 s window. The late cmi5 loss was read from the first refused statement. Every late form and every admin fire here is forced only.
- The useId divergence was read on a test-only component and on react-dom alone. No repository page hydrates a `useId`, and no replay has been seen with one under it outside this forcing.
- Only the replay's `case 5` and `resetWorkInProgress`'s mask are backported. Against Next 16.4.5's production build, `popToNextHostParent`, `popHydrationState`, `canHydrateInstance`, `throwOnHydrationMismatch`, `isThenableResolved`, `resetHooksOnUnwind`, `getNextHydratable`, `pushTreeId`, `pushTreeFork` and `popTreeContext` are unchanged, and `unwindInterruptedWork` differs only in a SuspenseList helper. `resetWorkInProgress` differs in its mask by `Forked`, which #35518 made static; this record backports that for the replay, and the rest of the mask concerns features 15.5 lacks. #35518 changed `StaticMask` as a whole, so 16.4.5 holds the bit at every site of that mask: `createWorkInProgress`, `resetWorkInProgress`, the two bubbling sites, the Suspense fallback path, and the development builds' static-flag check. Here only `resetWorkInProgress` changes. `beginWork` reads the flag only on a fiber with no alternate, and that is the one site of the mask such a fiber passes through: `createWorkInProgress`'s result always has an alternate, and the others write `subtreeFlags`, whose bit 20 nothing reads. The check in the development builds keeps 15.5's mask, so it does not compare the bit. The react-dom-experimental copy and the app's own `node_modules/react-dom` are not patched (ADR 0013 Limits): the `framework` chunk, which serves only Next's built-in error fallback, keeps all three broken forms. Next 16.4.5's react-dom was read as text and never run: the equality with upstream rests on the identical function text above and on bit 20 having one reader.

## Alternatives considered

- **B. Keyed Fragments, no React patch.** `<Fragment key="route">{children}</Fragment>` inside `<main>` in `(learner)/layout.tsx` and around `{children}` in `(admin)/layout.tsx`. A keyed Fragment is a real fiber (tag 7), so the lazy child suspends on it rather than on the host and the replay never re-claims `<main>`. Verified under forced timing on the same local build as the without-the-fix runs, with no React patch: learner launch 0 of 6, late cmi5 0 of 3 with `/api/xapi/fetch` 200 only, admin `reports` and `users/new` 0 of 6, each suspension held on the Fragment. It leaves any other host whose Flight child takes a client reference as a prop, and it puts a workaround for React's bug into app code where nothing explains it. In the admin shape the keyed Fragment has a sibling, so its replay strips `Forked` and useId below it differs from the server's: measured in Chromium on e43d1ef's react-dom (proof above). Not chosen; kept as the fallback.
- **Upgrade to Next 16.x.** The clean fix for both records; a major upgrade (AGENTS.md; the OpenNext and Cloud Run builds to check) and a separate plan. It remains the way to retire this record and ADR 0013.
- **Patch `node_modules`** (postinstall or patch-package): rejected for ADR 0013's reasons (mutates installed files; webpack's persistent cache keeps serving the old chunk).
- **Tolerate #418 in spec 57** (filter the message, or retry the launch): hides a real learner-facing bug and the late form; rejected.
- **Do nothing until Next 16.** The natural harm seen is one iframe boot, but the late form, shown only under forced timing, is silent for the learner on cmi5; rejected as the recommendation.
