## Decision

### A. The rule

1. **An AU `completed` that carries no result does not fire the completion webhook by itself.** The webhook for an official cmi5 or xAPI attempt fires when the attempt is complete and official and one of three things is true in the request: its pass/fail became known or changed in this request (`success_status` went from `unknown` to `passed` or `failed`, or from `failed` to `passed`); the statement that completed it in this request carried `result.success` (plain xAPI's course-level `passed`/`failed` with `result.completion: true`, FIXPLAN-v4 §4 O-4b); or a `terminated` was processed in this batch while `completion_webhook_at` was strictly `null` before the request. Otherwise the completion is held: no webhook, no latch. A held completion is released by a later request that meets the rule, or by the sweeper of step 5 once it is 15 minutes old. Scored modules therefore fire within seconds (A.1 packages in the same request as today, no delay added); unscored cmi5 modules fire at the session's real exit; unscored plain-xAPI modules fire from the sweeper. **Once a message has gone out, at most one more follows, always `passed: true`, when the attempt becomes passed after a message that said `passed: false` (step 4); nothing else is ever re-sent.** The contract, stated once for every runtime: at most two `course_completed` messages per official attempt; a change of score without a change of pass/fail, a `failed` that arrives after a message sent without a result, a granted retake starting, and the official result changing because the attempt rules were recomputed (ADR 0014 step 9: a pass can become a fail) are never pushed, and `learner-summary` and `progress` are authoritative for them (step 8). An attempt that has received no AU `completed`, `passed` or `failed` is not complete and is never held, whatever it has received about its sub-activities (Context: the closed-before-Results case and the attempt left with tries remaining).

### B. Steps

2. **The decision is a pure function.** New file `lib/integrations/webhook-hold.ts` in the existing `lib/integrations/` module (no new folder), `restart.ts`/`abandon.ts` shape: no `next/*` import, no runtime Supabase import. `decideCompletionWebhook(input)` with `input = { official: boolean; before: { complete: boolean; successStatus: string | null; webhookAt: string | null | undefined }; after: { complete: boolean; successStatus: string | null }; batch: { completingStatementCarriedSuccess: boolean; terminated: boolean } }` answers `"none" | "hold" | "fire" | "refire"`, in this order: (a) not official, or not complete after the request → `none`; (b) `before.complete && before.successStatus !== "passed" && after.successStatus === "passed" && typeof before.webhookAt === "string"` → `refire` (step 4): the attempt became passed after a message that said `passed: false`, whether that message carried a `failed` (KIVO ADR 0008 D-2) or no result (sent by the `terminated` branch or the sweeper); (b′) `typeof before.webhookAt === "string"` (already fired) → `none`; (c) `after.successStatus !== null && after.successStatus !== before.successStatus` (the pass/fail became known, or a `failed` became `passed` on a row that never latched), or `batch.completingStatementCarriedSuccess && !before.complete`, or `batch.terminated && before.webhookAt === null` → `fire`; (d) otherwise `hold`. The null check in (c) is an explicit `=== null`, never `!x`: `undefined` means the column could not be read (step 3), and the `terminated` branch must stay inert then, because `fireCompletionWebhookForAttempt` falls through to firing on a database without 0082 (`webhook.ts:68–71`) and would fire on every later `terminated` of an unscored module. The same file exports the sweeper of step 5, the provider's selection of step 6 and the start-date constant `WEBHOOK_HOLD_SWEEP_FROM` (step 5), so the cron step and the Attention provider share one definition of "held". `successStatus` in `before` and `after` is `"passed"`, `"failed"` or `null`, where `null` stands for the column's `'unknown'` (`0003_attempt_status_split.sql:21–22`: `not null default 'unknown'`; normalised in step 3), so (c) compares known results only.
3. **The route (`app/api/xapi/statements/route.ts`).** The `before` value is taken where line 50 reads it today and the `after` value where line 144 does. ADR 0014 step 4 turns the before-request read (lines 41–50) into one error-checked `select *` of the bound row, kept for the request, with 503 before any insert on an error or no row; from that row `before = { complete: isCompletedAttempt(row), successStatus: row.success_status === "passed" || row.success_status === "failed" ? row.success_status : null, webhookAt: row.completion_webhook_at }` (the column is `not null default 'unknown'`, `0003_attempt_status_split.sql:21–22`; in this record `null` means `unknown`; the `after` read is normalised the same way), where `webhookAt` is `null` on a 0082 database when not latched and `undefined` where the column is absent (the key is missing from the row), exactly the distinction step 2 relies on. The pull-request order is ADR 0014's PR 1a first, then this record's PR, stated the same way in ADR 0014 step 4. Should this record reach the route before ADR 0014 does, `attemptStatus()` (lines 41–49) is widened instead to one select of `completion_status, success_status, completion_webhook_at`; when that select errors (a select naming a column the database lacks errors as a whole, the hazard `webhook.ts:72–76` documents for `reference_code`), it re-reads the two status columns as today and answers `webhookAt: undefined`; when both reads fail it answers `{ complete: false, successStatus: null, webhookAt: undefined }`, as today's `.catch(() => false)` does. The `after` read stays the two-column read of today (`complete` and `successStatus` are all it needs), `successStatus` normalised as above. ADR 0014's gate for flagged rows (no insert, no derivation, `officialRun` false for a flagged row) sits before and around this block and is unchanged by it. Inside the loop (lines 56–139) two flags are kept over the elements that were processed (`toProcess` not null): `terminated` when an element's verb is `terminated`; `completingStatementCarriedSuccess` when an element's verb is `completed`, `passed` or `failed` and `typeof result.success === "boolean"`. The `officialRun` computation (lines 145–153, a failed classification treated as official) and the gamification block (lines 158–170) are unchanged. Lines 173–175 become: `decideCompletionWebhook({ official: officialRun, before, after, batch })`; `fire` → `fireCompletionWebhookForAttempt(session.attemptId, kind?.attemptNumber ?? null)` as today; `refire` → the same function with `{ refireFrom: before.webhookAt }` (step 4); `hold` and `none` → nothing. One log line per `hold` and per `refire`, ids only (`{ event: "webhook_held" | "webhook_refired", attempt_id }`).
4. **The re-fire on becoming passed, once.** `fireCompletionWebhookForAttempt(attemptId, attemptNumber, opts?: { refireFrom: string })`: with `refireFrom`, the latch update (`webhook.ts:62–67`) uses `.eq("completion_webhook_at", opts.refireFrom)` in place of `.is("completion_webhook_at", null)`, a compare-and-set on the value this request read before the batch, so of two requests that observe the same change to `passed` exactly one moves the latch to `now()` and fires; a 0-row answer returns as today (line 68–71); an error on that update (a database without 0082) returns without firing, which keeps the re-fire inside the strict-null rule of step 2 (defensive only: both environments are at 0099). The payload is built exactly as today from the row (lines 77–122): `passed: true`, `score` = the row's score (on cmi5/xAPI the highest AU-level scaled score received on any verb, `process-statement.ts:117–125`; on the SCORM 1.2 import the last committed score, `commit/route.ts:168, 179`; for a KIVO package the passing Results score, because a pass at the course mark exceeds any earlier fail), the same `attempt_number`, `official: true`, `event: "course_completed"`; no new field. The analysis's decision 2, "the score of the statement that set the final status" for every sender, is a grading rule the analysis puts to the owner (ADR 0014 "Decisions requested from the owner" records the answer when given), not decided here; it would change only what `score` this message and the pull carry for non-A.1 content. "Once" rests on two things: the compare-and-set, and `process-statement.ts:107–115` (a `passed` is never downgraded, so the change to `passed` happens once per attempt); KIVO ADR 0008 D-2 (one upgrade per registration) is why KIVO packages reach it at all, and under course-result decision 1 an A.1 cmi5 package never does. The 0082 column comment ("Set once when the CRM course_completed webhook is fired", `0082:21–22`) becomes stale on re-fired rows; the code comment at `webhook.ts:55–61` says so; no migration for a comment. `tests/unit/attempt-write-sites.test.ts:209` lists `lib/integrations/webhook.ts` with one `course_attempts` write; the entry becomes `receivers: ["svc", "svc"], what: "webhook latch; the re-fire compare-and-set"` if the compare-and-set is a second call site, or stays as it is if the same call site takes the predicate from the option (the executor records which). No other file gains a `course_attempts` write: the sweeper and the provider only read, and the sweeper fires through this function, whose latch is the concurrency guard against a request firing for the same attempt at the same moment.
5. **The sweeper is a step of `/api/cron/gamification-refresh`.** `sweepHeldWebhooks(svc)` in `webhook-hold.ts` runs inside `run()` (`gamification-refresh/route.ts:22–37`) after the matview refresh, fail-isolated: its outcome goes into the result as `webhook_sweep: { scanned, fired, skipped, error? }` and into the heartbeat detail (`recordHeartbeat`, line 45), and it never changes `ok` (line 33–36 keep deciding the 500 from the refresh alone). Selection intent, service-client selects in pages of 200 rows, keyset-paged on (`completed_at`, `id`) past rows that `classifyAttempt` skips, stopping after 200 fires or 1,000 rows scanned per run (so complete rows that are never official, which keep a null latch for good, cannot fill the cap and hide a held official row behind them): `course_attempts` rows that are complete (`completion_status = 'completed' or success_status = 'passed'`), `status <> 'abandoned'` (abandoned is never official, ADR 0004 step 11), `completion_webhook_at is null`, `completed_at < now() - 15 minutes`, `completed_at >= WEBHOOK_HOLD_SWEEP_FROM`, joined through `course_versions` to `manifest_type in ('cmi5', 'xapi')` (`0076_xapi_manifest_type.sql:26–28`). The type bound is required: the SCORM commit route never sets the latch (`commit/route.ts:306`), so an unbounded sweep would re-send `course_completed` for every SCORM attempt ever completed. The completeness bound excludes every attempt that has received no AU `completed`, `passed` or `failed`: an attempt closed before Results and an attempt left with module tries remaining are never candidates. For each candidate the sweeper re-runs `classifyAttempt` (`attempt-kind.ts:32`): `official: true` → `fireCompletionWebhookForAttempt(id, attemptNumber)`; `official: false` or a null classification → skipped, logged with the id, retried next run. The 15 minutes is the owner's N ("F yes, 15 minutes"), a constant next to the decision function. One log line per run, ids only (`{ event: "webhook_sweep", fired: [...], skipped: [...] }`). A database without 0082 errors the select (the latch column is named in it): the sweep reports the error and fires nothing, which is the same consequence as the inert `terminated` branch: W-1's unscored path needs 0082 on the environment (both environments have it). No new `cron.yml` line, no `CRON_CADENCE_MIN` change (`tests/unit/cron-cadence.test.ts` stays green as it is), no new route; the sweep rides the existing 15-minute schedule, so a held unscored plain-xAPI completion fires 15 to 30 minutes after `completed_at`, plus whatever GitHub delays the run by; a starved schedule catches up on every held row when it next runs, because the window is a fixed start date, never a rolling one.
   **The start date.** `WEBHOOK_HOLD_SWEEP_FROM` is one ISO date constant exported from `webhook-hold.ts`: the UTC date on which this record's build first reaches staging, set in the pull request before merge and recorded under this record as a dated note; one value for both environments, never moved. Why one value is safe on production, whose deploy comes later: under today's code every official cmi5/xAPI completion takes the latch before anything else (`webhook.ts:62–71`), so a production row completed between the two deploys already carries the latch and is never swept; the residual is a row whose latch update errored and fell through to firing (`webhook.ts:68` returns only on a clean zero), which the sweep would fire once more with the same values. Rows completed before the date are never touched by the sweep or the provider, whatever their latch: they were handled under the old rule and the consumer reconciles them with `learner-summary` as the guide already says.
6. **The alert is an Attention Center provider, not a cron step** (a step inside a starved cron cannot raise the alert about the starved cron). One registry entry appended to `ATTENTION_PROVIDERS` (`lib/attention/types.ts:68–132`): `{ type: "held-webhooks", label: "Completion webhooks held", description: "cmi5/xAPI completions whose CRM webhook has not fired after 24 hours.", defaultEnabled: true, defaultPriority: "high", configurablePriority: true }`; `effectiveConfig` (lines 140–169) gives every organisation the defaults until an admin changes them. | A held scored completion never fires (a `passed` lost after `completed`, M-1) | the `terminated` branch fires at the session's exit and the sweeper fires 15 minutes after completion; the payload then says `score: null, passed: false`, the attempt stays complete with no score, and under the policy only an admin grant gives a new official attempt (addendum §3.4 item 7); A.1's KE-8 removes the normal-path cause |
| Unscored cmi5 modules fire at every `terminated` | the branch is edge-triggered on `completion_webhook_at` strictly null before the request; the latch is the second guard; two `terminated` requests that both read null (concurrency) are the latch's job |
| The first sweep re-sends history | the type bound (SCORM never latches) and the fixed start date; rows completed before the date are never touched |
| The sweep fires for a revision row or a non-official row | `classifyAttempt` re-run per candidate; a null classification skips the row; from 0103 a flagged row never becomes complete (ADR 0014) |
| A starved cron hides held rows | the Attention Center provider needs no cron; the fixed window lets a late sweep catch up |
| The re-fire fires twice or never | the compare-and-set on the value read before the batch (one winner); `process-statement.ts:107–115` makes the change to `passed` happen once; a database without 0082 returns without re-firing; the consumer is told what the second message means |
| A `passed` processed while the sweeper or a `terminated` request fires the same held row | the firing call reads the row after it takes the latch (`webhook.ts:62–83`): a `passed` written before that read is carried; one written after it meets the taken latch and is not pushed (`webhook.ts:68–71`); rare (the sweep takes rows older than 15 minutes only); the pull is authoritative; recorded, not fixed. | Existing records | no row is rewritten or deleted; no migration |

## Consequences

- Scored cmi5 and xAPI modules keep firing within seconds, with the score and `passed` set; A.1 packages fire once in the request that carries the pair, as the route already does for an array delivery. Older packages and third-party cmi5 AUs get the corrected payload at the `passed`/`failed` instead of a null score at the `completed`.
- Unscored cmi5 modules fire at the session's real exit; unscored plain-xAPI modules (KE-6) fire from the sweep, worst case about 30 minutes after completion plus the scheduler's delay. The consumer is told that `passed: false` on such a module means "no pass mark".
- An attempt closed before its outcome is sent is not complete: nothing is held and nothing fires until the learner finishes (addendum §3.4). Ambak never invents a result.
- A learner who fails and then passes in the same official sitting (KIVO ADR 0008 D-2) is recorded as passed, and the CRM now receives a second `course_completed` with `passed: true` for the same `attempt_number`; without it the CRM would keep "not passed". The same second message follows a pass that arrives after a message sent without a result (the `terminated` branch or the sweeper). The CRM therefore receives at most two messages per official attempt on every runtime: SCORM 1.2 already sends exactly these two (`commit/route.ts:251–255`), and no latch is added there, because one would suppress its second message (Alternatives). A change of score without a change of pass/fail is not sent on any runtime; the pull is authoritative for it. For a KIVO A.1 cmi5 package under course-result decision 1 a `failed` leaves only when the result is final, so the CRM gets one message and the re-fire is dormant; it serves pre-A.1 packages, third-party cmi5 and plain xAPI, and A.1 if decision 1 is declined. The addendum records the engine side of D-2 (a `passed` after a `failed` inside one cmi5 session) as a cmi5 deviation Ambak accepts, with its clean fix in a later engine release (§6 stated default (i)); ADR 0014 step 19's session rule reports it per package as a finding (`outcome_twice_in_session`), so the deviation is visible rather than silent.
- An attempt left with module tries remaining is in progress with no score: nothing is held and nothing fires until its result is final; the CRM pull shows `in_progress`, `score: null`, `progress_pct` ≤ 99 for as long as that lasts (under course-result decision 1, until the learner passes, uses every try, can no longer reach the pass mark or presses "Finish now"; ADR 0014 rule A and its Consequences say what else that means in Ambak: reminders, the overdue count, the journey day). Ambak never invents a result here either.
- A granted retake is a new official attempt with its own messages, at most two, so a `passed: false` can follow a `passed: true` for the same learner and course with a higher `attempt_number`; `attempt_number` and `official: true` (`webhook.ts:120–121`) already mark it and the guide says so (ADR 0014 step 7 and step 11 (7) state the same sentence).
- The SCORM 1.2 commit path is unchanged: it already follows the at-most-two rule; its second message's `completed_at` is the time of sending, and a SCORM message can very rarely arrive twice with identical values.
- A revision visit never reaches the CRM through this path: a revision row never completes, never latches and is never swept; Ambak records only the visit (ADR 0014).
- The latch's meaning widens from "fired once" to "fired, and moved once by the re-fire"; the sweep and the provider read only whether it is null.
- Code only; no `cron.yml` change; no migration; the hazard list of `docs/ARCHITECTURE.md` §9 is unchanged.

## Alternatives considered

- **Fire at the first transition to complete, as today:** the CRM receives `score: null, passed: false` for every non-A.1 cmi5 pass (W-1); rejected.
- **Hold with no sweeper:** an unscored plain-xAPI module sends no `terminated`, so its completion would never reach the CRM; rejected.
- **A rolling window ("held rows from the last 24 hours") instead of a fixed start date:** the first run after a long outage would skip rows older than the window, and a window that reaches back far enough to be safe re-sends history; rejected.
- **A new `cron.yml` schedule or a new cron route:** a schedule fires on production as soon as it is on `main`, before the route exists there (`docs/ARCHITECTURE.md` §9), and `report-card-refresh` showed what that costs; rejected in favour of a step inside a route that is already deployed and scheduled.
- **A `held` column or a `webhook_status` column:** not needed; a null latch on a cmi5/xAPI attempt already means "never attempted", because the latch is taken before the URL check; rejected (no migration).
- **The alert as a step of the cron:** a step inside a starved cron cannot raise the alert about the starved cron; rejected in favour of the Attention provider, which runs when the admin landing loads.
- **The re-fire without a guard (request-local detection only):** two concurrent requests observing the same transition would both fire; the duplicate would carry identical values, so the consumer's state would be right either way; rejected in favour of the compare-and-set, which needs no column.
- **A second latch column for the re-fire:** one timestamp would need a migration; rejected while the compare-and-set on the existing column gives one winner.
- **A payload field marking the re-fire (`supersedes_previous: true`):** a contract change for a case the consumer can already tell from the sequence (`passed: false` then `passed: true`, same `attempt_number`); not taken; recorded as an option if the consumer asks for it.
- **A latch on the SCORM commit route** (course-result analysis revision 2, L-1): it would stop the message SCORM 1.2 already sends when an attempt becomes passed after completing (`commit/route.ts:251–255`), so the CRM would keep "not passed" for a learner Ambak shows as passed; FIXPLAN-v4 §5.5 says "the SCORM path is unchanged", and the sweeper's type bound (step 5) relies on SCORM never latching; rejected. The SCORM path already follows this record's rule (one message at completion, one more on becoming passed) and is left unchanged; leaving it unchanged is not an addition, so nothing is put to the owner about it.
- **A separate `course_result_updated` correction event with its own latch** (course-result analysis revision 2, §5.3): the compare-and-set on the existing latch column, the same event and no new field do the same for the only correction that exists (a change to passed); a new event would be needed only for score-only corrections, which no consumer has asked for; rejected.
- **Re-firing only on `failed` → `passed`** (this record as first written): a pass after a message sent without a result (the `terminated` branch or the sweeper) would never be pushed, which is W-2 again on the hold's own fallback path, and the runtimes would follow different rules, because SCORM's `justPassed` already covers `unknown` → `passed` (`commit/route.ts:253–254`); widened to any change to `passed` (step 2 (b)).
- **A per-request timer ("fire in N minutes unless the pass/fail arrives"):** the Worker has no scheduler and the request must return; rejected.
- **Widening `attemptStatus()` without the fail-soft re-read:** on a database without 0082 the three-column select errors as a whole and the route would treat every attempt as incomplete, firing nothing; rejected.
