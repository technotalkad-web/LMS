## 1. The system today

### Stack

- Next.js ~15.5 App Router, built for Cloudflare Workers by `@opennextjs/cloudflare` (fetch-only worker: no `scheduled` handler, so GitHub Actions drives the crons). `AGENTS.md`: this Next.js differs from older releases; read `node_modules/next/dist/docs/` before writing code. The App Router runs Next's bundled react-dom (`node_modules/next/dist/compiled/react-dom`), not the app's own; ADR 0013 (accepted 2026-10-19) patches its lost-ping bug at bundle time through a webpack loader until a Next upgrade carries the fix (§9).
- Supabase per environment: Postgres with RLS and tenant isolation, Auth (magic link, password, SAML), Storage (`course-content` bucket for packages, `public-assets` for thumbnails and branding), Edge Function `send-smtp`.
- A Cloudflare R2 storage adapter exists (`lib/storage/r2.ts`, migration 0077) but `STORAGE_DRIVER = "supabase"` on both environments (`wrangler.toml`), and every staging version has `storage_driver = 'supabase'` (the column reaches production with 0077). Steps 6, 7 and 9 of `docs/CONTENT_STORAGE.md` (copy to R2, flip the driver, empty the Supabase bucket) are not done; step 8's workflow was enabled early and copies the unused R2 bucket.
- Backups: nightly `pg_dump` of the production database to Backblaze B2 (`backup.yml`, which also overwrites a `latest/` pointer). The content backup (`content-backup.yml`) runs `rclone sync` from the unused R2 bucket and fails every night; production course packages have no scheduled backup today. A one-off snapshot script exists on branch `ops/storage-snapshot` (ADR 0003).

### Roles

`organization_members.role` (enum `org_role`): `super_owner`, `admin`, `data_analyst`, `user`. `canManage` = super_owner or admin; `canViewReports` adds data_analyst (`lib/auth/permissions.ts`). `data_analyst` is RLS-plain: analyst-visible pages read with the service role after the permission check. A platform owner exists above organisations (migration 0021).

### Content

`courses` → `course_packages` (one per language slot: `language`, `display_name`, `is_active`) → `course_versions` (one folder `courses/{courseId}/{packageId}/v{n}/`, intended immutable but not yet enforced — objects are written with upsert and `storage_prefix` has no unique index, see ADR 0003; `upload_status`, `storage_driver`, `manifest_type` ∈ `scorm12 | cmi5 | xapi`). Packages come from KIVO (the in-house editor; cmi5 or SCORM export) and from third parties. SCORM 2004 and multi-AU cmi5 are not supported.

### Learning-data flow

1. Launch (`app/[org]/(learner)/courses/[courseId]/launch/page.tsx`): creates or resumes a `course_attempts` row; cmi5/xAPI launches mint a `cmi5_launch_tokens` row; content is served from the attempt's own version by `content/v/[versionId]/[...path]/route.ts` (step 0, #171). The legacy `content/[...path]/route.ts` is kept for one release.
2. Runtime writes: SCORM commits (`app/api/scorm/[attemptId]/commit`), xAPI statements (`app/api/xapi/statements`), xAPI State (`app/api/xapi/activities/state`). Every write is conditional on `status <> 'abandoned'` and answers 410 otherwise (`lib/attempts/abandon.ts`).
3. Attempt derivation: `lib/xapi/process-statement.ts` (completion only from AU-level statements: `launchedActivityIds`, `isAboutAu`), `lib/scoring/*` (migration 0081: one official attempt; `courseStatus()`).
4. Consumers: Report Card (`lib/manager`), CRM/Yoddha (`lib/integrations`: catalog, progress, learner-summary, completion webhook), journeys and XP (RPCs called from the write routes), question-analytics matviews `mv_course_interaction_breakdown` (0031) and `mv_course_interaction_top_wrong` (0035), built from `xapi_statements` only (the other 0031 report matviews read attempts), tenant LRS feed (`lib/lrs`: outbox, profile `ambak-v1`, sweeper behind `/api/cron/lrs-forward`).

## 3. Principles

1. Migrations are applied by hand in the Supabase SQL editor, staging first, then production. Never the Supabase CLI: it is linked to production.
2. Every new table or view gets RLS (deny-all or a scoped policy) and literal grants in the same migration; every new function gets explicit execute grants. `scripts/check-migration-grants.mjs` enforces the table/view grant part in CI (from 0073); RLS and function grants are checked in review.
3. Learner history is never rewritten or deleted: attempts, statements, stored package bytes. Correction happens through new rows, new versions, pointer changes and labels.
4. Production is owner-run: migrations, release tags, Cloud Run and editor deploys. Every production action is explained before it happens. A `v*.*.*` tag deploys production; never push one as a bookmark.
5. Staging first. Staging holds test data (owner's standing direction, 2026-10-18; §1 Data row): it may be created, reset, modified or deleted when development, testing, debugging or verification needs it. No test or seed data on production. No email to real learners from tests.
6. Deploy-safe in both orders: code tolerates a missing column; a `cron.yml` schedule line ships only after its route is live on production, and a `CRON_CADENCE_MIN` entry only after its schedule fires.
7. Folder structure, module boundaries and patterns change only through an ADR.

## 4. Governance

- Fable 5.1 decides (the `advisor` tool and the `architect` agent in `.claude/agents/architect.md`); Opus 5.5 codes from the plans. The architect writes only this file and `docs/adr/`.
- The advisor is consulted before schema changes, new modules or folders, login/roles/permissions changes, API changes, new libraries or integrations, anything about grading, privacy or data, when the same error happens twice, and before a big task is declared finished.
- Decision flow: the architect writes an ADR as Proposed → the owner accepts or changes it (steps individually, ADR 0001 decision 2) → the ADR is marked Accepted → the executor builds from it → the verification named in the ADR runs. An accepted ADR is never rewritten; a later ADR supersedes it.
- If advice or a request conflicts with this file or an accepted ADR, work stops and the owner is asked.

## 9. Known hazards

- Every non-main push and every PR event runs the e2e purge against staging: all `qa-*` organisations and `@example.test` users are deleted. Never push while a harness that seeds `qa-*` data is running. Lifecycle specs seed `lifecycle-*` / `@lifecycle.test` data through `tests/bot/lifecycle/data.ts`, which the purge never matches (`tests/unit/test-data-namespace.test.ts`); a lifecycle spec that still imports its seeding helpers from `tests/e2e/helpers/supabase` is in the purge's namespace. Neither the purge nor the 48 h lifecycle cleanup deletes the package files of the organisations they remove from the staging storage bucket (accepted staging debt, `tests/bot/README.md`).
- A `cron.yml` schedule fires on production as soon as it is on `main`, even when the route is not deployed there; `report-card-refresh` has been returning 404 since 2026-10-07 for this reason. The mirror hazard: a `CRON_CADENCE_MIN` entry whose schedule is not firing pages the watchdog.
- Any `v*.*.*` tag pushed to `origin` deploys production.
- The Workers staging is on the free plan: any SSR page can fail with error 1102 at random; Cloud Run is the deterministic staging target but needs an owner deploy.
- supabase-js head/count probes report a missing table as present; verify schema with real selects in the SQL editor.
- The Supabase CLI in this repository is linked to production; it is never used for migrations.
- Inside a `security definer` function or an FK cascade, `current_user` is the owner, not the caller; role checks in triggers use the JWT role claim (ADR 0003 step 10).
- `publishVersion()` (`lib/courses/upload.ts`) repoints `courses.current_version_id` on every upload and every "Make current" on any slot: the last published slot becomes the course default. This is how the Gujarati slot became the Turning Escalations default (ADR 0004 step 12a). ADR 0008 B (decided 2026-10-17) replaces this with the same-slot rule and an explicit "Set as default"; until it ships on an environment, an upload to any slot can still move that environment's course defaults, and the P1 audit checks each course's default against its slots. The Library cannot move a course default between slots until then: "Make current" is offered only on non-current versions.
- Both `force_restart` paths (replace-package and direct-upload finalize) abandon the in-progress attempts of every prior version of the package, not only the one being replaced (ADR 0004 step 14a). ADR 0008 A adds the per-version restart route; the selection of the two paths is unchanged. Reporting hazard (found 2026-10-18): the multipart route discards the error of its `course_versions` read (`versions/route.ts` 165–171), so a failed read answers 200 with `restarted: 0`; `abandonOldAttempts` (`lib/courses/direct-upload.ts` 707–725) discards the errors of both its read and its update and its caller throws the count away, so the Library's Replace dialog shows nothing in any outcome; and spec 34 skips its force-restart case on any non-ok body matching `/restart failed|constraint/i`, so a real failure reads as a skipped test. The new version is already published when the restart runs on both paths (`lib/courses/upload.ts` 186 inside `uploadCoursePackage`; `direct-upload.ts` 416 before 419). ADR 0011 (accepted 2026-10-18; code only, no migration) makes both paths check every read and update through one implementation (`lib/attempts/force-restart.ts`), report a genuine zero only after a successful selection read, re-read any shortfall, answer 500 `{ published: true, restart: "failed", … }` on failure with the per-version restart as the retry, show the outcome in the Library, and removes the spec 34 skip; the hazard stands on an environment until that code is there (production has no attempt rows as of 2026-10-17). The qa purge that runs on every non-main push (first bullet) is the only known deleter of attempt rows and was the cause of the 2026-10-18 spec false alarm, not an app race.
- `package_validations` is writable by any org admin through PostgREST (0070 policy `for all`): the 0098 override columns, `verdict` and `report` can be set outside the super_owner override route, and both upload gates accept a `blocked` row whenever `overridden_at` is set. ADR 0008 C (accepted 2026-10-17; code first, then migration 0099; on production only after v1.3.0) makes writes service-role only; the hazard stands on an environment until C is there: closed on staging on 2026-10-18 (0099 applied after both staging deployments ran 9f96318; spec 52 18/18), open on production until 0099 follows v1.3.0. 2026-10-20: closed on production too (0099 applied after v1.3.0 went live; `docs/release/v1.3.0.md` §6.7).
- `course_attempts` is writable by any learner through PostgREST with their own session (0002 policies `members create own attempts` and `members update own attempts`, never narrowed; no column restriction, no write trigger): a learner can PATCH `status`, `score`, `completion_status`, `success_status`, `completed_at`, `progress_pct` or `cmi_data` on their own rows (reviving an abandoned attempt, forging a pass) or POST a never-launched completed row; the launch page's attempt insert, its journey-tag update and the SCORM commit route still write with the caller client, so the policies cannot be dropped before that code moves to the service client. ADR 0009 (accepted 2026-10-17; ships in the next build with ADR 0008 C and D) moves those writes to the service client first, verified on every deployment that shares the database (on staging the Workers staging and the Cloud Run trial), and only then drops the two policies and revokes insert/update/delete in 0099 section 2, together with the `v_course_attempt_summary` / matview corrections deferred by ADR 0004 decision 9 (section 3); on production only after v1.3.0; the hazard stands on an environment until that is there, and 0099 applied before the code on any deployment breaks every launch there: closed on staging on 2026-10-18 in the required order (both deployments on 9f96318, then 0099; spec 55 guard branch 12/12), open on production (no attempt rows there as of 2026-10-17) until 0099 follows v1.3.0. 2026-10-20: closed on production too, in the required order (v1.3.0, which carries the server-write code, live since 2026-10-19; then 0099; `docs/release/v1.3.0.md` §6.7).
- The SCORM commit route (`app/api/scorm/[attemptId]/commit`) derives status, completion, success and score from the posted CMI object for any attempt the caller owns, without checking the version's `manifest_type`: a learner can complete and pass their own cmi5 or xAPI attempt with a score through it, with no AU-level statement, and the completion flows on to XP, journeys and the CRM webhook; 0099 does not close this, because the route writes as the server. ADR 0010 (accepted 2026-10-18; code ships in its own build) refuses non-`scorm12` attempts with 409 `wrong_runtime` (code only, no migration) and answers a fail-closed 503 that writes nothing when the attempt's type cannot be read; the hazard stands on an environment until that code is there (production has no attempt rows as of 2026-10-17); the code was verified against staging on 2026-10-18 from branch `feat/adr-0010-scorm-commit-runtime` (spec 55 case (k) 409 on cmi5 and xAPI attempts, rows unchanged).
- An aborted or swept upload deletes its `uploading` row, so the next upload to that package reuses the version number and folder; `content-backup.yml` (`rclone copy --immutable` into an Object-Locked bucket, 02:30 UTC, before the 03:00 UTC reaper) then fails every night on that folder. ADR 0008 D (accepted 2026-10-17; code only, plus the workflow flags) keeps such rows as `failed` so numbers are never reused; the hazard stands on an environment until D is there, and `content-backup.yml` keeps `--fast-list` (ADR 0008 decision 3 note).
- The Library upload page pre-ticks "Send update notification email to affected learners" when replacing a course; a corrective upload emails every assigned learner unless it is unticked (ADR 0004 step 13).
- Next 15.5.x bundles a react-dom (`19.2.0-canary-0bdb9206-20250818`, `node_modules/next/dist/compiled/react-dom`, which the App Router uses instead of the app's own) in which a transition that suspends on a streamed RSC chunk inside a Suspense boundary already showing content can lose its ping: the fetched payload is never committed, and every later `router.refresh()` or soft navigation on that tab hangs until a full reload. It is timing-dependent (the RSC response must still be streaming when React reaches the segment): spec 54 test 7 failed 10 of 10 on the owner's laptop against `next start`, passed on Cloud Run staging and failed once on Linux CI (attributed by inference, not by trace). Every `router.refresh()` and soft navigation in the admin UI is exposed, not only Set as default. ADR 0013 (accepted 2026-10-19; code only, no migration) applies React's upstream one-line fix to the four bundled client builds when webpack bundles them (`next.config.ts`, `scripts/react-dom-ping-fix.cjs`) and fails the build when the bundled code no longer matches; the hazard stands on an environment until a build with the loader is deployed there. The loader is webpack-only: `--turbopack` (unused today) would need it ported to `turbopack.rules`, or Next upgraded past the bug, first; the react-dom-experimental copy and the app's own `node_modules/react-dom` are not patched.
