Repository gap it found: a replay from the repository alone stops at `0049_security_advisor_hardening.sql`, which alters `public.set_updated_at()`; no migration creates that function (it was made in the dashboard before the migrations existed). Production and staging have it, so the sitting is not affected; a fresh project built only from `supabase/migrations/` is. The `no-dashboard-fn` scenario keeps the gap visible. Closing it needs a new migration, outside this release.

### 7.2 Restore drill (owner)

`D:\LMS\restore-drill.cmd` on the owner's machine (not in the repository) downloads the newest encrypted database backup from B2, decrypts it on that machine, checks that it is a complete dump (header and end marker, table and data-block counts), shows counts only, and deletes the decrypted copy. It must print `RESULT OK`. This is gate item 7's drill, run after the first green run of the hardened backup workflow.

### 7.3 What this rehearsal cannot prove

- Failures that depend on production's real rows: duplicate version-number pairs (`C03`, `C04`), shared storage prefixes (`D02`), the 0032 constraint state (`C01`, `C02`, `C05`), and any row a new constraint or trigger would refuse. The harness runs on synthetic rows only. The read-only audit run on production first (§2.3 item 11, again at §4.2) is designed to catch these: its stop rules hold the sitting before any file is pasted, and 0098 refuses on its own while `D02` is not 0.
- That the production dump restores into a Supabase project (the restore half of ADR 0003 step 4): the drill proves download, decryption and completeness by counts, not a restore. The disaster path of §8 (restore into a fresh project) stays unrehearsed.
- The hash-compare of one version prefix between the B2 content copy and the live bucket (the other half of ADR 0003 step 4): not part of this rehearsal.
- Both halves of ADR 0003 step 4 therefore stay open after v1.3.0 (ADR 0007 decision 7). They are not a gate item for this release. **Owner decision pending: when and where they are done** (the restore needs a Supabase project slot, §8).
- Supabase itself: its Postgres version (PGlite is 18.6), its roles, grants, default privileges, extensions and row-level security, and the SQL editor's batch and confirmation behaviour. The evidence there is staging, which took 0072–0097 one by one in earlier weeks and the 0032 no-op, 0098 and 0099 on 2026-10-17/18 through the same SQL editor, and the staging audit run of §2.3 item 10.
- Timing on production's nano compute, and locks held by live traffic (0032 and 0098 carry `lock_timeout = '5s'`, §4.1).

## 8. Rollback and forward-fix

- **The database has no rollback.** Production is on the free tier without point-in-time recovery, and the migrations have no down files. A failed file inside `begin … commit` (0032, 0098) changes nothing; the others are fixed forward and re-pasted (§4.5). Restoring the pre-sitting dump into a fresh project and repointing the app (`docs/ops/backup-restore.md` Scenario 1, steps 1–6) is the disaster path only: it loses every write since the dump, and it needs a free project slot, which staging and production occupy today. Finding one then is an emergency owner decision among the options §7 lists as not chosen; the rehearsal of §7 does not exercise this path (§7.3).
- **Code rollback** means redeploying `d86903f`, and it is valid **only before 0099 is applied on production** (§6.7). The header of `0099_postgrest_write_guards.sql` says that with the old code every launch fails with "Failed to create attempt", every SCORM commit answers 400 and every package validation insert fails: a rollback after 0099 would be a full launch outage. After 0099 the only paths are a forward-fix or a tag that carries the ADR 0009 server-write code.
- Before 0099: there is no tag for `d86903f`, and a `v*.*.*` tag must never be pushed as a bookmark. `workflow_dispatch` deploys the branch or tag it is run on, so the practical path is a branch at `d86903f` (for example `rollback/2026-09-17`) prepared before the tag and run with "Run workflow" only in an emergency. Owner decision: pushing any non-main branch triggers the staging e2e purge of `qa-*` data, so push it when no staging harness runs.
- Why the old code is expected to run on the schema after the sitting (before 0099). Three spot-checks against `d86903f`, **not exercised by any test**: `lib/courses/upload.ts` writes `storage_prefix` only when it inserts a version, so 0098's freeze of ready versions does not fire; `app/api/tickets/route.ts` inserts only `organization_id`, `user_id`, `subject`, `body` and `priority`, which satisfies 0095's insert policy (`source` defaults to `learner`; `category`, `context` and `outcome` stay null); 0096 re-creates `journey_audience_matches` with a defaulted seventh argument, so six-argument calls still resolve. Production also runs the old code on this schema between the sitting and the tag, but only for that short window. The old code lacks the step-0 versioned delivery and the P0 protections in code.
- **Forward-fix** is the default for a code fault: fix on `main`, verify on staging, tag `v1.3.1`.
- Learner data is never "rolled back" by editing rows: history is corrected by new rows, new versions and labels (`docs/ARCHITECTURE.md` §3.3).

## 9. Stop conditions in one list

Stop and ask (nothing further is applied) when:
- any audit row is `ERROR`, or the `Z90` number for the current moment is not 0 (one dated exception: on production before the sitting it reads `2`, from `B0073` and `B0073b` only, accepted 2026-10-19, §2.3 item 11; any other `at_before` mismatch is a stop);
- `A04` is not `postgres` (run again as `postgres`; read nothing from that grid);
- production is below 0071 (`B0070`, `B0071a`, `B0071b`), a migration is present above the first absent one (`Z02`), `Z01` is neither `0072` nor `0073` before the sitting (on production: `0074`, confirmed 2026-10-19, because production already holds 0073; there, any value other than `0074` is a stop), or a `B0099*`/`B0100*` row mismatches;
- `C04` is not 0;
- `D02` is not 0 and the repoint has not been done and ledgered;
- `A03` is not 0 on production;
- a paste fails with anything other than a lock timeout or the refusals listed in §4.5;
- the post-apply probe shows any `at_after` mismatch;
- before the tag: the owner has not yet seen the `D03` list, the release notes are not signed off, the stored-bytes check has not run with every mismatch ledgered (§2.3 item 12), a `D08.nnnnn` profile does not match the recorded decision, or `origin/main` is not the SHA in the release notes (§5).
