## 3. Reading the audit grid

One paste, one grid; its last row is `ZZ END OF AUDIT`. If that row is missing, the editor cut the result: raise the row limit or export CSV first. The file writes only a temporary table that lives in the editor session; it reads catalog tables and application tables and changes nothing (proven by a before/after hash of every table in the rehearsal replay, §7.2).

| Column | Meaning |
|---|---|
| `check_id` | A = environment, B = one presence probe per migration, C = the 0032 constraint state, D = data lists and counts, Z = summary |
| `observed` | what this database holds now |
| `exp_before` / `exp_after` / `exp_0099` | the expectation before the sitting, right after it (the post-apply probe), and after the later 0099 apply |
| `at_before` / `at_after` / `at_0099` | `ok`, `MISMATCH`, or blank where the row is for reading (`any`, `info`, `review`) |
| `note` | how to read the row and its stop rule |

Which column to read: staging today → `at_0099`; production before the sitting → `at_before`; production after the sitting → `at_after`; production after the later 0099 apply → `at_0099`. `Z90` counts the mismatches for each of the three moments; the number for the moment you are at must be 0, and the `review` rows must have been read.

### 4.5 If a paste fails

- Read the message. Do not continue to the next file.
- 0032 and 0098 run inside `begin … commit`: an error, a lock timeout or a deadlock rolls the whole file back. Fix the cause, paste the same file again.
- The other files have no explicit transaction. The SQL editor normally runs one paste as one transaction, but do not rely on it: every file was pasted twice in a row in the rehearsal replay without error (§7.2), so after fixing the cause, paste the same file again.

## 8. Rollback and forward-fix

- **The database has no rollback.** Production is on the free tier without point-in-time recovery, and the migrations have no down files. A failed file inside `begin … commit` (0032, 0098) changes nothing; the others are fixed forward and re-pasted (§4.5). Restoring the pre-sitting dump into a fresh project and repointing the app (`docs/ops/backup-restore.md` Scenario 1, steps 1–6) is the disaster path only: it loses every write since the dump.
- **Code rollback** means redeploying `d86903f`. There is no tag for it, and a `v*.*.*` tag must never be pushed as a bookmark. `workflow_dispatch` deploys the branch or tag it is run on, so the practical path is a branch at `d86903f` (for example `rollback/2026-09-17`) prepared before the tag and run with "Run workflow" only in an emergency. Owner decision: pushing any non-main branch triggers the staging e2e purge of `qa-*` data, so push it when no staging harness runs. The old code runs safely on the new schema (it ran on it between the sitting and the tag), but it lacks the step-0 versioned delivery and the P0 protections in code.
- **Forward-fix** is the default for a code fault: fix on `main`, verify on staging, tag `v1.3.1`.
- Learner data is never "rolled back" by editing rows: history is corrected by new rows, new versions and labels (`docs/ARCHITECTURE.md` §3.3).

## 9. Stop conditions in one list

Stop and ask (nothing further is applied) when:
- any audit row is `ERROR`, or the `Z90` number for the current moment is not 0;
- production is below 0071 (`B0070`, `B0071a`, `B0071b`), a migration is present above the first absent one (`Z02`), `Z01` is neither `0072` nor `0073` before the sitting, or a `B0099*`/`B0100*` row mismatches;
- `C04` is not 0;
- `D02` is not 0 and the repoint has not been done and ledgered;
- `A03` is not 0 on production;
- a paste fails with anything other than a lock timeout or the refusals listed in §4.5;
- the post-apply probe shows any `at_after` mismatch;
- the owner has not yet seen the `D03` list, the release notes are not signed off, or the stored-bytes check has not run (§2.3 item 12).
