## 1. What learners and integrations will notice (ADR 0007 step 8)

1. **One official attempt by default** (0081, #148). The platform default becomes one official attempt per course (it was three); after it, a learner can keep revising without it counting. Admins can require a pass (`pass_required`) and grant extra official attempts: learners can request one, admins grant in bulk, managers' support tickets lead to a grant (#150, #162; 0083, 0085, 0092, 0095). Attempts that already exist are unchanged.
2. **cmi5 modules complete only on a real completion** (#118, #119). A cmi5 or xAPI module completes when it reports completion for the module itself, not when a screen or question inside it reports one; before this, some KIVO modules completed at the first "Next". History: production holds `0` cmi5 attempts marked completed (completion status "completed") less than 60 seconds after the start (`D05`, 2026-10-19 audits); quick exits without a completion are not counted, although before #118 they also received a completion time. It also holds `0` completed cmi5/xAPI attempts (`D06`, 2026-10-19 audits) without a module-level completed, passed or failed statement. They stay as recorded (history is never rewritten).
3. **Completion webhooks for cmi5 and xAPI** (#148). The CRM completion webhook now fires for official cmi5 and xAPI completions too (before: SCORM only), never for revision runs. *CRM consumer sign-off.* Organisations with a webhook: `0` (`D07`, 2026-10-19 audits; no CRM sign-off needed).
4. **External LRS feed: analytics profile** (0078, #130–#132, #152, #154). Statements copied to a tenant's own LRS can use the `ambak-v1` profile (stable ids, learner and content dimensions, path and journey context, LMS events, SCORM included). Every enabled feed is set to `raw` (the shape it receives today) in the sitting unless its consumer was told about `ambak-v1` (ADR 0007 decision 3). *CRM/LRS consumer sign-off.* Enabled feeds: `0` (`D08`, 2026-10-19 audits; no profile decision or sign-off needed).
5. **Reset attempts look reset** (ADR 0004; #177, #183). An attempt an admin reset (abandoned) no longer shows as "In progress" anywhere: learner pages, Library, Report Card, progress integrations. The learner sees "Reset — module updated" and starts fresh. After v1.3.0, an in-progress attempt on a language package an admin has hidden is closed at that learner's next launch (the owner has seen the list, `D03` of the audit).
6. **Each attempt keeps its own version** (step 0, #171). A learner who started a module keeps being served the exact version they started, even after an admin uploads a newer one; switching language asks before restarting.

## 2. For admins

- **Uploads and the Library:** language chosen at upload (#116); package validation flags engine defects before a module can be assigned (#120); standalone xAPI (`tincan.xml`) packages upload, launch and resume like cmi5 (#121, #122, 0076); browser-direct uploads (#124–#126, 0077; storage stays on Supabase); versions grouped by language package (#127); a cross-course duplicate (same KIVO id or title in another course) is blocked, with a super-owner override that requires a reason (#177, 0098); a failed upload keeps its version number, so a folder is never reused (#184).
- **Course defaults:** an upload no longer moves the course's default language; "Set as default" is an explicit action, and the default slot cannot be hidden while another is active (#183).
- **Restarts:** restart learners on one specific version without touching newer versions (#183); a forced restart says how many learners were reset, and says so plainly when the reset failed or nobody was in progress (#190).
- **Scoring and reports:** attempt scoring rules per course, path and journey (#114, 0073); one official result everywhere (#156, 0090); per-course toggle for showing attempt history to learners (#113, 0072); progress percentages on attempts (#118, 0075).
- **Attention Center** (#150, 0086, 0087): one place for what needs an admin's attention, including uploaded-but-unpublished versions and course-default problems.
- **Managers:** reporting lines L1/L2/L3 (#157, 0091); Manager Report Card for L1, L2 and L3 with a precompute cache (#158–#161, 0092–0094); support tickets with context (#162, 0095); departments under business verticals and content mapping (#163, 0096); the manager visibility rule with an enforce switch and coverage pairs (#165, 0097).
- **Journeys:** calendar or progress unlock and a configurable daily reminder (#155, 0088, 0089).
- **Reference codes** for modules, paths and journeys (MOD/PTH/JUR, #147, 0079, 0080).
- **Pages update after an action** (#197, ADR 0013): after "Set as default", switching a course on or off, replacing content, assigning or any other action that refreshes the page, the page shows the result straight away. Before, it could keep showing the old state (for example the old default language in the course header) until a manual reload, and further clicks on that tab could stop responding. The cause was a bug in the copy of React that ships inside Next.js; the fix is applied when the app is built and is dropped once a Next.js upgrade carries it.
- **Fixes:** role change and removal on the Users page now really change the membership (#138); the bare organisation address goes to the dashboard after sign-in (#136); the Data Analyst lands on Learner Analytics (#166); failed-module and dashboard cards (#128, #129, #153); dashboard backgrounds (#117, 0074); mobile layout and language menu (#123, #151); branded loading states (#133); learning-path artwork (#111).

## 3. For the CRM and other API consumers (*CRM consumer sign-off*)

- **Employee sync** (#109, #110): `PUT/GET/DELETE /api/integrations/employees` with the organisation API key (joiners, transfers, leavers). Not on production before v1.3.0.
- **Catalogue and bulk progress** (#143, #145, #146): `/api/integrations/catalog` and `/api/integrations/progress`. The catalogue's `version_id` is the default language's current version, and `available` also requires that language to be active (#183).
- **Completion webhook** for cmi5 and xAPI official attempts (§1 item 3); payload unchanged (`attempt_number`, `official: true`).
- **Progress** excludes reset attempts from status and percentage; attempt counts and first/last access still include them, by design (ADR 0004 step 11).
- The catalogue's optional `analytics_tier` field, described in the integration guide, does not appear in v1.3.0: it belongs to the ALDS 2.0 build that ships switched off (§5).
- Integration guide: `docs/CRM_INTEGRATION.md` (§6 corrected for this release).

## 4. Protection of records (P0)

- A version's folder, launch file and type are fixed once it is ready; two versions can never share a folder (0098).
- A course or version with learner attempts cannot be deleted; deactivate instead (0098).
- An xAPI statement is stored once; a resent statement with different content never overwrites the stored one, and identical retries count once (#177).
- Package validation results and learner attempt rows are written only by the server in this release's code; the matching database guard (0099) follows after v1.3.0 is live (ADR 0008 C, ADR 0009).
- The SCORM save route refuses attempts that are not SCORM (ADR 0010, #187).

## 5. Built in, switched off: ALDS 2.0 package checks (P4, #195)

The code for the next phase is in this release but switched off on production: the server setting `ALDS_P4` is not set there, and its database change (0100) is not applied there. Learners, admins and integrations see nothing new from it: no badges, columns, fields or checks. (Staging may run it switched on for testing once 0100 is applied there; that changes nothing on production.)

- **What it does once switched on, in a later release:** it checks each uploaded ALDS 2.0 package and labels how far that package's analytics can be trusted (a tier badge in the Library and Reports, the optional catalogue field of §3), and it launches cmi5 modules with the launch settings the cmi5 standard defines. It never blocks an upload, and grades, completion, scores, the Report Card, CRM webhooks and journeys never depend on it.
- **Active even while it is off, and harmless to existing modules and integrations:**
  - A module can read its attempt's launch settings (`LMS.LaunchData`, which the cmi5 standard says belong to the LMS) but cannot change or delete them: such a request is refused (403). No module on any environment writes them today.
  - The LMS also accepts a module's progress messages when they carry the module id the LMS itself issues. Modules keep sending their own ids, which work as before.
  - A revision run no longer copies those launch settings from the attempt it continues (while P4 is off, none exist).
  - The super-owner "Re-run check" request answers "not enabled" (409); the Library shows no such button while P4 is off.

## 6. Operations

- Database: 28 hand-applied files in one sitting (0032 guarded, 0072–0098), verified by `ops/release-v1.3.0-audit.sql` before and after.
- Scheduled jobs: the `report-card-refresh` schedule returns only after the deploy is verified; the health check's cadence list covers the jobs that already run, now including the leaderboard refresh, the monthly leaderboard close and the journey reminders (ADR 0007 step 7).

The release is tagged only on a commit they passed on (runbook §2.1 item 2).
- Backups: encrypted nightly database dumps and Storage snapshots to B2 (#174, #178, #181); the backup job now fails instead of uploading when it cannot encrypt, and never publishes a dump as a run artifact (#191); CI checks migration grants (#170) and runs the unit tests (#177).
- Privacy of error reports (#191): session replays attached to error reports mask on-screen text and media, and sign-in links, invitation tokens and search terms are removed from error reports.
- Staging-only or not wired in (no production effect): the Cloud Run staging trial (#135, #144); the load-test scripts (#192); the ALDS rules module (P3, #193), used only by the switched-off build of §5.
