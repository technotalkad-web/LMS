**The order (the lead's ruling, 2026-11-10).** (1) The owner pastes 0103, then 0104, while production still runs v1.3.0. (2) The owner merges this pull request, pushes the tag, and the production deploy goes green with `ALDS_P4 = "on"`. (3) The owner pastes 0100. Why:
- **0103 must come before the code that uses it.** ADR 0014 step 2 binds it ("before the code of step 3 reaches that environment; production … before the tag that carries step 3"); the addendum note's item 14 repeats it; the file's header says so (lines 7–20): PR 1a's code refuses revision and grant launches on a database without 0103, by design (ADR 0014 step 3). The header also says "Today's code tolerates this file": nothing errors, and only the policy clamp takes effect at once. Staging took 0103 on 2026-11-04 while it ran `main` before #215: its `app/`, `lib/` and `components/` were v1.3.0's except one comment (#204), and its build differed by #212 (Next.js 15.5.29, OpenNext 1.20.16 and the matching react-dom patch script); no attempt write path had changed (`git diff v1.3.0..e366acf`). A1–A6 passed there. On production the clamp changes nothing visible: there are no courses.
- **0104 is safe in both orders** (its header lines 9–14; ADR 0017's "Deploy order" row, line 210): v1.3.0 never names the column; the new code holds a result without it and only the record is lost.
- **The flag goes before 0100.** With the flag on and 0100 absent, every P4 read or write of a 0100 object skips (`lib/alds/flag.ts`, `isAldsSchemaMissing`: the gate logs and skips, the launch page retries its insert without the P4 columns, no badge shows). The two parts of the cmi5 launch contract that need no 0100 object run as on staging: a cmi5 launch names the LMS-issued AU id, and the LMS.LaunchData document is written to `xapi_state`. Both are fail-soft, and with no course on production neither runs. With 0100 present and the flag absent, a staff launch is stored with `is_preview` false, 0100's delete guards count it as learner history, and an admin's course delete answers 409. So the flag is live first and 0100 lands after it; that pairing never exists on production.
- This is ADR 0014's own production order ("0103-then-0100", the addendum note's item 3) and the rehearsed scenario `0103-0104-then-0100`.

**One discrepancy, stated plainly.** 0100's header (lines 15–20) and ADR 0005's addition to note (k) say that between 0100 and the flag "app deletes carry the service_role claim and are not affected". Spec 50's observed run (2026-11-04: a build with `ALDS_P4` absent against the staging database, which holds 0100) got a **409 on the admin's course delete**, with the attempt count null: 0100's delete guard refused it. The cause: `DELETE /api/courses/<id>` counts learner attempts with the service role, by staff membership, so a staff launch does not count there; it then deletes through the signed-in admin's own client (`app/api/courses/[courseId]/route.ts` line 224), so the guard trigger sees the claim role `authenticated`, not `service_role`. The header's premise that app deletes carry the service_role claim does not hold for this route. The lifecycle nightly failed the same test while it built without the flag, until 2026-11-05 (ADR 0005 note of that date). **The observed result governs.** The order above avoids the pairing, so the 409 cannot arise on production. 0100's header is not edited: its bytes are what staging took and what §1's checksum names.
