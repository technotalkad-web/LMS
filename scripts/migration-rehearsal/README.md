# Migration rehearsal (v1.3.0)

The free local copy the owner chose on 2026-10-18 for the v1.3.0 practice run (`docs/release/v1.3.0.md` §7). It replays the repository's migrations on an embedded Postgres ([PGlite](https://pglite.dev) 0.5.10, Postgres 18.6) with a small Supabase shim and synthetic rows, runs `ops/release-v1.3.0-audit.sql` before and after the sitting exactly as the owner will paste it, and compares every result with `expectations.json`.

No network database, no credentials, no production or staging data. Nothing is written inside the repository.

## Run it

```bash
node scripts/migration-rehearsal/run.mjs                  # every scenario
node scripts/migration-rehearsal/run.mjs prod gap         # some scenarios
node scripts/migration-rehearsal/run.mjs --verbose        # also print each audit grid (synthetic rows)
```

PGlite is not a project dependency (`package.json` is not changed for it):

- `PGLITE_DIR=<folder>` uses an existing install: an `npm install --prefix <folder>` folder, or the package folder itself.
- Without `PGLITE_DIR`, the runner installs `@electric-sql/pglite@0.5.10` once into `<system temp>/lms-migration-rehearsal-pglite-0.5.10` with `npm --prefix` (`--ignore-scripts`, no lock file) and reuses it afterwards. It never installs into the repository's `node_modules`.

The runner needs only Node; it has been run on Node 22 (as CI does) and Node 24. It prints, for each scenario, every migration file applied (and re-applied where the sitting pastes it twice), and for each audit run the expected and actual value of each named check, the exact set of `MISMATCH` rows for that moment, `Z90`, and the read-only proof. The last line is `RESULT: PASS` or `RESULT: FAIL`. Exit code 0 = every check passed, 1 = a check failed, 2 = the run could not start.

CI runs the same command: `.github/workflows/migration-rehearsal.yml`, on every pull request and push that touches `supabase/migrations/**`, `ops/release-*.sql`, this folder or the workflow, and on demand (Actions → Migration rehearsal → Run workflow).

## Repository gap it found

A replay from the repository alone stops at `0049_security_advisor_hardening.sql`: it runs `alter function public.set_updated_at() set search_path = …`, and no migration creates `public.set_updated_at()`. The function was created in the Supabase dashboard before the migrations existed, so production and staging have it and a fresh project built from `supabase/migrations/` does not. The harness creates it in `shim-dashboard.sql`; the `no-dashboard-fn` scenario keeps the gap visible. Closing it would take a new migration (a schema change, outside this harness).

## What it cannot prove

- Anything that depends on production's real rows: duplicate version-number pairs, shared storage prefixes, the 0032 constraint state, rows a new constraint or trigger would refuse. The read-only audit run on production before the sitting is designed to catch exactly these, and its stop rules hold the sitting (`docs/release/v1.3.0.md` §2.3 item 11, §4.2).
- Supabase itself: its Postgres version (PGlite is 18.6), its roles, grants, default privileges, extensions and row-level security, and the SQL editor's batch and confirmation behaviour. The staging SQL-editor applies of 0072–0099 are the evidence there. 0103 grants and revokes every privilege it intends on its new objects, `service_role` included, so its after-apply A5 query must read on Supabase exactly what `assert-0103.sql` check (2) reads here; a difference is a defect in the file. The same holds for 0105: its after-apply A3 query must read on Supabase what `assert-0105.sql` check (2) reads here. Its cost on native Postgres and real group sizes is A1 and A8 on staging, not this harness (PGlite times overstate native Postgres).
- For 0107 (the ADR 0024 note of 2026-11-14, final review): (1) Supabase's default privileges. Until that review the privilege matrix of the objects 0107 creates was not evidence here: the shim gives no default privileges, so every "nothing for anon or authenticated" check on a new object passed whether or not 0107 revokes. `grants-0107-defaults.sql` now gives them everything by default in five scenarios, as a worst-case stand-in, and `0106-then-0105-then-0107` runs without it; which default privileges staging and production hold was not read, and 0107's own A5 and A23, inside the paste, are the proof there. (2) The SQL editor's request size: 0107 is 415,387 bytes and 7,947 lines (the git blob), about 8 times the largest file pasted so far by bytes (0053, 51,179 bytes) and about 7.4 times by lines (1,078); the before-checks run first, so a refusal costs nothing. (3) Postgres 17: PGlite is 18.6 and staging reads 17.6, so note N3's guards stay. (4) Anything that needs two connections: the purge's window between its read and its delete, the rule-change race of O3-j (5) (a completion that commits while an admin's rule change is in flight), lock waits against the app and the crons, and the race of two launches (`consume_grant`'s lock order is asserted on its stored body only). (5) A pasting role that may not SET ROLE to `anon` or `authenticated`: the rehearsal runs as a superuser, so section 0a's refusal never fires here; it was shown once on a scratch PGlite database with a non-superuser session.
- Concurrency: PGlite is one session. Two parallel `consume_grant` or `record_revision_visit` calls, and the `23505` race, are left to the staging e2e (`tests/e2e/attempts/consume-grant.spec.ts`, PR 1a).
- That last night's dump restores into a Supabase project, and timing on production's compute.

## When it fails

Read the `FAIL` lines. A changed migration or audit file that changes a result on purpose needs `expectations.json` updated in the same change, with the reason in the commit message. A migration added after 0099 is not part of the v1.3.0 sitting: it is rehearsed by its own scenario (0100 by `p4-0100`; 0103 by `0103-no-0100`, with `p4-0100-then-0103` and `0103-then-0100` for its two orders against 0100; 0104 by `0104-at-0099`, with `0103-then-0104` and `0100-0103-then-0104`; 0105 by `0100-0103-0104-then-0105`, with `0105-at-0104-no-0100` for a database without 0100; 0106 by `0103-0104-0100-then-0106` and `0100-0103-0104-then-0106`, with `0106-refused-without-0100` for its prerequisite check; 0107 by `0105-0106-then-0107` and `0106-then-0105-then-0107`, with `0107-refused-q8`, `0107-refused-q2` and `0107-refused-without-0106` for its refusals; with `0107-then-0108` for 0108 and `0107-0108-reverse-then-0107` for the reverse script of step 61; ADR 0024 step 63's `0107-0108-then-0109` is entered when 0109 exists), never by the `prod` one. The `static` step kind was added to the runner with 0103 (ADR 0014 step 2 and its addendum note of 2026-10-29): the word rule reads the raw file, so a forbidden token in a comment fails the rehearsal, not the paste.
